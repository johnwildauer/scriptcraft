## Findings

### Blockers

- **None.** The intended system can be identified and compared with the requirements. The empty [`apps/scriptcraft/`](../../apps/scriptcraft/) and [`crates/`](../../crates/) paths are correctly treated as desired placement rather than implementation evidence; unresolved framework, package, platform, command, extension, and PDF choices are generally disclosed rather than silently selected. No blueprint directly contradicts an explicit user decision or a mandatory Forge policy gate.

### Warnings

- **BP-REVIEW-W-001 — Core dependency direction is stated indirectly but not made enforceable.** **Severity:** warning. **Evidence:** [`technical-context.md`](technical-context.md:31-37) describes a UI shell above a headless core, and [`scriptcraft-desktop.md`](containers/scriptcraft-desktop.md:8-10) says the shell delegates semantic edits, layout, and persistence; however, [`screenplay-core.md`](components/screenplay-core.md:21-51) assigns all core components to the desktop container, while the feature composition also places them inside [`ScriptCraft Desktop Application`](features/screenplay-writing-loop.md:20-27). This makes the reusable-core-versus-app-shell ownership ambiguous even though the prose says the core is reusable. **Discrepancy:** the analysis recommends a one-way graph such as geometry → model → editing/session → layout → display/rendering, with persistence beside the semantic path and the app depending downward ([`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:616-640)). **Suggested action:** before implementation, record the intended graph and ownership explicitly: app/UI may depend on core/session/display results; core/model/layout/persistence must not depend on egui, window, widget, or app-shell types; render/export adapters consume layout output and do not paginate independently. **Required next state:** `draft` for the affected blueprints until the boundary is clarified; this remains a warning because the current desired direction is recoverable and comparison is meaningful.

- **BP-REVIEW-W-002 — `apps/scriptcraft` and `crates` placement is not yet an executable Cargo workspace decision.** **Severity:** warning. **Evidence:** [`technical-context.md`](technical-context.md:19-27) identifies [`apps/scriptcraft/`](../../apps/scriptcraft/) as the desired desktop boundary and `crates/scriptcraft-core/` or equivalent as a desired reusable package, while [`project-manifest.md`](../project-manifest.md:40-43) says the manifest and exact package structure remain unverified. The analysis presents a conceptual `core/` and `app/` layout ([`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:486-515)) rather than evidence about this checkout. **Suggested action:** make the workspace-foundation initiative choose and record the exact root [`Cargo.toml`](../../Cargo.toml), workspace members, package names, and path dependencies, including whether the core lives under `crates/` and the binary under `apps/scriptcraft/`. Do not infer that the analysis's conceptual `core/` and `app/` directories should replace the observed repository directories. **Required next state:** `draft`/`provisional` until the package placement and membership are verified; no implementation or Cargo command is claimed here.

- **BP-REVIEW-W-003 — The Rust/Cargo/egui relationship is appropriately unresolved but needs a guarded decision boundary.** **Severity:** warning. **Evidence:** Rust is confirmed, Cargo is an unverified agent-default, and the desktop framework is unknown in [`technical-context.md`](technical-context.md:52-63) and [`project-manifest.md`](../project-manifest.md:39-43). The container correctly leaves the framework unknown ([`scriptcraft-desktop.md`](containers/scriptcraft-desktop.md:22-26)), but the blueprints do not explicitly state the consequence that any eventual egui/eframe choice belongs only to the app/UI package. The analysis specifically warns not to put egui types in the engine ([`04-command-session-ui-boundary.md`](../../.analysis/stage2/04-command-session-ui-boundary.md:270-280)). **Suggested action:** retain framework selection as an explicit workspace-foundation decision and add a dependency acceptance check that the core compiles without egui/eframe/winit/rfd, while the app owns event translation, IME, rendering integration, dialogs, and platform services. **Required next state:** `draft` until the framework and dependency-layer check are recorded; this is not a blocker because the assumption is marked unknown rather than presented as fact.

- **BP-REVIEW-W-004 — Native persistence, filesystem I/O, session state, and recovery ownership need a sharper host/core split.** **Severity:** warning. **Evidence:** [`screenplay-core.md`](components/screenplay-core.md:45-57) gives `NativePersistence` serialization, migrations, atomic save, and recovery responsibilities; [`technical-context.md`](technical-context.md:31-37) places persistence beside the session boundary; but [`scriptcraft-desktop.md`](containers/scriptcraft-desktop.md:46-49) calls this a core-to-filesystem contract, and the feature blueprint says persistence handles the native source and recovery boundary ([`screenplay-writing-loop.md`](features/screenplay-writing-loop.md:20-27)). The analysis recommends persistence accepting abstract file operations while the host owns filesystem integration ([`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:761-765)). **Suggested action:** distinguish pure bytes/schema/migration and injected file-store operations from desktop path/dialog services; state that session owns caret, selection, undo, dirty, revision, and layout cache, while native project files exclude those transient values. Define recovery provenance, source identity, freshness, rotation bounds, and candidate-offer behavior before implementation. **Required next state:** `draft` until the ownership and recovery contract are made explicit; warning only because the blueprints already preserve the key no-silent-overwrite intent.

- **BP-REVIEW-W-005 — No-panic and hostile-input requirements are weaker in the blueprints than in the requirements and analysis.** **Severity:** warning. **Evidence:** [`screenplay-core.md`](components/screenplay-core.md:63-69) requires typed errors, rollback, deterministic layout, and an oversized-element escape hatch, while [`screenplay-writing-loop.md`](features/screenplay-writing-loop.md:78-83) maps requirements to components. The requirements additionally state typed/bounded error handling in [`screenplay-writing-loop.md`](../requirements/features/screenplay-writing-loop.md:82-86), and the analysis calls for `Result`-like APIs, bounded allocations, strict no-panic production lints, and a panic containment boundary ([`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:802-803), [`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:1043-1065)). The blueprints do not explicitly carry the production no-panic policy, hostile-input bounds, or the rule that panic containment is only a last-resort boundary. **Suggested action:** add these as implementation constraints in the next blueprint revision/work order: validate before mutation, bound JSON/text/layout/recovery inputs, preserve state on failed edits and I/O, prohibit panic-prone production shortcuts, and regression-test every discovered crash or data-loss defect. **Required next state:** `draft` until the safety contract is explicit; not a blocker because the requirements already supply the governing intent.

- **BP-REVIEW-W-006 — Deterministic layout depends on unresolved font and profile inputs.** **Severity:** warning. **Evidence:** [`technical-context.md`](technical-context.md:59-63) leaves font metrics and exact page values unknown, and [`technical-context.md`](technical-context.md:81-85) acknowledges cross-machine pagination risk. The component requires deterministic output for the same project/profile/font inputs ([`screenplay-core.md`](components/screenplay-core.md:63-68)), but the feature does not identify the acceptance decision for the supported font/profile combination. The analysis warns to pin or bundle an acceptable font/profile before promising exact output ([`06-screenplay-mvp-project-structure.md`](../../.analysis/06-screenplay-mvp-project-structure.md:831-847)). **Suggested action:** keep the fixed profile provisional, then record the supported font source, metrics, page dimensions, margins, and behavior for invalid/non-finite profile values before treating pagination/export as implementation-ready. **Required next state:** `draft`/`provisional`; no runtime determinism is claimed.

- **BP-REVIEW-W-007 — Export technology and loss-report behavior remain open at the blueprint layer.** **Severity:** warning. **Evidence:** [`technical-context.md`](technical-context.md:60-63) names PDF and lossy text as desired but leaves the exact library/contract unknown; [`scriptcraft-desktop.md`](containers/scriptcraft-desktop.md:30-33) lists PDF and text outputs; and [`screenplay-writing-loop.md`](features/screenplay-writing-loop.md:39-45) requires a deliberate loss report without defining its minimum structure. The independent requirements review also records this open decision at [`requirements-review.md`](../requirements/requirements-review.md:41-42). **Suggested action:** preserve the adapter boundary, but record the owner and decision gate for PDF implementation, print-layout inputs, export failure semantics, and the minimum plain-text loss status before the export work order. **Required next state:** `draft` pending decision ownership; no export library, command, or successful output is claimed.

- **BP-REVIEW-N-004 — Repository evidence is not overstated.** The reviewed documents consistently state that the application and reusable-code paths are empty or unverified and that `.analysis` is research/proposal input, not current source evidence ([`project-manifest.md`](../project-manifest.md:58-60), [`technical-context.md`](technical-context.md:11-15), and [`scriptcraft-desktop.md`](containers/scriptcraft-desktop.md:14-18)). ## Discrepancy handling

- The analysis describes a conceptual `core/` and `app/` layout and a future crate graph; the current blueprint baseline maps the repository's observed [`apps/scriptcraft/`](../../apps/scriptcraft/) and [`crates/`](../../crates/) directories without claiming that either contains source. This is recorded as a placement warning, not silently corrected.
- The analysis references an existing WordCraft-like Rust implementation and egui stack, while the manifest and technical context say those are not current checkout evidence. The blueprints therefore retain a native Rust desktop boundary but leave the framework and package commands unknown. No existing WordCraft or egui implementation is credited to ScriptCraft.
- The requirements review's unresolved role-transition, page-profile/font, export, and command concerns remain open dependencies. They are not reclassified as implementation defects, and this blueprint review does not rewrite requirements or blueprint documents.
