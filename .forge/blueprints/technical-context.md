## Final repository behavior map

This map describes the integrated repository after Phases 1–9; it supersedes transitional constructors, adapters, and dependency/test inventories described in earlier phase notes below.

- **Definitions and editing:** [`Project`](../../crates/scriptcraft-model/src/project.rs) owns an ordered registry of complete definitions keyed by exact, case-sensitive open type strings. Arbitrary body and typed Title Page Content types remain editable; type-less Title Page Content is valid. Only exact base labels derive the established structural capabilities. Return/Tab and generated controls resolve current definition [`Behavior`](../../crates/scriptcraft-model/src/element_definition.rs) and platform shortcut data; absent, unresolved, and semantically unchanged targets are consumed no-ops. Only Title Page `Content` paragraphs are semantically editable; other title structures remain opaque/preserved.
- **FDX and source ownership:** [`scriptcraft-fdx`](../../crates/scriptcraft-fdx/) manages arbitrary definitions, Behavior, body types, and typed/type-less Title Page Content, reconciles recognized source settings with the winning retained nodes, and preserves unrelated source. Ordinary import does not coerce unfamiliar types to Action or General. The first exact-label ElementSettings definition wins; later duplicates remain retained and inert. Required-base completion uses the packaged Screenplay definition source, while incomplete arbitrary definitions receive effective General-derived fields without General identity. Legacy document JSON codec/state/schema/recovery/detection and model Role/static formatting authorities are absent; the private version-1 command-envelope adapter is not document persistence.
- **Typography and layout:** Project owns effective DocumentPageLayout; session inputs are a derived read-only snapshot. Courier leading is 1.0×effective style size and Proportional is 1.2×size, selected by exact resolved face; DocumentLeading adds +0/+1/−1/−2 points, and the base style plus styles present on each wrapped visual line determine that line's maximum. SpaceBefore is exact whole-unit B/S times effective base leading. TopMargin anchors the first line-box top/imaginary preceding baseline, line-box bottoms are baselines, and bottom fit uses paper height minus BottomMargin. Natural font-table metrics are extent-only, with no ink-driven layout or line-box y clipping. Effective PageLayout defaults/fallbacks and preservation-free or absent-only detached source synthesis are documented in the FDX/requirements contracts. Canonical caches include effective page/resolver/style/space/per-line/font identity and require full equality after fingerprints. PDF receives coherent environment plus immutable font payload and embeds complete packaged Courier Prime bytes; eligible host embedding and host-only Base-14/scalar/color fallback are bounded and reported. macOS forwards the same payload snapshot, while plain text and Windows remain environment-only. Windows uses measured DirectWrite baseline only to cancel native row offset and retains canonical baseline/x; reports do not label that translation canonical-geometry uncertainty. Output success establishes no visual, pagination, coverage, or physical-delivery parity.
- **Templates and lifecycle:** [`builtin_templates.rs`](../../crates/scriptcraft-fdx/src/builtin_templates.rs) owns the single ordered compile-time catalog—Screenplay, Stageplay, Dramatists Guild Musical—and the common loader. Default New and landed New from Template retain the selected template's complete editable body/title content, use a fresh unsaved target, and have no writable template path or baseline. External FDXT opens as new untitled content through the shared staged-open disposition; ordinary FDX output removes only the direct-root unqualified Template marker, and neither built-in nor external FDXT can be overwritten through Save.
- **Apply and Elements:** Apply Template extracts only normalized target definitions/settings. It retains exact type-key matches and maps every unmatched managed body or typed-title key—including managed dual members—to target Action; type-less titles and opaque structures remain unchanged. One ordinary undoable edit preserves current text, runs, identities, direct formatting, attachments, unrelated settings/source, and dual source membership. Elements is a read-only registry-order inspector; the shared selector has the three catalog entries. Format → Elements and Apply use typed dispatch; File → New from Template is enabled and launches an independent child through the common loader. Selector cancellation does not load a target or create a candidate.

Model, FDX, Session, Commands, layout, export, and the desktop app have a zero-permanent-test and zero-test-only-fixture policy. WO-011.1 and WO-012.1 removed the app's permanent tests, helpers, module wiring, and test-only fixtures. Production contracts remain authoritative, and test absence is not validation evidence. The active prevention policy is in the [future-agent guidelines](../../.plan/2026-11-20-template-typography-pruning/future-agent-guidelines.md).

## Open element-definition contract

The Project owns exact, case-sensitive element-type keys and an ordered, bounded registry of complete definitions. Body paragraphs store their `ElementTypeKey` directly; title paragraphs store an optional key, with type-less titles remaining valid. The model has no Role projection; exact keys and the ordered registry are its only element-type authority. Definition order and values participate in equality, dirty state, undo/redo snapshots, validation, and save comparison. Every managed typed paragraph resolves to one definition. Stable paragraph IDs, runs, provenance, title formatting, and direct-formatting maps remain independent of type identity. Only exact Scene Heading, Character, Dialogue, Parenthetical, Transition, and Cast List labels derive their corresponding semantic capabilities; arbitrary labels and PaginateAs values do not imply guessed structure. Native FDX remains the durable format, with no legacy JSON migration or compatibility API. Phase ownership remains bounded: Phase 2 imports and completes definitions, Phase 3 reconciles their retained source projection, Phase 4 consumes Behavior for editing, Phase 5 consumes definitions for layout, Phase 6 owns command/control compatibility transitions and deferred shortcut-conflict diagnostics, and Phase 7 supplies templates. These future assignments do not claim implementation in Phase 1.

The Phase 2 required-base provider parses the Screenplay bytes owned by the Phase 7 compile-time catalog and returns independent owned clones of the nine required definitions for import completion only. It neither reads repository paths at runtime nor owns template lifecycle policy. Application new-document creation uses the full catalog's common-reader loader; the transitional nine-base constructor and model title/body seed were removed by WO-007.7. Stageplay, Musical, their content, and the full built-in template catalog were introduced in Phase 7.

## Phase 3 source-reconciliation contract boundary

Phase 3 makes the ordered Project registry the sole semantic authority for definitions and treats winning retained ElementSettings nodes as source projections: one optional winning anchor on import, exactly one after projection, with later exact duplicates unanchored and inert. It projects recognized definition values in registry order, preserves unrelated source and original input bytes, and removes an obsolete exact-label settings family if a retained duplicate could become a new winner after removal. Whole direct-root settings replacement is a distinct bounded primitive that leaves unrelated root children in order.

Managed Type changes use exact old/new keys and update semantic Type plus retained projection together. Body paragraphs require one unqualified Type; only TitlePage Content paragraphs are semantic titles, and those may have a Type or be type-less. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other title structures outside Content remain opaque/preserved-only and are not mapped. Namespaced/unknown attributes are not aliases. A generic session candidate accepts a complete ordered registry, separate explicit body/TitlePage Content mappings, and an optional ordered retained-settings replacement. It validates every managed current key and mapping target, then publishes definitions, body/title keys, provenance, source projection/indexes, and complete derived invalidation in one undoable revision/dirty update while preserving selections and other session state. Source-backed candidates reconcile winning settings in place unless the request supplies whole direct-root replacement nodes; preservation-free candidates reject that source-only input while ordinary definition replacement remains valid. Exact semantic no-ops and every failed validation/source operation leave history, redo, revision, token, dirty state, and the live project unchanged. The candidate contains no template extraction, Action fallback, or lifecycle policy; Phase 8 makes those choices outside the generic API.

Dual source membership is the ordered member identity list plus wrapper provenance. Active left/right sides are derived from current types, not stored as source membership. A type pattern that becomes inactive leaves a valid container and sequential body layout; it does not authorize unwrap. Save/reopen carries changed Type values by stable/foreign identity and preserves selections, content, definitions, and dual source ownership. These contracts do not add dynamic Behavior execution, scene/cast semantics, document-driven typography/layout, open commands/controls, template lifecycle/UI, or actual Apply Template policy. Phase 2 import-inspection coverage alone is not user-facing arbitrary open/edit/save readiness; only the grouped Phase 2–3 source, writer/reread, and save/reopen gate can establish that boundary. WO-003.1 updates these contracts only and records no test/check execution.

## Phase 4 dynamic-editing contract boundary

Phase 4 resolves ReturnKey and TabKey from each current definition by exact open key; absent and unresolved targets are safe consumed no-ops, and guidance shares the same pure decision as execution. ## Phase 5 typography and layout contract boundary

The current ordered definitions replace role-indexed layout settings and static role defaults as layout authority; stable-ID direct overrides overlay only their matching current definition. Typed Body and TitlePage Content values resolve by exact key. Type-less TitlePage Content uses an explicit neutral style from the layout environment, while direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other non-Content title structures remain opaque and outside semantic/layout resolution. Project also owns the effective DocumentPageLayout (paper width/height, TopMargin, BottomMargin, typed DocumentLeading, and optional retained HeaderMargin/FooterMargin); the session's PageLayoutInputs are a derived read-only snapshot. Absent PageLayout uses complete standard values. Field-local malformed input, duplicate PageLayout/PageSize, and unusable combined geometry use their documented fallback behavior; unsupported DocumentLeading remains Unsupported. Existing source nodes/original bytes remain unchanged; preservation-free output emits the effective node, while source-backed output synthesizes only when absent on a detached candidate. Apply Template remains settings-only and leaves PageLayout unchanged. No page-layout command is added; future mutation requires an additive typed command/patch and one atomic Project/source/session publication.

The resolved-font environment is explicit, transient, backend-neutral data: each declared family maps to four independently selected face styles; resolved face identities include deterministic byte/content identity; metrics include vertical data and a bounded scalar repertoire with advances/missing markers. Courier aliases map to bundled Courier Prime, nearest sans/serif choices are resolved by the desktop adapter, and unknown families or unavailable requested faces safely use the matching Courier Prime style. Host discovery, filesystem/byte loading, font registration, egui, and DirectWrite remain outside model/layout/export. Effective styles retain declared family and source color spelling. Color states remain distinct: absent means desktop theme default/output black, valid explicit RGB remains literal, unsupported explicit remains identifiable and uses a bounded reported fallback without rewriting source data.

The desktop host catalog has deterministic per-style order: Arial → Helvetica/Helvetica-like → Liberation Sans → Segoe UI for sans, and Times New Roman → Times → Liberation Serif → Georgia for serif. Every candidate is bounded-read and validated as an identifiable single-face font before selection; collections or unsupported containers, missing/oversized/malformed candidates, and invalid metrics advance independently per Regular/Bold/Italic/Bold Italic face. Preparation collects exact current definition families, direct run Font families, displayed canonical scalars, Unicode uppercase expansions, and the neutral Courier Prime request; its full request/scalar/catalog-generation signature controls reuse. The 16 MiB per-candidate and 64 MiB preparation byte limits, 64-family request limit, and 4,096-scalar repertoire limit fail the whole preparation rather than producing incomplete metrics. Exact bytes used for ab_glyph metrics are retained and registered under unique resolved-ID egui names; content collisions cannot silently share registration identity, while diagnostics/resolution metadata omit host paths and document text.

Canonical wrapping and composition sum resolved per-scalar advances and expose one canonical display-boundary mapping shared by paint, selection, caret, pointer, navigation, decorations, IME, PDF, and native print. Desktop rasterization cannot introduce natural-advance rewrap, repagination, realignment, or substitute glyph positions. Zoom, palette, selection, and native output settings stay outside canonical geometry/cache identity. Courier leading is 1.0×effective style size; Proportional leading is 1.2×size, selected by exact resolved face category. DocumentLeading contributes +0/+1/−1/−2 points to each candidate. After wrapping, the base style and styles actually present on each visual line determine that line's maximum; empty lines use base metrics. SpaceBefore is exact nonnegative whole-unit B/S times effective base leading and applies only at nonempty same-page boundaries. TopMargin is the first line-box top/imaginary preceding baseline; line-box bottoms are baselines and fit against paper height minus BottomMargin. Natural font-table ascent/descent and line gap are extent metadata only; ink never determines layout or clips to line boxes. PaginateAs enables keep-with-next only for exact Scene Heading, Character, and Parenthetical values; every other exact or arbitrary value disables it. PaginateAs never changes capabilities. StartsNewPage remains paragraph/direct-override data, and unsupported Leading/Spacing values gain no new numeric meaning.

The first line-box top is TopMargin, treated as the imaginary preceding baseline; every line-box bottom is its baseline, and ordinary fit compares baseline with paper height minus BottomMargin. Bounded oversized spill preserves forward progress without ink-based repagination or line-box y clipping. Complete/wrap/prepared caches include effective PageLayout/DocumentLeading, resolver category, exact face metadata/metrics/scalar maps, ordered definitions/direct values, base leading, SpaceBefore units/gap, styles/runs/text/context, purpose/composition/geometry mode, and retained per-line vertical output as applicable. Fingerprints select candidates only; complete equality authorizes reuse, and prepared-font ID collisions additionally require exact bytes, face index, and full face equality. Baseline is derived after placement/rebase. PDF uses one coherent resolved environment plus immutable face/byte payload and Print's canonical baselines/scalar boundaries. Packaged Courier Prime embeds complete unmodified OFL bytes; eligible host/synthetic faces embed under bounded licensing/format/metric/repertoire/budget rules; CID/GID and ToUnicode include non-BMP, missing embedded glyphs use GID 0. Base-14 and `?` are reported host-only fallbacks. macOS carries environment plus Arc-backed payload; plain text and Windows remain environment-only. Windows positions from canonical baseline/x, measuring DirectWrite baseline only to cancel native row offset and reporting family/face/shaping/coverage/missing-glyph/natural-extent/color observations, not canonical-geometry uncertainty. Output success claims neither exact visual parity, Final Draft pagination parity, universal glyph coverage, nor physical-printer delivery.

Phase 4–6 editing, layout, command, control, and shortcut contracts remain product authority; no permanent test suite or execution gate is retained. Any build, manual, native, visual/output, packaging, or interoperability evidence is user-selected and user-owned, with host observations distinct from source/build observations. Built-in catalog/lifecycle, Apply Template, and Elements UI remain Phase 7–9 scope.

Desktop Body and Title Page Content paint maps declared family and bold/italic flags through the prepared environment to resolved face identities. Canonical layout offsets drive glyph placement, selection, caret, pointer, vertical navigation, decorations, and IME anchoring; paint does not introduce independent wrapping or geometry. Unsupported glyph topology and explicit-color fallback use bounded value-free diagnostics. Managed Title Page Content uses the same definition/layout policy; non-Content title structures remain opaque. ## Phase 6 commands and document-driven controls target contract boundary

The Phase 6 target contract keeps command 22's stable ID and surface default while using an owned exact open element-type value. Target envelopes emit version 2 with `element_type`; version 1 is accepted only at the command-envelope boundary for the historical `role` field, mapping only the 17 known old spellings to their exact FDX labels. The conversion is not project membership, never falls back unknown labels to Action or General, and is unrelated to removed legacy document JSON. Missing, mixed, duplicate, unknown-field, version-inappropriate, or unsupported-version payloads fail before execution. IDs, descriptor identity/order, and all other command payload shapes remain unchanged. Envelope validation and direct execution each check target membership against the current ordered project registry. Body and typed/type-less Title Page commands use the generic exact-key session APIs; no-op and failed candidates leave session/source/history/selection/dirty/revision state unchanged. Origin is diagnostic metadata only.

Under the Phase 6 target contract, the ordered current registry is the single source for every toolbar/overflow choice, exact label, Behavior target, and raw platform shortcut. Generated choices preserve registry order, project the focused Body key without an invented fallback, and dispatch the same open-key command.
