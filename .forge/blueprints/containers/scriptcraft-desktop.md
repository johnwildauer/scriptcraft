# Container Blueprint: ScriptCraft Desktop

> ScriptCraft Desktop is the independently runnable local application boundary. This blueprint describes its established target composition; behavioral requirements remain in their linked requirements areas.

## Purpose and boundary

The desktop process composes the user workspace and host interactions around reusable, headless document capabilities. It owns application/window coordination and adapts user input and operating-system effects; it does not own screenplay semantics, editing transactions, FDX interpretation/emission, or canonical pagination. Model values, session editing and native storage, FDX codec work, layout, export, and command execution remain callable without opening a window.

## Runtime and delivery

- **Technology/runtime:** Rust desktop application using eframe/egui and target-specific native adapters.
- **Build/package:** Cargo workspace package [`apps/scriptcraft`](../../../apps/scriptcraft/); platform resources and packaging inputs are outside reusable document semantics.
- **Deployment/distribution:** Independently runnable local desktop process. Native dialogs, menus, clipboard, viewport operations, PDF/Print, and notifications are host integrations, not remote services.
- **Configuration:** Window/session presentation and interaction state is transient unless an explicit native document view-state contract applies. No credentials or service configuration are required.
- **Dependencies:** The app depends on all six headless libraries: [`scriptcraft-model`](../../../crates/scriptcraft-model/) for canonical dynamic definitions, content, and retained-source values; [`scriptcraft-fdx`](../../../crates/scriptcraft-fdx/) for the bounded FDX/FDXT reader/writer and compile-time built-in catalog; [`scriptcraft-session`](../../../crates/scriptcraft-session/) for editing/history, template Apply, and native storage; [`scriptcraft-layout`](../../../crates/scriptcraft-layout/) for canonical document-point composition from resolved document typography; [`scriptcraft-export`](../../../crates/scriptcraft-export/) for bounded plain-text/PDF encoders; and [`scriptcraft-commands`](../../../crates/scriptcraft-commands/) for stable typed commands and the headless executor. It also depends on the desktop GUI runtime, bundled presentation fonts, and narrowly scoped platform facilities. No reusable document behavior requires a window or a retired core package.

## Interfaces and composition

- **Inputs:** Keyboard, pointer, IME, toolbar/menu/status activations, typed commands, and native adapter results.
- **Outputs:** Body and title-page windows, transient desktop presentation, privacy-safe operation feedback, and explicitly requested noncanonical export or native print effects.
- **Internal areas:** [Document Model](../components/document-model.md) owns ordered open element definitions, semantic content, and retained source-preservation state; [Editing session](../components/editing-session.md) owns edits/history, settings-only Apply transactions, and native-storage transactions; [FDX preservation and storage](../components/fdx-preservation-and-storage.md) describes FDX/FDXT interpretation and the composition of FDX codec, model-owned source, and session-owned storage; [Layout and pagination](../components/layout-and-pagination.md) owns canonical geometry from resolved dynamic typography; [Command contract](../components/command-contract.md) owns typed activations and headless execution; [Exports and print](../features/exports-and-print.md) documents bounded output composition without adding an export component; and [Desktop adapters](../components/desktop-adapters.md) owns transient presentation and host effects.

- **Final app module map:** [`apps/scriptcraft/src/main.rs`](../../../apps/scriptcraft/src/main.rs) is the minimal process root. [`app/`](../../../apps/scriptcraft/src/app/) owns app state/construction, startup, root update, rendering/surface, diagnostics/responsiveness, and window lifecycle; [`commands/`](../../../apps/scriptcraft/src/commands/) owns availability, dispatch, and editing/navigation/clipboard/document/view/timer/Elements command families; [`documents/`](../../../apps/scriptcraft/src/documents/) owns lifecycle, open/import, save, replacement protocol/transport, PDF/Print, output, and unsaved-change coordination. [`chrome/`](../../../apps/scriptcraft/src/chrome/) owns menus/shortcuts, toolbar, status, theme, and focus presentation; [`presentation/`](../../../apps/scriptcraft/src/presentation/) owns shared fonts, geometry/style, wheel zoom, and runtime icons; [`views/script/`](../../../apps/scriptcraft/src/views/script/) and [`views/title_page/`](../../../apps/scriptcraft/src/views/title_page/) own the Script and title viewport adapters; [`widgets/elements/`](../../../apps/scriptcraft/src/widgets/elements/) owns transient Elements and template-selector presentation, and [`widgets/sprint_timer/`](../../../apps/scriptcraft/src/widgets/sprint_timer/) owns timer presentation; target-gated [`platform/macos/`](../../../apps/scriptcraft/src/platform/macos/) and [`platform/windows/`](../../../apps/scriptcraft/src/platform/windows/) own native adapters. These are modules of the one app package, not reusable UI or service layers.

```component
name: ScriptCraftDesktopComposition
container: ScriptCraft Desktop
responsibilities:
  - Own the runnable application, document session coordination, window/view lifetimes, and event loop.
  - Translate enabled user activations into typed commands and route them through one desktop dispatcher.
  - Compose presentation and native adapters without moving semantic rules into widgets.
```

## Contracts

- **Activation path:** Every enabled user-facing action—whether initiated by a menu, toolbar, editor input, status control, keyboard/pointer adapter, or native menu—is represented by a typed command and converges on the single dispatcher. The dispatcher rechecks current availability, delegates semantic editing to the headless executor, and coordinates narrowly scoped host effects. Framework painting, hover, layout measurement, and raw scrolling remain presentation bookkeeping.
- **Central editor scrollbar composition:** Root Body and Title Page editor content share a local save/apply/restore scrollbar wrapper in the central UI composition. The script-workspace theme owns distinct track and resting, hovered, and dragged handle colors. The background track is constant at 10 logical points; the sole visible app-painted handle is centered within it at 8 logical points, with 1-point side buffers at full visibility and rounded ends (maximum 4-point radius clamped to its actual geometry). The track and visible custom handle remain fully opaque in every pointer state, with directional direct-handle hover feedback and the owned dragged-handle presentation. The wrapper keeps stock background paint opaque and sets only the built-in stock handle shape's paint opacity to zero; that hidden shape is distinct from the fully opaque custom handle. Stock handle dragging scrolls its axis and track clicks outside the handle reposition the viewport. Editor text-selection hit regions yield only the 10-point right/bottom scrollbar strips required by current content overflow, preserving ordinary interaction elsewhere and modal element-window ownership. Visibility remains need-based and floating allocation is zero. Future central views inherit the policy at that boundary; unrelated egui scrollbars do not. This is desktop presentation/input ownership only and does not change canonical page geometry, viewport allocation, or command/document boundaries.
- **Transient dropdown geometry:** Elements popup sizing is derived from current choices and UI style on each render: normal and overflow presentations share desired inner row height and longest-current-label minimum width, while the main ComboBox outer-height cap includes popup margins. The closed toolbar geometry is unchanged and constrained scrolling remains available. In-window Windows top-level and nested menus derive width from their widest row and height from all entries, with vertical scrolling capped by the usable viewport. Popup dimensions are transient, not document/session state; native macOS menu ownership is unchanged.
- **Document ownership:** One application session backs Body and Title Page surfaces. Its ordered document-owned definitions are the authority for exact open body and typed-title keys; arbitrary defined types remain editable, and only exact base definitions supply their established structural capabilities. Surface focus and window lifetime are desktop-owned; canonical content, histories, resolved-font layout, and durable source remain in reusable components. Only TitlePage Content is editable/layout-managed; other title structures remain opaque.
- **Effective page and output ownership:** Project owns the complete effective DocumentPageLayout; the desktop consumes only its session-derived read-only layout-input snapshot and cannot install a competing page-setting authority. Canonical per-line leading/baseline and complete layout/cache identity remain in model/layout components. PDF/macOS PDF-backed Print receive a coherent prepared environment plus immutable face/byte payload; Windows and plain text remain environment-only. The desktop coordinates host preparation and snapshots but does not add output-side reflow, mutate PageLayout through Apply, or add a PageLayout command.
- **Typography-v3 output and print defaults:** The shared PDF composition uses the canonical baseline derived from line-box top plus retained natural ascent and DocumentLeading adjustment; standard Normal 12-point packaged Courier Prime derives 80.33 points and PDF y = 711.67 on US Letter from its resolved 1421/−643 metrics. Complete-face descriptor vertical metrics are independently normalized to 1000-unit PDF space without changing complete embedded font bytes. macOS Print uses the accepted snapshot's effective paper dimensions, zero additional application margins, 100% initial scaling, PDFKit no-fit scaling, and horizontal/vertical non-centering defaults before the panel; accepted native paper/orientation/scaling choices remain authoritative. Non-centered initialization does not claim that every host-specific translation or imageable-bounds effect is eliminated. This adapter policy adds no second page, margin, placement, or layout authority and uses no hardcoded PDF or macOS offset.
- **Root and child lifetime:** Root Close is guarded against unconfirmed dirty-session closure; File Close while Title Page is active closes only that child surface. Application Quit requests guarded root Close. Body and Title Page continue to use the same shared session, not separate documents or lifecycles. This guard does not imply that arbitrary forced process termination can be cancelled.
- **Default and template-backed document lifecycle:** A launch without a document and each independent File → New instance use the public default Screenplay built-in loader through the common FDX reader and retain its complete editable example body/title Content. The single compile-time catalog contains Screenplay, Stageplay, and Dramatists Guild Musical in order. File → New from Template uses the shared selector/catalog metadata and launches one independent child through the common loader; the selected template's complete body/title Content and settings are retained, while the parent session remains untouched. Built-in and external FDXT opening also use the common reader, but activation creates fresh unsaved content rather than a writable template document. Every template-backed instance receives a fresh session and Project layout identity, a presentation title of `Untitled ` plus the selected built-in catalog display name or, for external FDXT, the source filename stem with only its final extension removed (default Screenplay therefore remains `Untitled Screenplay`), and no native path or FDX storage conflict baseline. Fresh presentation identity is independent of writable path/baseline state; title synchronization uses the saved FDX filename after verified publication and the fresh template title otherwise. Initial semantic cleanliness is session bookkeeping, not a disk-save claim, so ordinary Save requires Save As to FDX; only verified publication installs the new path and baseline together. Activation prepares the replacement session and best-effort selection before publishing either the session or its persistence disposition; fresh-unsaved activation clears any prior path/baseline pair. Imported root WindowState/TextState is disposable view state and does not establish a baseline or semantic layout identity. The catalog is compile-time FDX data, not a runtime repository-relative resource. Apply Template is a separate settings-only edit to the current session, not a New/Open/replacement path.
- **In-app Open replacement lifetime:** File → New and New from Template remain independent-child creation paths, with New from Template instantiating its selected full-content template through the common loader and never entering replacement. In-app picker selection and direct-path Open use a selected-path dirty gate in the current parent, then at most one pending acknowledged child replacement record. While pending, the one shared session behind Body/Title Page is locked against document mutation; the parent remains open until the matching child reports Opened after installing its session. Only then does the parent reuse its one-shot guarded root-Close continuation. Migration pending/Cancel and all failures, child exits, channel errors, exit-poll errors, and timeout safely resume the parent session/title; timeout does not kill or wait for the child and late acknowledgements are inert. A successful Save before spawn is not rolled back, while Don’t Save never reverts or writes the source.
- **Windows shell process arguments and document lifetime:** Windows supplies shell-open paths as process arguments. The desktop entry point preserves argument-vector boundaries and accepts one positional native path as the sole shell document input, mutually exclusive with the custom internal document option. A positional request has no replacement handoff and occupies that process's one initial document slot; the first root update consumes it through existing staged opening. Each shell request starts an independent process with its own document and process lifetime. No existing-instance discovery/forwarding, singleton IPC, or cross-process broker is present in this route, and an existing process is not prompted, saved, mutated, acknowledged, closed, or terminated. Body and Title Page still share one session within each process. The portable Windows package does not register an association; Windows and the user own any deliberate Open With/default choice. Executable/shortcut drag compatibility is limited to a single positional path; taskbar/taskbar-hover and in-window drops are outside scope.
- **macOS Launch Services input and process lifetime:** Finder/Dock Open Documents events enter through one retained main-thread Open Documents Apple-event target registered immediately before eframe startup. A retained `NSApplicationWillFinishLaunchingNotification` observer re-registers the same target after AppKit setup and before Finder's launch document event; winit's application delegate is preserved and no `NSDocumentController` is used. Intake obtains an `NSURL` by applying `fileURLValue` to a bare descriptor or the sole item of a list, then validates that it is a local file URL and that its native path is valid. Each process has one initial document slot finalized at its first root update: absent a startup argument, the first valid request queued before that boundary uses the initial instance through ordinary staged opening; every later request launches its own independent child with an ordinary startup document argument. Separate single-file events remain independent and FIFO; one multi-file event is rejected atomically. There is no singleton, document broker, or `NSDocument` ownership. OS opens never use the in-app dirty gate, acknowledgement, replacement lock, receiver mutation, Close, or termination; the receiver's document/path/baseline/title/selection/dirty state and source bytes remain unchanged. Intake/spawn failure is visible in the receiver, cold open failure leaves the initial instance untitled, and child content-open failure is owned by the child. Extension-fallback metadata indicates Finder eligibility only; Finder Open With visibility, user-selected default-handler state, Dock-drop eligibility, and content validation are distinct and are not established by that metadata. This contract does not assert Windows shell or in-window drop behavior.
- **Host boundary:** Native paths, dialogs, clipboard access, window operations, system font availability, print submission, and notifications stay in desktop/platform adapters. All six reusable libraries remain independent of GUI widgets and native handles; the desktop app adapts those host effects around their respective model, FDX, session, layout, export, and command boundaries.
- **Failure and privacy:** Adapter outcomes distinguish routing from external success. User-facing diagnostics are bounded and do not expose screenplay/source payloads or unnecessary paths; semantic and storage failures retain their owning component's safe-stop behavior.
- **FDXT source protection and ordinary FDX output:** The Open picker admits FDX and FDXT. All staged paths use one ASCII case-insensitive filename-extension disposition for `.fdxt`; a root `Template` attribute alone never makes a document open-as-new, and other extensions retain content-based opening. The staged disposition survives migration Continue/Cancel. Fresh-unsaved activation discards the temporary FDXT read baseline and installs neither source path nor baseline; ordinary Save defensively refuses an FDXT source path, while Save As accepts only FDX. No OS or in-app route may install an FDXT path or read baseline as the writable target. Ordinary FDX output removes direct-root unqualified `Template` attributes only from the detached output projection, without adding `Template=No` or mutating original/live template bytes, namespaced lookalikes, descendants, attribute order among survivors, or unrelated root values.
- **Settings-only Apply and source preservation:** Apply loads one selected built-in through the common catalog/reader, extracts only normalized target definitions and their ElementSettings source, preserves exact current key matches, and maps every unmatched managed body or typed-title key (including managed dual members) to target Action. Type-less title Content and opaque structures do not change. Current content, stable/foreign identities, order, direct formatting, attachments, opaque source, dual source membership, and every unrelated current setting survive. One ordinary undoable session edit publishes the registry/type/source projection together; inactive dual groups remain source-preserved and lay out sequentially with each member once. Apply changes no path/baseline and never opens a picker, replaces a session, or writes a template source.
- **PageLayout persistence boundary:** Effective PageLayout is Project-owned durable document state. Absent source installs the complete standard default; malformed fields and unusable combined geometry use field-local/combined fallbacks; unsupported DocumentLeading stays Unsupported. Ordinary source-backed output preserves existing PageLayout nodes and original bytes and synthesizes one only when absent on a detached candidate; preservation-free output emits effective values and reread verifies them. Apply Template leaves the current effective and retained PageLayout untouched. Changing PageLayout would require a separately specified additive typed command/patch and atomic session/FDX publication; this initiative adds neither.
- **Legacy persistence boundary:** Native FDX is the durable document format. No legacy JSON codec, state, schema, migration, recovery, writer, or special detection path exists; unsupported JSON receives ordinary bounded unsupported-input handling. The private version-1 adapter for historical command-22 role spellings is command-wire compatibility only and does not restore a document Role model or JSON persistence.
- **Platform delivery:** Platform packaging is an adapter/distribution concern, described by [macOS packaging](../features/macos-packaging.md). The application runtime does not require Cargo or repository-relative resource paths.

## Decisions

- Keep the desktop independently runnable while keeping semantic editing, FDX, and fixed geometry headless and reusable.
- Use one typed activation boundary; place platform-specific effects behind desktop adapters rather than in document components.
