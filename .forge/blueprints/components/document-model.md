# Component Blueprint: Document Model

> The canonical document-model capability owns ScriptCraft's project and screenplay values, including the retained source state required to preserve an opened document.

## Capability

The `scriptcraft-model` package defines the canonical project value shared by document-format and application-service packages. It owns the ordered screenplay Body and its open, exact element-type keys; a bounded ordered registry of document-owned element definitions; owned font, paragraph, Behavior, and Outline values; the separate ordered Title Page paragraph model with optional element types; dual-dialogue semantics; stable model identities and source provenance; scene and cast metadata; validated layout inputs; and retained source-preservation state. It has no legacy JSON adapter. This is the canonical model package, not a legacy package or an alternate to a former core model.

The capability's source organization is rooted at [`scriptcraft-model`](../../../crates/scriptcraft-model/) and its deliberate module/re-export boundary in [`src/lib.rs`](../../../crates/scriptcraft-model/src/lib.rs). Its manifest has no internal ScriptCraft dependency; the approved package graph and downstream edges are summarized in the [technical context](../technical-context.md).

## Development policy

During the active development phase, `scriptcraft-model` maintains zero permanent Rust tests and no permanent test-only fixture directories. This source-development policy does not alter canonical model values, production behavior, public APIs, or any product contract defined below. Test removal is not evidence that a contract has been validated; validation and acceptance remain user-owned. Follow the [zero-permanent-test prevention guidelines](../../../.plan/2026-11-20-template-typography-pruning/future-agent-guidelines.md).

## Composition

```component
name: DocumentModel
container: ScriptCraft Desktop
responsibilities:
  - Own canonical project, ordered Body, and separate Title Page values.
  - Define open element-type keys, ordered document definitions, owned settings, text runs, formatting, layout inputs, and stable identities.
  - Define dual-dialogue semantics and derived scene/cast model values.
  - Retain source-preservation values and validate model inputs.
  - Validate definition order, exact-key uniqueness, typed paragraph references, and complete project values.
```

- [`project.rs`](../../../crates/scriptcraft-model/src/project.rs) composes Body owners, Title Page paragraphs, the ordered document definition registry, dual-dialogue groups, direct-formatting maps, and retained preservation state. [`element.rs`](../../../crates/scriptcraft-model/src/element.rs) stores each body's canonical open key directly, while [`title_page.rs`](../../../crates/scriptcraft-model/src/title_page.rs) stores an optional canonical key; neither stores a parallel Role value or exposes a Role adapter. Open element types are canonical and are not generated from Rust role variants. The model exposes an empty import projection and validated whole-registry replacement, not an application new-document constructor or fixed title/body seed; application-created documents come through the FDX built-in catalog's common reader.
- [`element_semantics.rs`](../../../crates/scriptcraft-model/src/element_semantics.rs) defines the borrowed [`ElementSemantics`](../../../crates/scriptcraft-model/src/element_semantics.rs) view and [`ParagraphBehaviorKey`](../../../crates/scriptcraft-model/src/element_semantics.rs)/[`BehaviorTargetResolution`](../../../crates/scriptcraft-model/src/element_semantics.rs) projection. [`Project.element_semantics()`](../../../crates/scriptcraft-model/src/project.rs) and [`Project.resolve_paragraph_behavior_target()`](../../../crates/scriptcraft-model/src/project.rs) resolve against the current exact-key registry without storing parallel capability flags or fallback semantics.
- [`element_type.rs`](../../../crates/scriptcraft-model/src/element_type.rs) defines only the bounded, owned exact-label key; no Role conversions or parsers exist in the model. [`element_definition.rs`](../../../crates/scriptcraft-model/src/element_definition.rs) defines complete owned font, paragraph, Behavior, and Outline values, including validation bounds and representable unresolved Behavior targets, plus [`SemanticCapabilities`](../../../crates/scriptcraft-model/src/element_definition.rs), derived only from exact `Scene Heading`, `Character`, `Dialogue`, `Parenthetical`, `Transition`, and `Cast List` keys. These canonical complete values are distinct from the optional, partial source projections [`SourceFontSpec`](../../../crates/scriptcraft-model/src/formatting.rs) and [`SourceParagraphSpec`](../../../crates/scriptcraft-model/src/formatting.rs). [`formatting.rs`](../../../crates/scriptcraft-model/src/formatting.rs), [`formatted_text/runs.rs`](../../../crates/scriptcraft-model/src/formatted_text/runs.rs), [`formatted_text/paragraphs.rs`](../../../crates/scriptcraft-model/src/formatted_text/paragraphs.rs), and [`formatted_text/alignment.rs`](../../../crates/scriptcraft-model/src/formatted_text/alignment.rs) define shared formatting values and formatted-text operations. [`layout_inputs.rs`](../../../crates/scriptcraft-model/src/layout_inputs.rs) contains model-owned layout-input values; pagination and layout computation are separate capabilities.
- [`typography.rs`](../../../crates/scriptcraft-model/src/typography.rs) defines transient resolved-font identities, four-face request mappings, bounded per-scalar and vertical metrics, deterministic metric scaling, effective color state, and the canonical backend-neutral [`EffectiveTextStyle`](../../../crates/scriptcraft-model/src/typography.rs). It stores no font bytes or host paths and does not discover or register faces. [`layout_inputs.rs`](../../../crates/scriptcraft-model/src/layout_inputs.rs) exposes `PageLayoutInputs` as the page-geometry input; fixed-cell characters-per-line, lines-per-page, line-advance, font-family, and character-width inputs are retired. [`position.rs`](../../../crates/scriptcraft-model/src/position.rs), [`identity.rs`](../../../crates/scriptcraft-model/src/identity.rs), and [`paragraph_id.rs`](../../../crates/scriptcraft-model/src/paragraph_id.rs) define position/selection primitives and model/source identity values. [`title_page.rs`](../../../crates/scriptcraft-model/src/title_page.rs), [`dual_dialogue.rs`](../../../crates/scriptcraft-model/src/dual_dialogue.rs), [`scene_metadata.rs`](../../../crates/scriptcraft-model/src/scene_metadata.rs), and [`cast_list.rs`](../../../crates/scriptcraft-model/src/cast_list.rs) own the corresponding semantic values and derivations.
- [`validation.rs`](../../../crates/scriptcraft-model/src/validation.rs) owns project, ordered-definition, typed-paragraph-reference, and layout-input validation. [`preservation/`](../../../crates/scriptcraft-model/src/preservation/) owns retained source values, preservation validation, and model-side reconciliation.
- FDX consumes the model to interpret and emit its retained source representation. Session consumes the model for editing and native-session composition. Layout, export, commands, and the desktop app depend on the model through the approved acyclic package graph; the exact package edges remain in the [technical context](../technical-context.md).

## Contracts

- **Canonical values and text:** Body is an ordered sequence of elements with exact open element-type keys, exact canonical UTF-8 text, and, when present, ordered runs whose concatenated text projects to that canonical text. The Project owns an ordered `DocumentElementDefinitions` collection; each definition owns its font, paragraph, Behavior, and Outline values. Title Page is a separate ordered paragraph model; a title paragraph may carry an exact element-type key or be type-less. Exact labels are case-sensitive and are not trimmed, normalized, converted to generated Rust variants, or mapped to a fallback type. Definition order and all complete definition values participate in project equality, dirty comparison, undo/redo snapshots, validation, and save comparison. Stable paragraph IDs, provenance, title formatting, and direct-formatting maps remain independent of element type. `SemanticCapabilities` derives six independent flags—scene boundary, character cue, dialogue, parenthetical, transition, and Cast List—from only the exact labels Scene Heading, Character, Dialogue, Parenthetical, Transition, and Cast List, respectively. General, Shot, New Act, End of Act, arbitrary labels, case variants, and `PaginateAs` values acquire no guessed structural semantics. Text, whitespace, and imported spelling remain model values rather than presentation-time normalization.
- **Reader definition population:** The common FDX reader assembles complete ordered definitions from first-wins source settings, missing managed-target paragraph keys in first-use order, and missing packaged required bases in the prescribed nine-label order. Effective General begins from packaged Screenplay General and overlays recognized source General fields. Incomplete arbitrary definitions overlay that effective General value field-by-field and restore their own exact key; exact base labels used without winning settings receive their packaged values. Behavior targets are resolved only after the complete registry is assembled and unresolved keys remain open values. No role-indexed formatting table or static model registry participates in import or runtime layout.
- **Template catalog boundary:** The built-in template set is exactly three catalog identities—`screenplay`, `stageplay`, and `dramatists-guild-musical`—with stable presentation metadata and Screenplay as the default. This closed set identifies available built-in resources only; it does not constrain the open document element-type vocabulary or arbitrary editable definitions. Catalog instantiation uses the common bounded FDX reader and retains the selected document's complete supported body/title content and other document settings. Only TitlePage Content paragraphs enter the semantic title model; direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other non-Content title structures remain opaque and preserved-only.
- **Positions and identities:** Position offsets address UTF-8 byte boundaries on their respective text surfaces; model helpers reject a non-character boundary. Stable model IDs identify canonical owners, while imported source provenance and foreign identities remain distinct source-owned values. [`position.rs`](../../../crates/scriptcraft-model/src/position.rs), [`identity.rs`](../../../crates/scriptcraft-model/src/identity.rs), [`element.rs`](../../../crates/scriptcraft-model/src/element.rs), and [`preservation/identity.rs`](../../../crates/scriptcraft-model/src/preservation/identity.rs) define these primitives. The editing session owns live caret/selection state and its operations; see [Editing Session](editing-session.md).
- **Validation and composition:** Project validation covers canonical Body and Title Page values, exact typed-key resolution against the unique ordered registry (missing definitions fail with a focused model error; type-less title paragraphs are exempt), identities, dual-dialogue relationships, formatting overrides, and preservation coherence. The vector-backed registry remains ordered and encapsulated; lookup is exact and case-sensitive. Definition changes are semantic Project changes and therefore participate in equality, dirty state, snapshots, undo/redo, and full validation. Layout-input values have a model validation API. Body owners are shared as immutable values at the Project composition boundary; a semantic owner change uses copy-on-write rather than mutating a shared owner in place. [`project.rs`](../../../crates/scriptcraft-model/src/project.rs), [`element.rs`](../../../crates/scriptcraft-model/src/element.rs), and [`validation.rs`](../../../crates/scriptcraft-model/src/validation.rs) define the model boundary. Session transaction, snapshot, and publication behavior remains owned by [Editing Session](editing-session.md).
- **Retained source state:** Preservation is part of the open Project value and semantic equality, not an FDX-owned sidecar. Its source snapshot, retained sections, identity/reference relationships, and board graph remain model values; ephemeral preservation indexes are excluded from preservation equality. Editing snapshots and successful-save rebase retain their established source-state behavior under the session and FDX contracts. FDX interprets and emits the representation but does not own the retained model state; see [FDX Preservation and Storage](fdx-preservation-and-storage.md) for detailed codec, save, and storage contracts.
- **Definition/source projection:** The ordered Project registry is the sole mutable authority for complete font, paragraph, Behavior, and Outline values. A source-backed definition has at most one winning source anchor after import and exactly one after successful source projection; each anchor targets an exact ElementTypeKey, while later exact-label duplicate ElementSettings nodes remain retained but unanchored and semantically inert. Definition-node lookup is derived from those anchors, never maintained in a second mutable settings model. Recognized values are projected from the registry into the winning node; duplicate recognized source children fail without partial mutation, and unknown source payload remains retained. Missing winners are materialized in registry order. Exact old-key/new-key Type changes preserve owner identity and other canonical/source fields; a managed body paragraph requires one unique unqualified Type, while only TitlePage Content paragraphs are managed titles and may be typed or type-less. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and other out-of-Content title structures stay opaque and are not mapped. Foreign-namespace attributes are not Type aliases. Source-backed definition remapping and whole direct-root settings replacement are detached candidate operations; source bytes are immutable, unrelated root children remain in order, and removal of a definition removes its complete exact-label settings family so a duplicate cannot become a new winner on reread. See [FDX Preservation and Storage](fdx-preservation-and-storage.md).
- **Dual source membership and projection:** A source-preserved dual container owns an ordered list of member IDs plus wrapper provenance. Left/right sides are derived from that existing ordered membership only when the current definitions grant exactly two Character-cue members, with only Dialogue- or Parenthetical-capability members after each cue; either side may be empty. The sides are derived values, never a second stored membership authority, and adjacent paragraphs outside the container do not become active dual members through label or role-pattern inference. Arbitrary/case-variant keys and `PaginateAs` never grant dual capabilities. If a type change makes the pattern inactive, the group remains valid Project/source state and its ordered members remain in sequential layout; Type-only changes and definition remaps do not unwrap or delete it. Explicit disable is the operation that unwraps an inactive source container.
- **Definition-remap candidate boundary:** A generic session candidate replaces the complete ordered registry and applies explicit body and TitlePage Content key mappings as one detached transaction. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other title structures outside Content remain opaque and are excluded. Successful publication creates one history entry and revision increment, recomputes dirty state, and invalidates affected derived state; a semantic no-op creates neither history nor revision, and any validation/source failure publishes nothing. Stable IDs, text/runs, direct formatting, attachments, opaque source, selections, and dual source ownership remain coherent. The generic mechanism contains no template extraction, selection, lifecycle behavior, or unmatched-to-Action fallback; only the later Apply Template phase may choose that policy and pass explicit mappings.
- **Apply Template semantic boundary:** The Project's ordered definitions remain the complete semantic authority after Apply; the model does not own a template catalog, selection, loader, or fallback policy. Apply's exact-key retention and unmatched-to-target-Action mappings affect only managed Body and typed TitlePage Content keys. Type-less titles and opaque/non-Content title structures do not acquire keys, and no Type-looking descendant under opaque ancestry becomes managed. Canonical text/runs/order, stable identities, direct formatting, attachments, dual source membership, and non-definition Project values remain those of the current document. The session owns one candidate that combines definitions and Type changes; this model contract does not add content correction, document replacement, storage target, or baseline semantics.
- **Durable and transient state:** Canonical Body/Title values, model identities, formatting inputs, and retained source state belong to the Project value. Caret and selection values may use the model's `Position`/`Selection` primitives, but active selections, editing history, dirty/revision tokens, disposable layout caches, desktop zoom or mode, native handles, and timer state are not canonical screenplay content. The bounded root FDX view-state projection has its own explicit native contract; refer to [FDX Preservation and Storage](fdx-preservation-and-storage.md) rather than treating all view state as model content.
- **Dependency and exclusion boundary:** `scriptcraft-model` depends on no other ScriptCraft package. It owns no XML parser or writer, filesystem access or publication, editing history, pagination or layout caches, PDF/plain-text emission, command wire types, `egui` types, native dialogs, or desktop state. Native storage and filesystem adapters remain in session; the package graph is six libraries plus the `scriptcraft` desktop app, with no `scriptcraft-core` or separate UI package. See the [technical context](../technical-context.md) for approved package ownership and edges.
- **Legacy JSON exclusion:** The unused pre-production JSON codec, envelope, schema API, project state, and recovery compatibility surface are absent. No JSON migration or replacement compatibility API exists; native FDX remains the durable project format.

- **Managed Type projection primitive:** Source-backed body and dual-member Type changes use exact expected/replacement `ElementTypeKey` values, verify managed ownership and the retained type summary, and mutate only one unique unqualified `Type` plus its retained summary. Managed title Type changes use optional exact keys, require the current semantic key and title source provenance/identity to match, and support typed-to-typed, typed-to-type-less, and type-less-to-typed transitions. Duplicate and namespace-qualified `Type` lookalikes fail before retained mutation; adding a Type inserts it deterministically before a paragraph ID. Direct and nested newly constructed body paragraphs use the canonical key rather than a closed Role label, and preservation-free title output emits the exact optional key. Text/runs, IDs, provenance outside the Type projection, direct formatting, attachments, opaque descendants, namespace bindings, and unrelated attributes remain unchanged. Session publication and source provenance updates remain owned by the detached editing candidate.

- **Dynamic semantic projection and Behavior:** `SemanticCapabilities` are derived solely from the exact current key: Scene Heading, Character, Dialogue, Parenthetical, Transition, and Cast List receive only their corresponding built-in capabilities. Arbitrary labels and case variants receive no guessed semantics. Scene ranges, Character-name projections, Cast List correction, and preservation-free SceneProperties generation use the current Project definitions and those exact capabilities; `PaginateAs` is never structural identity. SceneProperties are inspected or reconciled only while their owner currently has scene-boundary capability, so a Type-only capability removal leaves the attachment opaque and unchanged until a later ordinary refresh after the exact capability is restored. Character normalization and Cast List safe-stop, sorting, and no-synthesis behavior remain unchanged. Behavior ReturnKey/TabKey values are document data, resolved only by exact lookup in this same ordered registry; absent and unresolved targets remain distinguishable and neither manufactures a fallback. A same-key target is preserved as data, not treated as a new semantic identity. `PaginateAs` may guide layout only and is never consulted for structural capability. These are read-only projections of the current Project, not stored flags or an additional registry. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other title structures outside Content remain opaque and outside semantic projection.
- **Shared semantic view handoff:** `Project.element_semantics()` borrows the exact current definition, its complete owned values (including raw Shortcut/WinShortcut), and capabilities derived only from its key. `Project.resolve_paragraph_behavior_target()` distinguishes an unknown source definition (no result), an absent target, an unresolved owned target key, and an exact resolved owned target key, including same-key resolution. Editing, scene/cast, dual, layout, and later controls consume these projections rather than reconstructing closed-role semantics; Phase 5 consumes the same definition/capability view, while Phase 6 owns shortcut parsing, conflicts, and bindings.

- **Structural semantic boundaries:** A split retains its paragraph's exact key, and join compatibility is exact key equality rather than capability equality. Generic Type replacement and definition remapping alter Type only, preserving text/runs, stable and foreign IDs, direct formatting, attachments, and opaque source. Parenthetical generation is a high-level editing transition/assignment behavior only; it is not a side effect of generic Type mutation or definition remapping. Dual source membership remains the ordered members plus wrapper provenance; active sides are derived from capabilities, while inactive containers remain valid source/model state.
- **Transient typography boundary:** Declared family, size, style, paragraph values, and source color spelling remain document-owned definition/direct-formatting data; resolved host faces, byte/content identity, measured vertical/scalar metrics, and effective color resolution are transient layout inputs, not Project, FDX, dirty-state, history, or source-preservation values. Backend-neutral consumers receive explicit resolved identities and metrics and have no host-font discovery or platform API dependency. Direct values overlay only their matching current definition. A type-less TitlePage Content paragraph receives a neutral presentation from its explicit layout environment; direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all title structures outside Content remain opaque/preserved-only and are never promoted into managed typography inputs.
- **Effective document PageLayout:** `Project` owns a validated `DocumentPageLayout` containing paper dimensions, TopMargin, BottomMargin, typed `DocumentLeading`, and optional retained HeaderMargin/FooterMargin values. It has a complete standard default and conversion/equality/validation boundary; common FDX import installs the projection and template instantiation retains its selected values. `Project::session_layout_inputs()` derives the read-only layout snapshot consumed by session/layout; callers cannot install a competing session-only page authority. Effective values participate in Project equality, dirty/history/save comparisons. Retained XML spelling and original input bytes remain preservation evidence, not a second semantic authority. Only a future additive typed command/patch and one atomic session/FDX candidate may mutate an existing effective value; this initiative adds no command or mutation API.
- **Resolved typography values:** [`typography.rs`](../../../crates/scriptcraft-model/src/typography.rs) bounds opaque face IDs, family/face labels, byte lengths, request counts, face counts, scalar repertoires, font-unit values, and supported point sizes. Each declared-family request maps exact case-sensitive family text to independent Regular, Bold, Italic, and Bold Italic IDs; the explicit neutral Courier Prime request is part of the environment. A face carries source-kind classification, deterministic content fingerprint, units-per-em, vertical metrics, and explicit per-scalar advances including missing-glyph markers. Scaling to hundredths of a point uses integer arithmetic and one half-up final rounding step. Environment equality includes the complete mappings, face identities, and metrics, while its stable content fingerprint is only an identity summary and is not a substitute for full equality. Effective color distinguishes absent/theme-default, valid 12-hex-digit RGB source values (most-significant byte per channel), and unsupported explicit spellings; the source spelling remains available for diagnostics/cache identity and is never rewritten by presentation. Model typography values are host-independent and transient; host discovery, byte retention, and renderer registration remain desktop responsibilities. `scriptcraft_model::typography::EffectiveTextStyle` is the sole effective-style representation; the former `formatting::EffectiveTextStyle` compatibility type and projection/conversion shims are retired.
- **Vertical resolver identity:** Transient typography includes typed `DocumentLeading` and a `LeadingResolverKind` on each exact resolved face, alongside full face metadata, metrics, and scalar maps. The exact resolved face—not the declared family spelling—selects Courier (1.0 × effective style size) or Proportional (1.2 × effective style size). Natural ascent/descent and face line-gap metadata remain extent information and do not define leading. These transient values participate in the complete layout environment identity but do not become retained document font bytes or Project font-resolution state.
- **Transient decoration metrics:** Each resolved face also carries required underline position/thickness from `post` and strikethrough position/thickness from `OS/2`. Position identifies the stroke top relative to the font baseline; positive thickness extends downward. Metrics use bounded validation and checked deterministic fixed-point scaling and remain transient rather than Project/FDX data. Both kinds participate in complete environment equality/fingerprints; desktop face identity and exact PDF-payload coherence include the same raw values. Missing/invalid host metrics reject that candidate through existing per-style fallback, while a bundled Courier Prime defect fails preparation without a synthetic position.

- **Open command and compatibility boundary:** Command ID 22's version-2 `element_type` value is an exact open key; project membership is resolved only against the current ordered Project registry. The sole closed old-role mapping is the bounded, private version-1 command-envelope adapter from historical spellings to exact FDX labels; this is command-wire compatibility, not document JSON or a model registry. The model Role enum, static formatting/default table, conversions/facades, and session `change_role` adapter are absent. Legacy JSON codec/state/schema/recovery/detection is removed with no migration or compatibility API; native FDX remains durable.
- **Template-backed creation:** Startup, File New, and the landed independent-child New from Template path use the single built-in catalog/common loader and retain complete editable example Body and TitlePage Content. Each new session has fresh semantic/layout identity, no template path or saved baseline, and Save As behavior. The private nine-base Screenplay provider remains required-base completion for import only; generic model projection/replacement and preservation-free FDX serialization operate on explicitly supplied values, not as application constructors. TitlePage Content paragraphs alone are semantic/editable titles; every other title structure remains opaque. No runtime repository-relative resource lookup or Save as Template API exists.

## Decisions

- **Keep retained preservation state in the model.** Source state is part of the open document value and must participate with canonical semantics in equality, editing snapshots, undo/redo, and successful save rebase. Keeping it in the model lets FDX depend on the model without creating a model-to-FDX cycle; FDX remains the interpreter/emitter, not the owner. This is a deliberate ownership boundary, not a claim that every preservation helper is format-independent.
- **Keep native storage in session.** Native storage prepares and publishes session candidates and rebases the live session only after successful publication. Keeping that composition, filesystem access, and native storage outside model preserves the session transaction boundary and avoids giving the model filesystem or codec ownership. No additional core, UI, or storage package is introduced.
