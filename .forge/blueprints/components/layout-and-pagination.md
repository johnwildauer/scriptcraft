# Component Blueprint: Layout and Pagination

> This component derives deterministic, backend-neutral page structure and document-point geometry from semantic content and effective layout inputs.

## Capability

Layout maps canonical body and editable title-page Content positions to deterministic page geometry for editing, Print composition, and export. It resolves the current document's exact open type definitions, direct values, and explicit resolved-font metrics; it owns per-scalar wrapping, page placement, source/display maps, and immutable-layout query indexes. Desktop zoom and glyph rasterization project this geometry but do not alter it. Title structures outside Content remain opaque and outside typography/layout resolution.

## Composition

```component
name: LayoutAndPagination
container: ScriptCraft Desktop
responsibilities:
  - Resolve current-definition and direct paragraph geometry into document-point layout.
  - Produce deterministic body, title-page, and Print compositions with canonical source mappings.
  - Own bounded prepared-Body and wrap caches plus indexes derived from immutable complete layouts.
```

- The public layout surface is rooted at [`scriptcraft-layout/src/lib.rs`](../../../crates/scriptcraft-layout/src/lib.rs). [`geometry.rs`](../../../crates/scriptcraft-layout/src/geometry.rs) owns layout result geometry, [`inputs.rs`](../../../crates/scriptcraft-layout/src/inputs.rs) resolves effective paragraph and text-style inputs, [`wrap.rs`](../../../crates/scriptcraft-layout/src/wrap.rs) owns measured per-scalar wrapping, source/display remapping, and atomic expansion-boundary helpers, and [`spans.rs`](../../../crates/scriptcraft-layout/src/spans.rs) builds positioned styled spans.
- [`paginate.rs`](../../../crates/scriptcraft-layout/src/paginate.rs) composes page placement, [`title_page.rs`](../../../crates/scriptcraft-layout/src/title_page.rs) composes title-page lines, [`dual_dialogue.rs`](../../../crates/scriptcraft-layout/src/dual_dialogue.rs) composes dual-dialogue blocks, and [`interaction.rs`](../../../crates/scriptcraft-layout/src/interaction.rs) owns source-mapped geometry queries. [`cache/mod.rs`](../../../crates/scriptcraft-layout/src/cache/mod.rs), [`cache/wrap.rs`](../../../crates/scriptcraft-layout/src/cache/wrap.rs), and [`cache/prepared.rs`](../../../crates/scriptcraft-layout/src/cache/prepared.rs) own the disposable cache entry points, wrap entries, and prepared-Body entries.
- Canonical formatting and page-layout values come from [`Document Model`](document-model.md), including [`formatting.rs`](../../../crates/scriptcraft-model/src/formatting.rs), [`layout_inputs.rs`](../../../crates/scriptcraft-model/src/layout_inputs.rs), and `scriptcraft_model::typography::EffectiveTextStyle`. Every layout build and cache lookup uses an explicit `LayoutEnvironment` containing page inputs and prepared resolved-font identities/metrics; no environment-free or fixed-cell typography authority remains. FDX interprets and emits retained source through [`FDX preservation and storage`](fdx-preservation-and-storage.md); layout consumes current Project values and session-validated inputs, including the session-aware cache path. Layout does not call export and has no XML, native-filesystem, `egui` painting, PDF-emission, or plain-text-emission ownership. [`Desktop adapters`](desktop-adapters.md) projects canonical positions to viewport pixels without changing document-point geometry.

## Contracts

- **Open element types and settings ownership:** Paragraphs carry exact open element-type keys. Effective layout values resolve from the exact current ordered definition, then only the direct override keyed to the same stable paragraph/wrapper identity. A missing exact definition is an invalid layout input; there is no Role projection, General/Action conversion, static formatting row, or guessed fallback. Typed TitlePage Content paragraphs use their exact definition; type-less Content paragraphs use the explicit neutral title style in [`LayoutEnvironment`](../../../crates/scriptcraft-layout/src/inputs.rs). Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and every other title structure outside Content remain opaque and outside typography/layout resolution. Active dual wrappers use only the current exact General definition plus matching wrapper direct overrides for outer extent. PaginateAs is read from the current definition solely as pagination policy and never supplies capabilities. The complete resolved definition/style inputs belong to the transient layout environment and must participate in later cache identity.
- **Imported text color boundary:** Phase 2 import removes only exact 12-digit all-zero/all-F FontSpec Color attributes on winning managed settings and stores those colors as absent, which represents theme-default text. Other explicit colors remain exact document values. This is import normalization only: Phase 5 owns consuming explicit colors and resolving absent colors against the active theme across screen, PDF, and native print presentation.

- **Bounded wrap-cache eviction:** The element-wrap cache maintains an ordered usage index keyed by last-used generation, unique insertion order, and collision-bucket fingerprint. Hits update the index with the entry's current generation, insertion adds its key, and generation wrap rebuilds every key while resetting entry freshness. Overflow removes the oldest indexed key and locates that unique insertion within its collision bucket, avoiding whole-cache oldest-entry scans; lookup, freshness update, and eviction use ordered-index operations plus the existing collision-safe bucket search. Full-content equality, cache output, entry/byte limits, accounting, and invalidation remain unchanged.

- **Canonical span boundaries:** Each positioned span carries an immutable display-boundary offset vector with one entry per display-character boundary, beginning at zero and ending at the span width. Hit testing and caret geometry use those offsets and deterministic midpoint selection; justification adjusts the whitespace boundary and every later boundary consistently. This representation is ready for proportional per-scalar advances and does not itself select or measure a font.

- **Indexed first-line query for ruler projection:** [`ScreenplayLayout::first_line_for_element()`](../../../crates/scriptcraft-layout/src/interaction.rs:363) reads the first location from the existing per-element line index and returns its canonical `LocatedLayoutLine`; it does not resolve paragraph settings, recompute layout, or allocate a marker cache. The desktop ruler reads `unaligned_line_left` for the first-line position and `paragraph_bounds` for the final left/right bounds. These values include direct paragraph formatting and the currently composed active dual-dialogue columns. Querying the immutable current layout each frame avoids stale type-only caches and keeps the ruler a display projection rather than a second geometry resolver.

- **Monotonic wrapped-source remapping:** Projected display offsets return to canonical UTF-8 offsets through independent monotonic cursors for ordered line boundaries and ordered display segments, preserving the prior inclusive/exclusive boundary rules and empty/unmapped fallbacks without restarting a full source-map search for every line or segment. Unicode expansions retain every display cell's association with the originating source scalar, and newline/CRLF skipping, wrapped output, cache rebasing, and canonical line text remain unchanged. All wrapped lines from one owner share one immutable run slice; sharing does not change run content, style resolution, cache identity, or positioned-span ownership.

- **Ordered wrap run/style preparation:** Before scalar display projection, wrapping resolves each canonical run's source range and parsed style flags once in source order. A monotonic cursor selects those prepared flags as source offsets advance, replacing per-scalar run searches and repeated style-attribute parsing with linear run/style preparation. Effective run styles participate in horizontal scalar measurement and wrapping; after wrapping, the base style and distinct styles actually present on each visual line determine that line's maximum vertical leading. Canonical text, run-sensitive wrap-cache identity, uppercase display expansion, display/source mapping, Unicode boundaries, atomic ranges, and line-breaking policy remain unchanged. Direct fresh layouts and complete rebuilds that reuse element-wrap entries must produce identical geometry and styled content.

- **Ordered atomic expansion boundaries:** [`wrap_for_layout()`](../../../crates/scriptcraft-layout/src/wrap.rs) preserves the complete per-canonical-scalar display/source map and, for cached wrapping, the complete ordered display-range identity. A separate index contains only display ranges projecting one canonical scalar to multiple display scalars; multibyte UTF-8 encoding alone does not qualify. The index is constructed once before the cache/noncache branch, and noncached wrapping does not allocate the complete temporary range vector. [`atomic_boundary_is_forbidden()`](../../../crates/scriptcraft-layout/src/wrap.rs) uses an ordered partition-point lookup to select the first range whose end is greater than the proposed display byte boundary, then rejects it only when its start is strictly below that boundary. This is exactly the legacy strict-interior predicate: range starts and ends remain legal. Same-source expansion extension, backward whitespace selection, line advance, source remapping, cache identity, alignment, oversized behavior, and all other wrapping decisions remain unchanged.

- **Complete-layout session reuse:** Lookups anchored to a validated editing session may reuse an immutable complete layout when the session revision, effective layout inputs, merged source/direct settings, document identity, purpose, composition, and transient Body active-group presentation all match, without reconstructing the document-sized semantic signature. Validated-session misses also rely on the session-published revision rather than storing that generic fingerprint. Generic Project lookups retain semantic-signature construction and comparison on every same-revision lookup so direct content mutation cannot reuse stale geometry; changing any effective key still requires a complete layout build. Prepared Body reuse occurs only inside such a complete-layout miss and does not add incremental pagination, renderer caching, or viewport state to layout cache identity.

- **Complete prepared Body identity and hit flow:** A retained prepared Body paragraph is an immutable shared sequence of complete owner-local lines: canonical and display text, source/display maps, wrapped boundaries, positioned styled spans and decorations, run-sensitive scalar advances, alignment/justification results, paragraph bounds and metrics, keep/oversized flags, and every other value needed by placement and interaction. Its lines use local element zero, page zero, and zero vertical placement. The lookup hashes only the retained shared `BodyOwner` pointer, its local revision, and the resolved environment: purpose, exact composition, sequential/dual geometry, exact open key, effective definition/direct paragraph values, effective font/size/style/color values, resolved faces/metrics, and wrapping limits. Owner text and runs are never hashed or debug-formatted for a known-owner lookup. The cache retains each owner `Arc`, so pointer addresses cannot be recycled while entries live. A same-pointer candidate still requires revision and environment equality; any distinct-allocation collision candidate additionally requires complete canonical owner equality. Pointer, revision, or fingerprint alone never authorizes cross-candidate reuse. A hit returns the shared prepared paragraph before projection, source-map construction, wrap-cache lookup, rewrapping, or positioned-span construction; a miss follows the canonical resolved preparation path.

- **Resolved prepared-body miss policy:** Resolved-environment misses use complete canonical preparation; no previous-owner incremental preparation or suffix-reuse path remains. Prepared cache hits continue to require complete owner/environment identity equality, and misses still pass through the existing resolved wrap and span construction path before placement.

- **Prepared placement and bounded retention:** Complete page composition still performs explicit starts, keep-with-next, ordinary and dual block placement, oversized forward progress, spill, page creation, occupancy, active-group boundaries, and interaction-index rebuilding on every complete-layout miss. Placement clones prepared line/span shells and rebases only element index, page number, and vertical geometry; source offsets, owner-local horizontal geometry, text, maps, styles, and decorations remain exact. Title Page remains on its existing wrap/make-line path. Body and Print entries cannot substitute across purpose or composition. Prepared retention uses collision buckets plus an ordered `(last-used generation, insertion order, fingerprint)` index, with no additional whole-cache eviction scan; entry count and the complete retained owner/environment/line/span payload cost are updated on insertion, eviction, and clear under explicit entry and byte limits.

- **Optional value-free build observations:** `LayoutBuildDiagnostics` remains separate from immutable layout output and cache identity and contains only durations and work counts. An active carrier observes successful actual builds with aggregate whole-request, prepared environment/cache lookup, miss-only preparation, ordinary/Title/dual/oversized placement, prepared line/span rebase, interaction-index construction, and Body Y-order/sort values. Prepared hit and miss counts are distinct; miss preparation is never averaged with hit-only builds. Rebase is nested inside Placement and Body Y-order/sort is nested inside interaction indexes, so neither nested value is additive with its parent. The desktop computes a saturating remainder only from whole-request time minus lookup, miss preparation, Placement, and interaction indexes. Per-line rebase timestamps are taken only for an active optional carrier and their measurement overhead belongs to development readings; disabled callers use the existing non-diagnostic path without those timestamps. These observations do not change wrapping, placement, dual dialogue, oversized behavior, indexes, pagination, document content, or exports.

- **Document-point geometry and precedence:** Shared geometry uses OS-independent 72-points-per-inch document coordinates and signed fixed-point hundredths of a point. Effective body values resolve matching stable-ID direct fields over the exact current definition. TopMargin is the first line-box top; each canonical baseline is its line-box top plus the retained per-line natural ascent and DocumentLeading adjustment, while the next line-box top advances by full effective leading. Candidate fit compares each final natural bottom (baseline minus signed natural descent) with paper height minus BottomMargin; leading-based line-top advancement remains separate. Direct geometry is field-local and invalid definition derivation is bounded. Wrapping/horizontal placement use resolved per-scalar advances including run/font/size changes and display expansions; available width comes from effective indents, not fixed cells. Courier leading is 1.0×effective style size and Proportional leading is 1.2×size, selected by the exact resolved face. DocumentLeading contributes +0/+1/−1/−2 points for Normal/Loose/Tight/Very Tight before selecting the per-line maximum. The element base style participates on every visual line; distinct effective styles present on that wrapped line also participate. Empty lines use base metrics. SpaceBefore is exact nonnegative whole-unit B/S (selected points/base element-setting size) multiplied by effective base leading; inline size does not alter it. Apply only at nonempty same-page paragraph boundaries, not fresh-page starts. Natural descent determines final-line fit through baseline minus signed descent; line-gap remains extent data, and character ink never controls leading, wrapping, or clipping. Occupied-line counts are derived metadata only.
- **Compositions:** Body editor, Title Page editor, and Print with/without title page are explicit purposes. Body navigation/hit testing excludes title pages; title layout retains its separate paragraph source mapping. Only editable TitlePage Content paragraphs enter typography/layout resolution: typed Content uses its exact open definition key, type-less Content uses the explicit neutral title style, and every other title structure remains opaque. Print composition is independent of zoom, palette, host glyph advances, and transient active editor grouping. Definitions marked HiddenText remain visible/editable in subdued editor layout and are omitted from Print purpose without source renumbering. `AllCaps` is display-only and its display/source map preserves UTF-8 boundaries across Unicode expansions.
- **Dual Dialogue source/projection boundary:** The source group owns ordered member identities and wrapper provenance; active left/right sides derive only from that existing membership when current exact capabilities form two Character cues with only Dialogue- or Parenthetical-capability members after each cue. Either side may be empty. Only an active projection is composed as synchronized two-column geometry with a fixed shared 18-point center gap and equal column widths from the outer General writing extent; exact Character-capability cues center in each full column. If the projection is absent, the layout emits no dual block and the ordinary sequential Body path lays every member exactly once in document order. This inactive fallback does not unwrap or delete source membership. Active columns advance by the taller leading-derived side height, while fit uses the greater downward final natural-bottom extent of the two sides. They combine outer/first-member leading spacing by maximum rather than sum, suppress fresh-page and first-member top spacing, and retain inner source geometry for sequential mode. A fitting active group is placed atomically on the current page or moved whole to a fresh printable page; members do not make independent keep-with-next decisions. Only an active group too large for a fresh printable page enters bounded oversized spill/split fallback; it must progress and does not promise atomicity or synthesize MORE/CONT'D. A transient active Body group may use sequential ordinary geometry; it never changes Print composition. This changes only active-versus-sequential selection, not typography, geometry policy, or pagination policy.

- **Exact semantic handoff:** Active dual recognition uses exact Character, Dialogue, and Parenthetical capabilities over the source container's ordered members; nearby ungrouped paragraphs are not added by matching roles or labels. Layout consumes that derived active projection and otherwise emits every source member once in sequential order. Only exact base-label capabilities identify structural kinds. `PaginateAs` remains layout-only data: it cannot create scene, cue, dialogue, parenthetical, transition, Cast List, or dual identity. Dynamic fonts, paragraph geometry, wrapping, pagination composition, cache identity, and output typography remain Phase 5 work and are not part of the Phase 4 semantic contract.
- **Source/display correspondence and interaction:** Each rendered line carries canonical UTF-8 source ranges and display-to-source mapping. Hit tests, caret, selection, wrapped-line Up/Down, goal-x navigation, page ownership, and export resolve against the same immutable complete layout. Geometry indexes use deterministic document-order tie-breaking, constrain caret/owner lookup to requested-element lines, use ordered vertical candidates for nearest-body hit tests, and query adjacent body lines without flattening all lines; title pages are excluded from Body hit-test/navigation. Indexes are rebuilt per complete layout and contain no desktop presentation state.
- **Wrapping, pagination, and oversized content:** Exact definitions, direct values, and resolved scalar metrics control wrapping and page fit. Page placement, explicit page starts, empty paragraphs, title pages, and keep-with-next run deterministically on each complete revision. Body, keep-with-next, Title Page, dual-block, oversized, and spill placement fit through candidate final natural bottoms while retaining leading-based advancement and bounded forward progress without infinite loops or unbounded blank pages. A source-backed paragraph that changes direct attributes cannot be split by copying them; joining across a paragraph carrying supported direct attributes stops rather than losing them.
- **Resolved layout authority:** The desktop/session and output entry points provide the explicit resolved-font `LayoutEnvironment`; Body, Title Page Content, dual members, PDF, Windows print packaging, and plain-text Print composition pass its definition/style/paragraph resolutions into measured wrapping, span geometry, and vertical page fit. Direct and complete layouts use the same canonical position policy. Public layout builders and cache entry points require the explicit environment; canonical positioned spans always carry resolved style.
- **Canonical decoration spans:** A decorated positioned span retains optional backend-neutral scaled geometry beside its underline/strikethrough flags. Fixed-point font-coordinate `font_top`/`font_bottom` offsets are derived from the exact resolved face and effective style size; enabled flags must match geometry presence. Span coalescing, prepared/wrapped values, placement cloning/rebasing, and complete cache identity retain these values. Desktop projection/culling and output consumers use this geometry, but decoration extents remain excluded from wrapping, horizontal advances, line-box/leading advancement, baseline derivation, pagination, page fit, and interaction geometry.
- **Minimal placement page identity:** Fresh owner-local line construction receives only the immutable page number rather than a clone or borrowed whole growing page. Title Page continues to place those fresh lines directly; Body ordinary, dual-block, oversized, and spill placement rebase complete prepared lines. All paths retain their existing page creation, break, line-order, vertical-advance, and occupancy decisions. Pagination remains complete on every layout build; this placement implementation does not introduce incremental pagination or renderer policy.
- **Wrap-cache identity below prepared Body:** Immutable per-element wrap values remain the Title path and the prepared-Body miss path. They may be reused only when stable identity, full canonical content, exact open key, purpose/title/body context, effective paragraph geometry, resolved text style/color, scalar advances, and wrapping limits match. The fingerprint hashes those inputs together with the complete projected text, the ordered canonical run structure (run text and ordered attribute name/value pairs), and ordered atomic-range endpoints directly from borrowed slices; it does not debug-format runs or allocate a separate identity vector. Retained entries own shared exact run and range slices created on misses. A fingerprint collision still requires equality of every context field, the complete run and range values, and the complete projected text before cached lines can be reused. Complete page placement runs for every revision; retention is bounded and invalidated/rekeyed for source/runtime changes, purpose changes, replacement, undo/redo, and structural edits. Presentation scale, palette, egui context, font atlas, and galley data do not enter either layout cache. Interaction indexes belong only to their complete immutable layout.
- **Desktop conversion and export isolation:** Platform conversion is a presentation concern: at 100%, effective paper width in document points is multiplied by 1.0 on macOS, 96/72 on Windows, and neutral 1.0 elsewhere; native display scale is applied once by the host, independently of page zoom. Zoom changes page presentation only and never alters document points or source mapping. PDF and plain text request Print composition; PDF's supported styles do not change layout metrics, and viewport zoom, natural Arial advances, active grouping, and desktop layout caches never leak into output.

### Phase 5 typography and layout authority

The following decisions supersede any earlier fixed-role, fixed-cell, nominal-line, static-default, or desktop-natural-advance wording in this blueprint. The resolver in [`inputs.rs`](../../../crates/scriptcraft-layout/src/inputs.rs) accepts an explicit [`LayoutEnvironment`](../../../crates/scriptcraft-layout/src/inputs.rs), looks up managed body and TitlePage Content definitions by exact key, and overlays only matching stable-ID direct values. Type-less Content titles use the environment's explicit neutral style and page-bounds paragraph baseline. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and every other title structure outside Content remain opaque and outside layout/model typography resolution. For paragraph fields, valid direct left/right values are accepted as a pair; an invalid direct pair falls back to the complete definition pair, and an unusable definition pair falls back to page margins. First indent resolves independently: direct value, definition value, then zero, retaining a negative hanging indent only when it fits. Alignment, SpaceBefore, and StartsNewPage resolve independently from the matching direct field over the current definition. Unsupported Leading/Spacing spellings fail bounded resolution rather than acquiring guessed numeric meanings. Courier and Proportional are size-derived resolvers; DocumentLeading adjusts candidate style leading by +0/+1/−1/−2 points, then the base style and styles actually present on each post-wrap visual line determine that line's maximum. SpaceBefore is the exact nonnegative whole-unit ratio of selected points to base element-setting size, multiplied by effective base leading. PaginateAs enables keep-with-next only for exact Scene Heading, Character, and Parenthetical values; every other spelling disables it without changing structural capabilities.

Canonical layout receives an explicit, transient, backend-neutral resolved-font environment. It contains declared-family requests, four independently resolved face styles, resolved face/content identities, vertical metrics, and bounded per-scalar advances/missing markers. Courier Final Draft, Courier, Courier New, and Courier Prime requests select bundled Courier Prime; Arial/Helvetica-like requests select the nearest available sans family, Times New Roman requests the nearest available serif family, and unknown families or unavailable requested faces resolve safely to the matching bundled Courier Prime style. Host discovery, platform font APIs, byte loading/registration, and renderer objects remain in the desktop adapter; model/layout/export consume only explicit resolved identities and metrics. Scaling uses one deterministic final fixed-point rounding rule. The environment is not Project/FDX semantic state.

The model-owned value contract is implemented in [`typography.rs`](../../../crates/scriptcraft-model/src/typography.rs): each bounded face ID identifies a face with source-kind, labels, byte length, deterministic content fingerprint, vertical font-unit metrics, and an explicitly bounded scalar-to-advance/missing-marker map. A requested family maps exact family text to four separately selected face IDs; missing selections are not inferred during a layout query, and the environment must provide the neutral Courier Prime request. Metric scaling uses checked integer arithmetic and rounds once to hundredths of a point. Full environment equality compares every mapping, face identity, and metric; a fingerprint is a candidate identity summary, not permission to reuse output without equality. These values remain transient and backend-neutral. `LayoutEnvironment` carries page-only inputs, the prepared `DocumentFontEnvironment`, and explicit neutral title-style inputs; it does not store host font state on Project or preservation data. Effective styles retain declared family/color spelling while referring to the resolved face ID and explicit color state.

The desktop preparation signature is the exact set of current definition families, direct run Font requests, canonical displayed scalars, required Unicode uppercase expansions, and host-catalog generation. [`presentation/document_font_preparation.rs`](../../../apps/scriptcraft/src/presentation/document_font_preparation.rs), coordinated by [`presentation/document_font.rs`](../../../apps/scriptcraft/src/presentation/document_font.rs), rebuilds it before layout lookup; unrelated revisions can reuse an equal prepared environment, while changed definitions, run text/Font attributes, or all-caps projections require a new complete preparation. Every selected face is parsed/measured from the same bounded bytes later offered to the renderer. Regular/Bold/Italic/Bold Italic and missing-glyph markers are explicit per face/scalar. Any preparation error rejects the whole environment rather than exposing partial metrics. [`presentation/host_font_catalog.rs`](../../../apps/scriptcraft/src/presentation/host_font_catalog.rs) remains desktop-only discovery; [`presentation/bundled_font_startup.rs`](../../../apps/scriptcraft/src/presentation/bundled_font_startup.rs) owns bundled Courier Prime registration, and [`presentation/renderer_font_registration.rs`](../../../apps/scriptcraft/src/presentation/renderer_font_registration.rs) owns egui activation/readiness. Host filesystem paths and screenplay text never enter the model environment, face IDs, or fallback metadata.

Effective body/title styles retain declared family and source color spelling while resolving supported size/style flags and color state. Absent color alone means theme default on desktop and black ink in output; supported explicit RGB remains literal on text and decorations. Unsupported explicit color remains distinguishable from absence, uses the bounded documented fallback, and contributes to a value-free report/diagnostic without rewriting source spelling.

The model color input has three exact states: absent means `ThemeDefault`; only a `#` followed by twelve hexadecimal digits resolves to `ExplicitRgb8` by taking each channel's most-significant byte; any other present spelling is `UnsupportedExplicit`. The original optional spelling remains attached to the transient effective style so downstream cache/report policy can distinguish invalid explicit input from absence.

Per-scalar resolved advances define canonical wrap, alignment, justification, page geometry, and display-boundary offsets for desktop interaction and output. Desktop paint positions glyphs at canonical baselines and scalar offsets; it cannot independently rewrap, repaginate, realign, or replace canonical advances with natural galley advances. Viewport zoom, palette, selection, and native output settings stay outside canonical geometry/cache identity. Courier leading is 1.0×size and Proportional leading is 1.2×size, selected by exact resolved-face category; DocumentLeading adds +0/+1/−1/−2 points per style. After wrapping, each line uses the maximum among the element base style and effective styles actually present on that visual line. SpaceBefore uses the exact whole-unit B/S ratio times effective base leading, and applies only at nonempty same-page paragraph boundaries. Natural descent determines candidate final-bottom fit; line-top advancement remains full effective leading, and line boxes do not clip glyphs vertically. TopMargin anchors the first line-box top. Each baseline is the line-box top plus its retained per-line natural-ascent/DocumentLeading offset, while the next line-box top advances by full effective leading. Existing ordinary bottom fit remains based on line-box bottom until WO-002.1. Unsupported Leading/Spacing spellings acquire no new numeric meaning. PaginateAs enables keep-with-next only for exact Scene Heading, Character, and Parenthetical values; all others disable it. StartsNewPage remains paragraph/direct-override data.

Page-fit decisions use candidate final natural bottoms against the BottomMargin boundary; advancement remains based on full effective leading and oversized spill remains bounded with no ink-clipping promise. Oversized spill remains bounded and makes no ink-clipping promise. Complete, wrap, and prepared-body cache reuse includes effective PageLayout/DocumentLeading, resolver category, ordered definitions/direct values, base leading, SpaceBefore units/gap, styles/runs/text/context, exact face metadata/metrics/scalar maps, and retained per-line leading/natural extents plus the derived baseline offset as applicable. Fingerprints select candidates only; full equality is required. Prepared-font ID collisions additionally compare exact bytes, face index, and complete face equality. Baseline is derived after placement/rebase from the line top plus its retained per-line offset, not independently cached; full effective leading remains the line-top advance. A same resolved ID with changed bytes or metrics is not interchangeable. Viewport, palette, native scale, PDF payloads, and native output objects remain outside canonical identity.

The cache identity implementation carries an exact [`LayoutEnvironment`](../../../crates/scriptcraft-layout/src/inputs.rs) into complete cache lookup and retained [`ScreenplayLayout`](../../../crates/scriptcraft-layout/src/geometry.rs). Complete semantic identity includes Project-effective page fields and DocumentLeading, ordered definitions/direct settings, purpose/composition/geometry mode and neutral title style. Environment equality includes resolver category, exact family/style mappings, resolved face identity/content, complete vertical/scalar metrics and missing markers. Wrap and prepared identities include base leading, SpaceBefore units/gap, exact keys, full text/runs/styles/colors and output line geometry; fingerprints only select candidates and full equality authorizes reuse. Prepared-font ID reuse additionally compares exact bytes, face index, and complete face values. Per-line leading and natural extents remain with wrapped/prepared output; absolute baselines derive after placement/rebase. Source spelling/original bytes/unknown attributes and unused header/footer margins do not cause false misses when effective inputs match. Zoom, palette, viewport, native scale, PDF payloads/objects, Windows packages/native handles, and desktop galleys remain outside canonical caches. Existing collision, entry/byte bounds, invalidation and eviction behavior remain unchanged; reused output equals fresh preparation/layout.

PDF requires one coherent explicit resolved-font environment plus immutable face/byte payload, and consumes Print's canonical baselines and scalar boundaries without reflow. Used packaged Courier Prime faces embed complete unmodified OFL bytes; eligible host/synthetic faces embed only within licensing, format, metric, scalar, resource and byte bounds. CID/GID and ToUnicode support non-BMP mappings; missing embedded glyph uses GID 0 and is reported. Base-14 and `?` fallback is limited to eligible host/synthetic faces and separately reported. macOS PDF-backed Print forwards the same Arc-backed environment-plus-payload snapshot. Windows receives environment-only snapshots and immutable vector packages: DirectWrite measures its no-wrap baseline only to cancel native row offset, while canonical baseline and x remain authoritative; its report covers nearest-family substitution, unverified face/shaping/coverage, missing glyph and natural-extent observations—not canonical geometry uncertainty. Plain text remains environment-only. No output consumer rewraps or repaginates; output does not establish exact visual parity, universal coverage, Final Draft pagination parity, or physical delivery.

For standard Normal 12-point Courier Prime inputs, the packaged resolved ascent of 8.33 points places the first canonical baseline at TopMargin + ascent = 80.33 points; PDF converts that same baseline to y = 711.67 on US Letter. The shared PDF complete-face encoder expresses FontBBox coordinates, ascent, descent, and cap height in normalized 1000-unit descriptor space using the face's actual units per em, without modifying the complete embedded font bytes or canonical baseline/scalar positions. Hanging-indent-aware horizontal clipping, expected natural-extent observation policy, and the 0.15-leading visual-caret translation are desktop projections only: canonical layout, selection/interaction geometry, and the IME anchor remain unchanged, so none introduces a second layout authority.

macOS native Print initializes paper from the accepted snapshot's effective dimensions, zero additional application margins, and 100% scaling, while PDFKit adds no fit scaling. These are pre-panel defaults; accepted native settings remain user-owned, and no second application margin or native layout authority is introduced.

### WO-009.1 resolved output-consumer ownership

`scriptcraft-export::export_text(project, environment)` and `export_text_with_layout_inputs(project, inputs, environment)` require the prepared `LayoutEnvironment` and build Print composition with title page included. PDF entry points likewise require that environment, and PDF/Windows package consumers read each span's required `resolved_text_style`. ### Landed direct paragraph formatting layout formula

The paragraph Leading list and adjustment in the formula below include Very Tight: the supported direct values are Very Tight, Regular, Tight, and Loose, with adjustments −2, 0, −1, and +1 points respectively. This narrowly supersedes the earlier three-value enumeration and does not alter document-level Leading or the composition order.

The Very Tight Leading and Run Colors initiative adds paragraph Very Tight at −2 points (−200 fixed-point hundredths), with exact source spelling `Very Tight` and menu order Very Tight, Tight, Regular, Loose. The adjustment enters the existing formula after maximum ordinary leading and exact Spacing multiplication, is additive with DocumentLeading, and also contributes to baseline offset and the effective base leading used by Space Before. Document-level Very Tight remains distinct; definition-owned `Single` remains Regular. Background has no effective-style, geometry, cache, page-paint, PDF, or print role in this initiative.

Direct paragraph values are typed `ParagraphLeading` (Regular, Tight, Loose) and `ParagraphSpacing` (Single, OneAndHalf, Double); absence inherits from the current exact definition. Unrecognized imported values remain source-owned and have no numeric interpretation. For each visual line, compute ordinary leading for the element base style and styles actually present on that line from effective size and exact resolved-face category without document/paragraph adjustments, take their maximum, multiply by spacing ratio 1, 3/2, or 2 using fixed-point arithmetic, then add DocumentLeading's +0/+1/−1/−2 point adjustment and ParagraphLeading's Regular +0, Tight −1, or Loose +1 point adjustment. Require positive finite leading. ParagraphLeading is also added to the baseline offset in the same way as DocumentLeading; neither point adjustment is multiplied by spacing. Space Before uses the resulting effective base leading; menu choices 0/1/2/3 lines multiply the current definition's base font size in points, not inline run size. Typed direct values and effective paragraph values participate in complete cache equality. This approved formula supersedes the earlier boolean-only Regular/Single and unsupported Tight/Loose/1.5 descriptions for these direct overrides. It is an application contract, not a claim of Final Draft pixel parity.
