# Component Blueprint: Desktop Adapters

## Beat spatial interaction (WO-007)

The Beat viewport owns transient pointer capture and fractional previews, never semantic geometry. Reverse Item-order hit testing selects the top card; selected edges/corners take resize precedence and title/body regions are reserved for later text editing. Card margin drag and resize draw the preview above other cards, and release dispatches one snapped/clamped geometry command with activation. Empty-board double-click creates at the snapped/clamped pointer; an empty click clears selection. Escape, pointer loss and focus loss cancel; release outside uses the last available pointer position. Current root, menu, modal, replacement, native-output, element-dialog and Title ownership block input. The card cache reuses position-only layouts; size changes rebuild only the affected card. This source description is not visual acceptance.

## Beat root integration (WO-004)

The desktop owns a transient Script/Beat root independently of the Body/Title semantic surface. Command 64 and Script mode commands select the root through the shared availability/dispatch path; both menu backends project mutually exclusive checks, with retained native check updates. A Dashboard action is added only to the default main composition. Beat central composition does not call the Script frame or allocate a ruler. Its status omits page and Body guidance but retains the existing per-window Focus Mode action, Timer, Appearance, diagnostics and zoom ownership; Focus Mode uses the shared fullscreen observation, state, command and dispatcher. Script/Title status behavior is unchanged. Title child zoom wins while active or swapped; otherwise the active root chooses Script 75–300 or Beat 5–300. The shared typed zoom range is 5–300, with desktop target enforcement, unchanged presets and policy-aware slider/gesture/step handling. WO-004 did not introduce card painting; WO-006 subsequently added read-only cards.

## Beat viewport and navigation (WO-005)

[`views/beat_board/geometry.rs`](../../../apps/scriptcraft/src/views/beat_board/geometry.rs) is the shared projection authority: `screen = viewport_origin + (board - scroll_origin) * z`, `board = scroll_origin + (screen - viewport_origin) / z`, with `z = zoom_milli_percent / 100000`. The origin is clamped per axis to `0..max(0, board_dimension - viewport_dimension / z)`, including on resize and zoom. [`viewport.rs`](../../../apps/scriptcraft/src/views/beat_board/viewport.rs) paints a top-left-anchored finite board and workspace outside it, clips to the actual viewport and board, and derives visible line ordinals for the 40-pixel grid beginning at 20. Only painted line centers are pixel-snapped; no scrollbar is allocated. Culling and 20-pixel snapping helpers prepare later card work without altering imported geometry.

The app publishes only transient viewport, clip, pointer and visible-board geometry. Raw wheel/pinch processing respects root/menu/modal/replacement/native-output/element ownership; the zoom adapter removes matching wheel gestures before ordinary axis-preserving pan, and the same event is not replayed through smooth scrolling. Center controls and pointer-or-center gestures calculate and clamp their anchor immediately, so later pan has no pending anchor to cancel. Root switch and successful activation clear transient publication; activation installs the new FDX values. Save/Save As capture live milli-pixel origin and milli-percent zoom through the existing save context without touching Project, revision, mutation token, dirty state or history for navigation alone. Script and Title retain their existing viewport paths.

### Supplemental Beat overlay-scrollbar adapter (WO-005)

`views/beat_board/scrollbars.rs` computes both axes independently from the currently clamped viewport geometry and paints 10-point overlay bars/thumbs after all board and card content. Visibility, proportional extent/position, 24-point minimum thumb, flush right/bottom placement and shared-corner reservation are derived on demand; no geometry is persisted. The track is not painted. Handles retain `EditorScrollbarPalette` RGB values with alpha 64 fill and a 1-point corresponding-RGB alpha 128 border in every state, and changes only the disposable Beat view state through `clamp_origin`. The capture and consumed-track-press state are nested in `BeatInteraction`, so existing cancellation covers Escape, pointer/focus loss, root/view/document changes, and interaction-token invalidation. The viewport invokes this hit target before spatial and text adapters, suppressing card/text activation, selection, empty-board deselection and double-click creation over the bars. Wheel/pinch and focused-body-first vertical scrolling remain on their existing path; the board rectangle and card-body presentation are unchanged. This is source integration only, not a native or visual result.

Auto-hide is part of that same transient adapter state. It starts hidden on root/document reset; actual pointer movement inside the clipped viewport or an effective central comparison change to disposable zoom/scroll origin refreshes a 1.0-second deadline and requests the repaint that hides the bars at expiry. This covers wheel/trackpad, pinch, thumb drag, status/menu/slider zoom, and other view-state paths. Pointer presses/clicks, card creation/selection/editing, text selection/caret placement, typing, IME, clipboard, formatting, semantic edits, and focused-body scrolling alone are nonqualifying. Thumb capture and active pointer presence over a previously visible hit region retain visibility; hidden bars do not hit-test. No animation, command, persisted field, package edge, or change to existing card/text behavior is introduced.

## Beat read-only cards (WO-006)

[`viewport.rs`](../../../apps/scriptcraft/src/views/beat_board/viewport.rs) culls against the visible board and paints cards in forward Item order, so later cards appear on top. [`paint.rs`](../../../apps/scriptcraft/src/views/beat_board/paint.rs) uses the page paper and border roles, clips to the board/viewport and card-local title/body regions, and paints canonical positioned spans and decorations. The reusable selected border is a 3-point light-blue middle stroke, but the viewport supplies no selection. There is one board interaction surface, not a persistent widget tree per card.

[`presentation/span_paint.rs`](../../../apps/scriptcraft/src/presentation/span_paint.rs) shares resolved face, scaled size and color projection between Script and Beat; canonical galley and decoration geometry remains shared presentation machinery. The existing preparation path includes Arial regular/bold defaults, Beat run families, canonical scalars and uppercase expansions, placeholders and ellipsis, with existing bounded fallback and renderer registration/readiness. Empty titles and wholly empty bodies use subdued presentation-only “Beat Title” and “Body”; long titles use a display-only ellipsis, and body paint stops at the first line that does not wholly fit. Explicit supported run colors and existing decoration behavior remain in force; Background remains durable data without a new highlight-rendering policy.

[`cache.rs`](../../../apps/scriptcraft/src/views/beat_board/cache.rs) retains disposable per-card layouts by stable identity and compares the complete card with x/y excluded, card metrics, resolved environment and exact prepared face bytes/index. Width or height, content or environment changes can rebuild the affected entry; movement and zoom do not. Whole-pixel dimensions are exact in card text layout; existing fractional imported sizes round to hundredths only there, with the durable rectangle unsnapped. Card layout is independent of screenplay page composition and excluded from PDF, plain text and native print.

This describes landed source, not rendered or host-font acceptance. Card selection, creation, moving/resizing, caret and editing remain WO-007 onward; validation is user-owned.

> This component owns desktop presentation and translates typed host-effect requests into platform interactions without taking ownership of document semantics.

## Capability

Desktop adapters render the Script View and title-page window, project semantic/session state into toolbar, status and menu controls, and bridge native facilities such as fonts, clipboard, dialogs, viewport operations, PDF/Print, icons, and packaging/runtime resources. Their state is presentation or host state unless a distinct component explicitly commits a typed semantic operation.

## Composition

The app-private [`settings.rs`](../../../apps/scriptcraft/src/settings.rs) is declared from [`main.rs`](../../../apps/scriptcraft/src/main.rs) as the desktop package's global-preference owner. It is distinct from transient per-window adapters and introduces no reusable service or package; its integrated ownership and persistence contract is detailed in [User Settings](user-settings.md).

```component
name: DesktopAdapters
container: ScriptCraft Desktop
responsibilities:
  - Render body/title surfaces and transient toolbar, status, and menu state.
  - Adapt keyboard/pointer/IME, native windows, clipboard, dialogs, fonts/theme, and output facilities.
  - Keep native handles and platform-specific behavior outside reusable document components.
```

## Contracts

- **Unified desktop page geometry and publication:** Script View allocates every layout page row in order to preserve the full scroll extent and source geometry. Each row contributes one presented-page value containing its actual host-allocated viewport rectangle and unscaled document-Y offset; Page/Normal/Speed presentation policy determines that row's height, explicit gap, scoped vertical spacing, horizontal overflow/centering, and offset. A separate viewport paint range finds actual page-rectangle/editor-clip intersections and expands by the existing one-page overscan on either side. Painting and ordinary interaction projection are bounded to that range, with a conditional reveal target projected when needed. The same complete presented-page collection drives pointer-page selection, caret reveal, page-status publication, visible-page and nearest-page center-anchor selection, and zoom-anchor inputs. The existing nonvirtual `ViewportPageTracker::publish()` path owns a frame/viewport-local snapshot, validates finite geometry, compares the complete old/new page values together with revision, viewport, scale, clip, and scroll offset, and requests repaint on change. Pending zoom planning retains its complete origin/stride/extent computation and compensation behavior. Model canonical text, layout pagination/source maps/interaction indexes, export outputs, Print, session persistence, and responsiveness metric definitions remain authoritative and unchanged.

- **Session-aware render layout lookup:** Body and Title Page rendering request complete layouts from `scriptcraft-layout` through validated-session cache entry points rather than generic Project lookups. The session supplies its revision and read-only layout inputs derived from the current Project-owned effective DocumentPageLayout; Body additionally keys the transient active-group presentation and Title Page fixes the title-editor composition. Document replacement and all effective-key mismatches retain ordinary cache invalidation/rebuild behavior. Desktop zoom, palette, viewport, font atlas, renderer registration, and galley state remain outside this lookup and do not alter layout-owned geometry.

- **Phase 5 resolved typography projection:** This contract supersedes any earlier statement that host Arial natural advances may affect screen interaction or that fixed cells remain canonical. The desktop resolver owns bounded host-font discovery and exact-byte registration, prepares transient resolved-font identities and scalar/vertical metrics required by the current document, and supplies the same resolved face identity to layout and paint. Paint selects the registered egui family only through the prepared environment's declared-family/style-to-resolved-ID mapping; it does not reclassify a family or query a generic Monospace/Sans/Serif face. Backend-neutral model/layout/export code does not enumerate host fonts or call platform font APIs. Desktop text paint, selection, caret, pointer, navigation, decorations, and IME use one projection of stored canonical display-boundary offsets; the galley contributes glyph rasterization/UVs only, and its natural advances cannot change wrapping, pagination, alignment, or geometry. Selection and interaction retain canonical leading-sized line boxes; desktop glyphs use the retained canonical baseline (line-box top plus offset), while the full-height visual caret remains translated by the named 0.15-leading presentation ratio. Visual caret painting and conditional reveal use its shifted rectangle; IME keeps the canonical line-box top and height and uses the same baseline offset as ordinary glyphs. Horizontal clipping uses the lesser of paragraph left and the scaled canonical indented line left, while retaining paragraph right; metric-aware culling uses that same interval. Natural extent remains available to culling (including the line box, baseline, and natural intervals) and its performance counter, with Windows package observations compared against the actual line-box bottom; expected natural descent does not post a persistent desktop status warning, while actionable typography diagnostics remain available. Absent color follows the theme, supported explicit color remains literal on text and decorations, and unsupported explicit color uses a value-free bounded diagnostic and documented theme fallback. The projection applies to managed Body and TitlePage Content text only; non-Content title structures remain opaque and unchanged. A prepared environment changes when a required family/scalar or host-catalog generation changes, not merely because of zoom, palette, or unrelated revision.

- **Phase 5 output boundary:** PDF receives one prepared resolved-font environment plus immutable face/byte payload and consumes canonical Print baselines/scalar x positions without reflow. Used packaged Courier Prime faces embed complete, unmodified OFL bytes; eligible host/synthetic faces embed only under the bounded licensing/format/metric/repertoire/budget policy. CID/GID and ToUnicode include non-BMP mappings; missing embedded glyphs use GID 0 and are reported. Base-14 and `?` substitution are host-only fallbacks, separately reported from embedding reason and explicit-color fallback. Packaged payload/face failures are errors. PDF limits are 8 MiB per face, 24 MiB aggregate original bytes with packaged-first reservation, 4,096 scalars per face, 268 resources, 64 MiB complete output, and 16 report categories. Save As PDF and macOS PDF-backed Print carry the same coherent Arc-backed environment-plus-payload snapshot and bounded report. Plain text remains environment-only. Windows captures environment-only immutable request inputs and vector packages, measures the no-wrap DirectWrite baseline only to cancel native row offset, and positions glyphs from canonical baseline and scalar x; no line-box y clipping occurs. Windows reports Courier New/nearest-family substitutions, unverified face/shaping/coverage, known missing glyph and natural-extent counts, and color fallback. Baseline measurement is not canonical-geometry uncertainty; Windows does not claim exact face-byte identity. No output claims exact visual parity, Final Draft pagination, universal glyph coverage, or physical delivery.

PDF FontDescriptor FontBBox coordinates, ascent, descent, and cap height are normalized by the shared complete-face encoder to 1000-unit PDF space using each face's units per em; embedded font-program bytes remain complete and unchanged. This metadata conversion is independent of the canonical standard first baseline, which derives from retained packaged metrics (80.33 points, PDF y = 711.67 on US Letter), and does not create a second layout authority.

WO-009.1 leaves preparation ownership in `documents/output.rs::output_layout_environment`, which calls the existing `DocumentFontStore::prepare_document` and passes that environment to PDF and immutable native-print requests. The Windows print worker receives the already-prepared environment through its request snapshot; it does not discover fonts or construct another authority. The public plain-text export API now requires an environment, but source inspection found no desktop production caller for it.

- **Phase 6 shortcut grammar and conflict policy:** Parse only the platform source value (`Shortcut` on macOS, `WinShortcut` on Windows); all other platforms have no active document-defined bindings. The bounded parser trims surrounding ASCII whitespace only, preserves the owned source spelling, and treats empty/whitespace-only values as no binding. Plus-separated components accept ASCII case-insensitive Ctrl/Alt/Option/Shift modifiers, without repeated slots, followed by exactly one A–Z, 0–9, supported named editor key, semicolon, or colon. Bare chords imply Command on macOS and Control on Windows; macOS Ctrl adds literal Control, Windows Ctrl is the implied primary, and Windows Shift adds Shift. Alt and Option alias the same slot. Semicolon and colon are logical text chords, with colon canonicalized to Shift+semicolon before exact matching/conflict resolution. A pure resolver reads only the selected platform field from the current ordered definition registry. Injected exact menu reservations (including platform aliases and disabled placeholders) and fixed-editor wildcard key classes disable all affected definitions; all members of any unreserved duplicate group are also disabled. No vector-order winner is selected. Issues contain only a zero-based definition ordinal, stable issue kind, and optional coarse normalized key category; at most 32 are retained and suppressed issues are counted separately. Diagnostics exclude raw shortcut strings, element labels, screenplay text, paths, and source payloads. This parser/resolver does not bind keyboard events; WO-006.6 owns live input, focus/IME, menu ownership, and refresh integration.

Exact reserved chords include actual native/in-window menu accelerators (including aliases and disabled placeholders) and macOS Command-Q; an unavailable menu owner does not release its chords.
