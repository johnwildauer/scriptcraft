# Component Blueprint: Desktop Adapters

> This component owns desktop presentation and translates typed host-effect requests into platform interactions without taking ownership of document semantics.

## Capability

Desktop adapters render the Script View and title-page window, project semantic/session state into toolbar, status and menu controls, and bridge native facilities such as fonts, clipboard, dialogs, viewport operations, PDF/Print, icons, and packaging/runtime resources. Their state is presentation or host state unless a distinct component explicitly commits a typed semantic operation.

## Composition

```component
name: DesktopAdapters
container: ScriptCraft Desktop
responsibilities:
  - Render body/title surfaces and transient toolbar, status, and menu state.
  - Adapt keyboard/pointer/IME, native windows, clipboard, dialogs, fonts/theme, and output facilities.
  - Keep native handles and platform-specific behavior outside reusable document components.
```

- [`main.rs`](../../../apps/scriptcraft/src/main.rs) is the process entry and top-level module root. [`app/mod.rs`](../../../apps/scriptcraft/src/app/mod.rs) declares the focused state, startup, update, window, surface/render, diagnostics, and responsiveness modules; [`commands/mod.rs`](../../../apps/scriptcraft/src/commands/mod.rs) declares availability, dispatch, and editing/navigation/clipboard/document/view/timer/Elements command families, with [`commands/dispatch.rs`](../../../apps/scriptcraft/src/commands/dispatch.rs) as the single desktop dispatcher. [`documents/mod.rs`](../../../apps/scriptcraft/src/documents/mod.rs) declares lifecycle, open/import, save, replacement, output, PDF, Print, and unsaved-change coordination.
- [`chrome/mod.rs`](../../../apps/scriptcraft/src/chrome/mod.rs) declares menu/items/shortcuts, toolbar/items, status, theme, and focus-mode modules; [`presentation/mod.rs`](../../../apps/scriptcraft/src/presentation/mod.rs) declares the document-font facade, host catalog, bundled-startup, document-preparation, renderer-registration, material-font, geometry/style, wheel-zoom, and runtime-icon modules. [`views/mod.rs`](../../../apps/scriptcraft/src/views/mod.rs) declares [`views/script/mod.rs`](../../../apps/scriptcraft/src/views/script/mod.rs) and [`views/title_page/mod.rs`](../../../apps/scriptcraft/src/views/title_page/mod.rs); the Script View's focused children own page policy, paint, pointer, keyboard/IME/navigation, caret/reveal, zoom/scroll, and frame composition. [`widgets/mod.rs`](../../../apps/scriptcraft/src/widgets/mod.rs) declares [`widgets/elements/mod.rs`](../../../apps/scriptcraft/src/widgets/elements/mod.rs) for the transient Elements/selector windows and [`widgets/sprint_timer/mod.rs`](../../../apps/scriptcraft/src/widgets/sprint_timer/mod.rs) for timer state, geometry, paint, interaction, animation, and notifications. [`platform/mod.rs`](../../../apps/scriptcraft/src/platform/mod.rs) declares target-gated [`platform/macos/mod.rs`](../../../apps/scriptcraft/src/platform/macos/mod.rs) and [`platform/windows/mod.rs`](../../../apps/scriptcraft/src/platform/windows/mod.rs) native-adapter roots.
- Module roots contain declarations and deliberate crate-local re-exports where those boundaries are established; focused implementations live in private child modules, while an implementation established directly in a feature root remains app-private there. They compose the single [`scriptcraft` app package](../../../apps/scriptcraft/) and do not form a reusable UI library, service locator, public app API, alternative document/service layer, or new package.
- All enabled semantic actions enter through [`Command Contract`](command-contract.md). [Document Model](document-model.md) owns canonical values and retained source-preservation state; [Editing session](editing-session.md) owns edits/history and native storage; [FDX preservation and storage](fdx-preservation-and-storage.md) separates codec ownership from those model/session responsibilities; [Layout and pagination](layout-and-pagination.md) owns canonical geometry; [Exports and print](../features/exports-and-print.md) documents bounded reusable output and native print composition.

## Contracts

- **Unified desktop page geometry and publication:** Script View allocates every layout page row in order to preserve the full scroll extent and source geometry. Each row contributes one presented-page value containing its actual host-allocated viewport rectangle and unscaled document-Y offset; Page/Normal/Speed presentation policy determines that row's height, explicit gap, scoped vertical spacing, horizontal overflow/centering, and offset. A separate viewport paint range finds actual page-rectangle/editor-clip intersections and expands by the existing one-page overscan on either side. Painting and ordinary interaction projection are bounded to that range, with a conditional reveal target projected when needed. The same complete presented-page collection drives pointer-page selection, caret reveal, page-status publication, visible-page and nearest-page center-anchor selection, and zoom-anchor inputs. The existing nonvirtual `ViewportPageTracker::publish()` path owns a frame/viewport-local snapshot, validates finite geometry, compares the complete old/new page values together with revision, viewport, scale, clip, and scroll offset, and requests repaint on change. Pending zoom planning retains its complete origin/stride/extent computation and compensation behavior. Model canonical text, layout pagination/source maps/interaction indexes, export outputs, Print, session persistence, and responsiveness metric definitions remain authoritative and unchanged.

- **Session-aware render layout lookup:** Body and Title Page rendering request complete layouts from `scriptcraft-layout` through validated-session cache entry points rather than generic Project lookups. The session supplies its revision and effective layout inputs; Body additionally keys the transient active-group presentation and Title Page fixes the title-editor composition. Document replacement and all effective-key mismatches retain ordinary cache invalidation/rebuild behavior. Desktop zoom, palette, viewport, font atlas, and galley state remain outside this lookup and do not alter layout-owned geometry.

- **Phase 5 resolved typography projection:** This contract supersedes any earlier statement that host Arial natural advances may affect screen interaction or that fixed cells remain canonical. The desktop resolver owns bounded host-font discovery and exact-byte registration, prepares transient resolved-font identities and scalar/vertical metrics required by the current document, and supplies the same resolved face identity to layout and paint. Paint selects the registered egui family only through the prepared environment's declared-family/style-to-resolved-ID mapping; it does not reclassify a family or query a generic Monospace/Sans/Serif face. Backend-neutral model/layout/export code does not enumerate host fonts or call platform font APIs. Desktop text paint, selection, caret, pointer, navigation, decorations, and IME use one projection of stored canonical display-boundary offsets; the galley contributes glyph rasterization/UVs only, and its natural advances cannot change wrapping, pagination, alignment, or geometry. Absent color follows the theme, supported explicit color remains literal on text and decorations, and unsupported explicit color uses a value-free bounded diagnostic and documented theme fallback. The projection applies to managed Body and TitlePage Content text only; non-Content title structures remain opaque and unchanged. A prepared environment changes when a required family/scalar or host-catalog generation changes, not merely because of zoom, palette, or unrelated revision.

- **Phase 5 output fallback boundary:** PDF and plain-text Print composition require the prepared resolved-font environment; PDF consumes Print's canonical scalar-boundary positions and reports bounded Base-14 resource substitutions, unsupported scalar substitutions, and unsupported explicit-color fallbacks. Save As PDF surfaces the report summary after successful writing. macOS PDF-backed print retains the same report in its immutable request and surfaces the summary with the operation outcome. Windows captures the same prepared environment in its immutable request, selects the resolved host family/style by family name, and uses Courier New only as a reported Windows substitution for bundled Courier Prime/unknown-family fallback. It draws each scalar at canonical boundary offsets without wrapping or repagination, applies supported per-run RGB and black ink for absent/unsupported output color, and surfaces fixed-size, count-only summaries for Courier/nearest-family substitution, DirectWrite family/glyph and host shaping/metric limitations, and unsupported-color fallback when preview opens. DirectWrite family-name selection does not prove byte identity or exact shaping parity. Neither successful output nor native callback claims embedded-font parity, exact Final Draft pagination, complete non-ASCII support, or physical delivery.

WO-009.1 leaves preparation ownership in `documents/output.rs::output_layout_environment`, which calls the existing `DocumentFontStore::prepare_document` and passes that environment to PDF and immutable native-print requests. The Windows print worker receives the already-prepared environment through its request snapshot; it does not discover fonts or construct another authority. The public plain-text export API now requires an environment, but source inspection found no desktop production caller for it.

### WO-009.2 resolved Script View paint

Script View span paint requires the resolved style carried by each canonical positioned span. It uses that style and the same prepared layout environment for declared-family/style face selection, size, decorations, and color; it does not rebuild legacy effective style from source font-family or run attributes. Caret/IME font selection uses the span's resolved style, with the prepared neutral resolved font as the final fallback. Legacy span-paint/color projection helpers and missing-style family fallback branches are retired. The desktop font responsibility split is described in the WO-010.1 ownership section; renderer registration/readiness remains separate from exact document preparation.

### WO-010.1 desktop font ownership

[`presentation/document_font.rs`](../../../apps/scriptcraft/src/presentation/document_font.rs) remains the app-private `DocumentFontStore` facade and preserves `install()` for startup. It delegates bundled Courier Prime installation to [`presentation/bundled_font_startup.rs`](../../../apps/scriptcraft/src/presentation/bundled_font_startup.rs), exact request/family/style/scalar preparation, host-catalog generation and invalidation, metrics, resolved identity, fallback metadata, and prepared caching to [`presentation/document_font_preparation.rs`](../../../apps/scriptcraft/src/presentation/document_font_preparation.rs), and egui face queueing plus activation/readiness to [`presentation/renderer_font_registration.rs`](../../../apps/scriptcraft/src/presentation/renderer_font_registration.rs). [`presentation/host_font_catalog.rs`](../../../apps/scriptcraft/src/presentation/host_font_catalog.rs) remains the one bounded app-only host-discovery authority; no second catalog or environment owner is introduced.

[`app/startup.rs`](../../../apps/scriptcraft/src/app/startup.rs) retains the existing install call; [`app/render.rs`](../../../apps/scriptcraft/src/app/render.rs) prepares the transient environment for resolved layout, and [`views/script/frame.rs`](../../../apps/scriptcraft/src/views/script/frame.rs) waits for renderer activation before painting. [`documents/output.rs`](../../../apps/scriptcraft/src/documents/output.rs) continues to obtain the same prepared environment for PDF/Print. Declared families remain document data; resolved face identity/metrics and renderer bindings remain transient. The split does not change family policy, scalar/metric bounds, fallback, cache invalidation, or output behavior.

This policy does not establish rendered behavior, native preview, COM behavior, physical delivery, accessibility, or user acceptance. - **Phase 6 command payload and document-control projection:** Command 22 keeps its stable ID and Body surface default while version 2 carries an exact open `element_type` string. Version 1 is read only at the versioned envelope boundary through its old `role` field and its bounded known-spelling-to-FDX-label conversion; v2 accepts/emits `element_type` only. Missing, mixed, duplicate, unknown-field, or version-inappropriate payload forms and unsupported versions fail before dispatch. This command-wire adapter is unrelated to removed document JSON. The ordered current Project registry supplies every toolbar and overflow choice, exact displayed label, and raw Behavior shortcut value; ordinary and overflow presentations share one per-render ordered choice snapshot, focused Body selection is resolved fresh, and no static role list or Action fallback supplies a choice. Enter/Tab guidance consumes the same current Behavior decision as execution. Activation produces the shared open-key typed command and rechecks availability and exact registry membership at execution. Controls are read-only/disposable projections, not document or history state.
- **Phase 6 shortcut grammar and conflict policy:** Parse only the platform source value (`Shortcut` on macOS, `WinShortcut` on Windows); all other platforms have no active document-defined bindings. The bounded parser trims surrounding ASCII whitespace only, preserves the owned source spelling, and treats empty/whitespace-only values as no binding. Plus-separated components accept ASCII case-insensitive Ctrl/Alt/Option/Shift modifiers, without repeated slots, followed by exactly one A–Z, 0–9, supported named editor key, semicolon, or colon. Bare chords imply Command on macOS and Control on Windows; macOS Ctrl adds literal Control, Windows Ctrl is the implied primary, and Windows Shift adds Shift. Alt and Option alias the same slot. Semicolon and colon are logical text chords, with colon canonicalized to Shift+semicolon before exact matching/conflict resolution. A pure resolver reads only the selected platform field from the current ordered definition registry. Injected exact menu reservations (including platform aliases and disabled placeholders) and fixed-editor wildcard key classes disable all affected definitions; all members of any unreserved duplicate group are also disabled. No vector-order winner is selected. Issues contain only a zero-based definition ordinal, stable issue kind, and optional coarse normalized key category; at most 32 are retained and suppressed issues are counted separately. Diagnostics exclude raw shortcut strings, element labels, screenplay text, paths, and source payloads. This parser/resolver does not bind keyboard events; WO-006.6 owns live input, focus/IME, menu ownership, and refresh integration.
- **Phase 6 input ownership and current controls:** One transient current-control snapshot is derived atomically from the current Project and keyed by document identity, session mutation token, platform, and accelerator owner; open/replacement, Type changes, undo/redo, registry replacement, platform changes, or menu-owner changes cannot reuse stale controls. It is not stored in Project, session history, FDX, or layout identity. Dynamic type bindings are Body-only. Existing ownership wins first: the active native/in-window menu accelerator owner and platform-specific dual-dialogue owner, then fixed deletion/navigation and unmodified Enter/Tab behavior, then dynamic named bindings, then navigation fallback. Dynamic named bindings require logical key equality with physical key and exact modifiers. Supported semicolon/colon text chords resolve before ordinary text insertion and an accepted binding is dispatched once, never also inserted. Suppress all dynamic bindings for Title Page focus, unfocused Body, replacement/modal/native-output locks, active IME, or any IME input in the current frame. Fixed-editor wildcard reservations cover Delete/Backspace and navigation keys whose current behavior ignores arbitrary modifiers, plus unmodified Enter/Tab. Exact reserved chords include actual native/in-window menu accelerators (including aliases and disabled placeholders) and macOS Command-Q; an unavailable menu owner does not release its chords. Post one bounded issue summary through the existing diagnostics/status channel when a newly computed issue-bearing projection is installed; do not add a dialog or a per-frame warning.
- **Phase 6 popup and issue ownership:** While an in-window top-level menu popup is open, it retains keyboard routing and editor event dispatch is suspended until dismissal. Shortcut issues are reported through the existing bounded status/diagnostic command channel as count-only summaries; a pending or visible unrelated migration/operation warning is preserved. A clean current projection clears only a stale shortcut summary.

- **Script View and title surface:** Script View allocates every layout page row for exact scroll extent and complete source geometry, while painting only the viewport range plus at most one page of fixed overscan on either side. Actual allocated rectangles and document-Y offsets form the unified presented-page collection used for hit testing, selection, zoom, page status, and caret reveal. Per-frame interaction projections use the layout indexes for the paint range and any conditional reveal target; active selections/carets outside the immediate viewport do not force all-page projection work. Desktop converts semantic positions into screen geometry; `scriptcraft-layout` source maps and canonical scalar boundaries remain authoritative for paint, selection, caret, IME, hit testing, navigation, and reveal. The prepared resolved-font environment is transient and binds measured metrics to the exact bytes and unique egui family registration; paint uses that registration and never changes canonical advances or rewraps. Managed body and TitlePage Content text is dynamically resolved; non-Content title structures remain opaque. Title Page is a separate native viewport in the same process, Project, session, dispatcher, and history; its tracker, selection, and zoom are transient surface state, not a second document/session, and its renderer continues to resolve Page mode. Ordinary collapsed Title Page caret geometry uses the same resolution and paint path as Body, including focus, blink, and clipping; projection remains limited to the existing caret page rather than expanding to all pages.
- **Three-mode Script View presentation:** One root application field owns transient Body mode (`Page`, `Normal`, or `Speed`) and defaults to Page for each new window. Title Page resolves Page at the shared renderer boundary and does not read or inherit Body mode. All modes use the same complete `scriptcraft-layout` page composition and fixed centered paper-width column. Page uses the workspace backdrop and existing per-page paper fill/border. Normal uses the active paper color across the Script View backdrop, omits per-page fill/border, retains full paper-height rectangles and existing explicit plus implicit inter-page spacing, and paints a 1.0-logical-point text-colored rule across the imaginary full-paper bottom edge only when another page follows. Speed uses the paper backdrop without page fill, border, or rule; each row uses that page's printable content height and content-top document-Y offset, with zero explicit gap and zero scoped vertical item spacing between rows. It removes only configured top/bottom paper margins and preserves unused space within printable bounds; it does not repaginate, reflow, merge pages, or alter layout pagination/output.
- **Central editor scrollbar presentation:** Root Body and Title Page central composition use the shared local wrapper, which saves and restores the complete scroll style and visuals around its application of the script-workspace-owned editor-scrollbar palette. The palette has distinct track, resting-handle, hovered-handle, and dragged-handle roles, initially derived from status background, status foreground, and directional hovered foreground (used initially for both hovered and dragged handles). Both stock width fields are 10 points, so the background track remains 10 logical points thick at rest and direct hover rather than expanding. Stock background opacity remains 1.0 in dormant, active, and interact states; stock handle opacity is 0.0 in those states solely to suppress the built-in handle shape. The app paints the sole visible handle directly with the existing palette, fully opaque and centered at 8 points inside the 10-point track. Its custom geometry mirrors stock content/offset/minimum-length calculations and stock visibility-factor IDs, scales cross-axis thickness during visibility animation, and clamps the maximum 4-point corner radius to half the smaller handle dimension. The existing stock scrollbar response is read through its stable scroll-output/axis identity for pressed/dragged and direct-custom-handle hover colors; no second widget or input target is registered. Floating allocation remains zero. During ordinary editing, the editor interaction rectangle excludes the 10-point right and/or bottom strip only when the corresponding content overflows; modal element-window behavior remains unchanged. Actual clipping and page-geometry rectangles remain unchanged. Future views in the same central region inherit this policy through the composition boundary; dropdowns, menus, and unrelated egui areas do not. This wrapper is desktop presentation and does not change page width, canonical layout, zoom, or viewport geometry.
- **Dynamic dropdown sizing:** The normal and overflow Elements presentations share per-render metrics derived from current choices and UI style: desired inner content height includes every current row and inter-row gap; the main ComboBox maximum outer height adds popup margins and is capped by the viewport; minimum popup content width is the larger of the closed-control width and the widest current label plus existing horizontal option padding. The closed toolbar allocation and truncation remain unchanged, and constrained viewports retain scrolling. In-window Windows top-level and recursive submenu popups measure required width from the widest rendered row and desired height from all entries, then cap vertical scrolling to the usable inner viewport while shrinking shorter content. Menu activation, keyboard/ownership behavior, disabled placeholders, and native macOS menus remain unchanged.
- **Presented-page coordinate and state boundary:** Each desktop presented page couples its allocated viewport rectangle with its unscaled document-Y offset. The shared forward/inverse Y conversion is `rect.top + (document_y - offset) * scale` and `offset + (screen_y - rect.top) / scale`. Fixed/projected text, selection, decorations, caret, IME, dual-dialogue boundaries, pointer hit testing, clipping, culling, and reveal use that same conversion; published rectangles and offsets drive visible-page status and full-document-local viewport-center capture. Zoom and mode-transition prepaint prediction use the same per-page height, offset, and gap policy, including clamping an anchor from a cropped paper margin to the nearest printable edge. A real Body mode change captures the old Body center anchor before changing mode and invalidating Body viewport geometry; same-mode selection does not invalidate geometry. This view state does not enter the editing session, revision, dirty/history state, FDX, fixed layout cache, or PDF/Print/plain-text output and does not change the current zoom value.
- **Input and command ownership:** Keyboard, IME, pointer, menus, toolbar, status controls, and native menu events converge on typed commands and the shared dispatcher. Physical keys, modifiers, focus, coordinates, clipboard objects, and native handles stay at the adapter boundary. Menu accelerators have one resolved backend owner and FIFO dispatch; focused editing input preserves source event order synchronously. Disabled placeholders never acquire hover, focus, keyboard, accessibility, popup, or activation behavior. Editor input commits semantic Positions/Selections through the headless session executor. Panel and native-host consumers share one availability/Dual-Undual-label projection only while the session mutation token, active surface, migration/replacement/native-output gates, title-window open state, and title-viewport unsupported state all match; the token covers content, selections, typing styles, undo, and redo. Every dispatch still recomputes current gates, and only dual-dialogue dispatch resolves its current dual target. macOS native-menu setters run only when complete availability, Script View mode, or the Dual/Undual label changes; native event draining and lifecycle safeguards are independent of that presentation gate. Only the typed incompatible nonempty-join failure requests one best-effort native rejection sound; successful no-ops and unrelated failures remain silent, and the sound does not alter command outcome or session state.
- **Toolbar, status, and menus:** Widgets project current semantic selection and live command availability. Status planning follows surface-visible controls: Body retains five right-hand controls and four gaps; Title Page has four controls and three gaps, with no hidden Focus Mode slot, gap, input, or accessibility presence. The status center owns only Ready/cursor/modifier guidance; operation errors route to a separate privacy-safe Diagnostics disclosure gated per process by exact `--dev`. When disabled, no diagnostics UI/accessibility target is allocated and errors are not redirected. Page status comes from actual presented viewport/page overlap, not caret position. The Sprint Timer selector centers Countdown and Stopwatch radio labels around a named checkbox-semantic switch whose checked state means Stopwatch; label activation selects its mode, while switch activation toggles modes. Pointer and Enter/Space activation, visible focus, and disabled presentation follow timer availability, with no separate timed switch transition. The popup uses one local geometry plan for its toggle, central display, bounded feedback region, and paired fixed action rectangles; the toggle and action rectangles are mode-independent. Idle Countdown edits minutes in the central stage using a framed 128 × 38 logical-point editor with a Minutes caption; running, paused, or completed Countdown and Stopwatch use centered, unboxed readout text in that stage. Static readouts have no pointer target and publish their complete accessible label, and the popup body alone supplies the background. Both idle modes label the primary action Start Sprint and dispatch the existing typed start command. Feedback cannot move the toggle or action tracks; the popup omits a heading, Close button, and top separator. Status-icon toggle, outside release, Escape, and host movement/resize request ordinary dismissal through the typed close command. Zoom, view mode, appearance, focus mode, timer, menu, toolbar, and status state are transient and never enter screenplay data, fixed layout, or exports. The three Script View menu actions are enabled typed commands; in-window checks and native macOS `CheckMenuItem` state are projected from the same Body mode, with exactly one checked. The unrelated static checked placeholder remains separately retained and unchanged. macOS native menus and non-native catalog presentation share command semantics; only the selected backend constructs/owns menu activation.
- **Fonts and theme:** Bundled Courier Prime/Material resources and bounded host font discovery support presentation. The desktop catalog tries Arial, then Helvetica-like candidates, then Liberation Sans/Segoe UI for sans requests; Times New Roman, then Times/Liberation Serif, then Georgia for serif requests. Candidate order is deterministic and resolves Regular, Bold, Italic, and Bold Italic independently. Courier Final Draft, Courier, Courier New, Courier Prime, and monospace resolve to the four bundled Courier Prime faces; unrecognized families and unavailable individual faces use the matching Courier Prime face and remain distinguishable in transient resolution metadata. Candidate reads are capped at 16 MiB each, preparation at 64 MiB, requests at 64 families, and scalar repertoires at 4,096; malformed fonts, unsupported collections/variable containers, missing files, oversized payloads, invalid metrics, and byte-identity collisions fail over to the next candidate or bounded Courier fallback. The parser measures only the exact retained bytes; host paths and document text are excluded from identities/diagnostics. No host discovery or font parsing enters model/layout/export. Theme/palette tokens and native icon axes are app-owned presentation, independent of screenplay typography and shared geometry.
- **Clipboard, viewport, and window state:** Clipboard reads/writes occur only after explicit activation; Cut deletes only after write success and Paste inserts only nonempty successfully read text. Viewport coordinates convert to semantic positions before command dispatch. Scroll, focus, zoom, pinch, appearance, fullscreen requests, imported window restore, and native outer-position/inner-size capture are host-owned; they do not mutate Project/session semantics. Root WindowState is disposable FDX state captured/reconciled only by the native save transaction; window movement/resizing does not alter dirty/revision/history/layout/export state.
- **Native document and output dialogs:** Pickers collect input and dispatch distinct typed direct-path commands. Paths must remain UTF-8 and are not lossily rewritten. Native import/version decisions use typed Continue/Cancel while pending-source ownership and staged import remain with document workflow. Cancellation/failure does not replace the active session or claim semantic success. Native PDF panels return the selected path and a fresh default-on Include Title Page value atomically; unsupported platforms return a deliberate unsupported result without an egui options fallback. macOS Print collects settings/title choice in one native panel, builds from an immutable request-time snapshot only after acceptance, and submits one native operation; reported operation success does not claim spooling or physical delivery. Windows and other unsupported Print paths remain unavailable.
- **Template open disposition:** Startup and independent File → New instantiate the default Screenplay through the public built-in loader. The Open picker admits both FDX and FDXT. A single shared staged-open classifier uses only an ASCII case-insensitive `.fdxt` filename extension to select open-as-new; the root Template attribute does not determine lifecycle, and other extensions retain content-based opening. The disposition is captured once with the pending source and survives non-Version-6 Continue/Cancel. Built-in and external FDXT use the common reader/activation route, retain supported body and TitlePage Content examples as editable content, and install a fresh session with no template path or FDX storage baseline and a separate presentation title: built-ins use `Untitled ` plus catalog display name, external FDXT uses `Untitled ` plus source filename stem with only the final extension removed (default Screenplay remains `Untitled Screenplay`); the temporary `OpenedFdxSource` read baseline is discarded before that activation. Session construction and best-effort selection restoration finish before the app publishes the replacement session together with one persistence disposition: an ordinary saved source has its matching path/baseline pair, while a new template session has neither. Imported WindowState/TextState remain disposable view state, not saved identity. Save on a session without a matching pair routes to the FDX Save As picker; ordinary Save also refuses an FDXT source path defensively, while Save As accepts only FDX. Only verified publication establishes both destination path and baseline. Failed or cancelled opens leave the prior active session unchanged. ## Decisions

- **Sprint Timer popover placement:** The status response rectangle is captured in the active viewport's local coordinates when the popup opens and remains its anchor for the entire open lifetime. A shared helper places the fixed-size popup directly above the icon and paints a rounded, theme-matched body with a seamless bottom notch, safe corner clearance, and body-plus-notch outside geometry. Placement uses the active viewport content bounds, preserves above-icon placement when feasible, and has bounded short-viewport/missing-anchor fallbacks. Root and title-page viewports call the same helper with their own coordinates; no cross-viewport translation is performed.
- **Sprint Timer host lifecycle:** On open, the owning viewport captures optional outer left/top and inner width/height observations. Each popup frame compares known current values with that original snapshot and requests ordinary animated dismissal before painting a detached frame after any known change. Missing observations do not imply movement, and returned values are compared with the original capture. Root and title-page snapshots are distinct transient adapter state; ordinary close completion clears them, while viewport destruction clears them during immediate finalization. Geometry is not persisted to FDX or native saved window state. Cleanup runs once at finalization, preserves running/paused timers, and resets idle/completed presentation state only then.
- **Sprint Timer opening transition:** Opening records a transient egui-time start timestamp and applies a popup-local 140 ms cubic-out scale/fade from the captured icon center to the fixed rest geometry (0.85–1.0 scale, 0.0–1.0 opacity). The egui layer transform owns both paint and input coordinates; popup controls remain inactive until completion, then the transform returns to identity. Repaint is requested only while this opening transition is active, independently of existing timer repaint scheduling. The effect is app-owned, not an operating-system animation, and cannot alter timer/document semantics or global UI scale.
- **Sprint Timer closing transition and teardown:** The typed `ToolsSprintTimerClosePopup` command is a coalesced user-dismissal request, not a cleanup command. The desktop captures current scale/opacity, egui-time origin, fixed rest placement, and icon anchor; disables popup controls; and animates for an initial 120 ms toward scale 0.85 and opacity 0.0. A close during opening starts at that current visual progress. Rest geometry and anchor remain frozen during closing, including after host movement. Desktop-internal animation-completion finalization removes the popup, restores identity transform/opacity, clears transient state, and invokes existing timer cleanup exactly once. Opening/closing repaint is bounded to active transition frames; active/paused timekeeping continues throughout. Reopening after completion starts fresh. Destruction of the owning viewport is the sole immediate-finalization exception because no drawable surface remains; native destruction is never delayed. No reversal, global motion preference, native animation claim, or general animation framework is implied.

- Confine host objects, GUI coordinates, native callbacks, and platform APIs to the desktop adapter boundary.
- Make the command dispatcher the bridge from presentation to semantic actions; keep painting and adapter bookkeeping out of document command state.
