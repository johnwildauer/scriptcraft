# Feature-Area Blueprint: Native Document Lifecycle

> This feature composes bounded FDX interpretation, FDXT open-as-new activation, session replacement, derived scene preparation, and transactional storage around the native project as the durable source.

## Scope and requirements

- **Requirements:** [Native document lifecycle](../../requirements/features/native-document-lifecycle.md); [Screenplay editing](../../requirements/features/screenplay-editing.md) for `AC-WRITING-012.3`.
- **Technical context:** [Technical context](../technical-context.md)
- **Requirements traced:** `REQ-WRITING-LOOP-003`, `REQ-WRITING-LOOP-007`, `REQ-WRITING-LOOP-008`, `REQ-WRITING-LOOP-009`, `REQ-WRITING-LOOP-010`; `AC-WRITING-003.1`–`AC-WRITING-003.8`, `AC-WRITING-003.10`, `AC-WRITING-007.4`, `AC-WRITING-008.1`–`AC-WRITING-008.6`, `AC-WRITING-009.1`–`AC-WRITING-009.4`, `AC-WRITING-010.1`–`AC-WRITING-010.5`.
- **Area summary:** FDX Open stages and validates a source-backed project before replacing the active session; FDXT Open creates fresh unsaved content without making the template writable; in-app FDX and FDXT Open both use the parent dirty-session gate and acknowledged child replacement. Save prepares a detached candidate through the same semantic, preservation, and codec boundaries, then publishes it against a guarded destination and rebases only on success. Root Close and application Quit use the live session’s dirty state and a transient confirmation gate.

## Shared composition

- [Document Model](../components/document-model.md) owns canonical Project values and retained source-preservation state, including the Project composition in [`project.rs`](../../../crates/scriptcraft-model/src/project.rs) and retained source modules under [`preservation/`](../../../crates/scriptcraft-model/src/preservation/). [FDX preservation and storage](../components/fdx-preservation-and-storage.md) assigns bounded decode/encode, version/settings/lineage/root-state projection, and codec diagnostics to FDX; native file access, transactional publication, and successful rebase belong to session storage, not the codec or model.
- [Editing session](../components/editing-session.md) owns edits over model values, live state, dirty/history semantics, and derived refresh; [Command contract](../components/command-contract.md) exposes typed Open/Save and import-resolution activations; [Desktop adapters](../components/desktop-adapters.md) owns picker/modal presentation and process/native coordination; [Layout and pagination](../components/layout-and-pagination.md) consumes effective inputs without modifying native source.

## Capability realization

### Open and safe replacement

- **Requirements:** `REQ-WRITING-LOOP-008`; `AC-WRITING-008.1`–`AC-WRITING-008.5`, `AC-WRITING-012.3`.
- **Composition and flow:** In-app picker selection and direct-path Open for either FDX or FDXT stage the selected path in the parent. Both formats use the same parent dirty-session gate and acknowledged child-replacement lifecycle; FDXT alone gives the child fresh-unsaved activation persistence, with no writable template path or baseline. The parent applies the existing dirty-session decision first: clean proceeds without a prompt; dirty Cancel stops; Save proceeds only when the save succeeds and leaves the session clean; Don’t Save is transient authorization and does not revert or clean the parent session. After that gate, the parent launches one child with a handoff identity and retains a pending replacement record. The child reads a bounded source baseline and stages FDX validation/import independently from the parent's save/dirty continuation. Explicit non-Version-6 input holds the child in a Continue/Cancel migration decision and is not an activation. Continue resumes that staged import; Cancel, validation/import failure, or activation failure is a non-Opened terminal outcome. Only after constructing and installing the replacement editing session does the child emit Opened. The parent accepts only the matching Opened identity and then reuses the one-shot root-Close path. Failure, migration Cancel, channel error, child exit, exit-poll error, and timeout safely clear the parent lock and resume its existing session/title; timeout does not kill or wait for the child, and late acknowledgements cannot authorize closure. An independently completed Save at the earlier gate is not rolled back.
- **Boundary:** The picker and migration UI do not parse FDX or mutate the active document. The selected source is read-only during Open; Don’t Save never writes/reverts it. Pending migration, process spawn, dispatch, and child startup are not Open success. FDXT is never activated as a writable path/baseline. In-app replacement does not apply to Finder, Dock, Windows shell, or other OS-originated opens and introduces no OS ingress behavior.

### macOS Launch Services Open Documents

- **Requirements:** `AC-WRITING-008.6`; workspace criteria `AC-WRITING-005.2d`–`AC-WRITING-005.2f`; [macOS packaging](macos-packaging.md) for bundle eligibility metadata.
- **Composition and flow:** One retained main-thread Open Documents Apple-event target accepts a bare descriptor or a list containing exactly one item. It requests an NSURL through `fileURLValue` on the bare or sole-item descriptor, and proceeds only if the resulting URL is local and has a valid native filesystem path that is nonempty UTF-8 and accepted by `DocumentPath`. The adapter does not require the descriptor type to equal `typeFileURL`, use a custom alias importer, or manually coerce aliases, bookmark data, or FSRefs. It enqueues one typed request or fixed error per event into a bounded 16-event FIFO; enqueue and overflow request repaint when a UI context is attached. The callback does not read content, spawn, prompt, access session state, or acknowledge success. The target is registered immediately before eframe startup; a retained `NSApplicationWillFinishLaunchingNotification` observer re-registers that same target after AppKit setup and before Finder's launch document event. The existing winit delegate is preserved, and no `NSDocumentController` route is installed. The initial slot is finalized at the first root update: absent a command-line document, the first valid request queued before that boundary receives the slot; intake errors do not claim it. Each later valid request launches one ordinary independent child in FIFO order. The existing bounded FDX read/version/migration/activation pipeline remains authoritative; a pending non-Version-6 decision is not activation success or an acknowledgement.
- **Failure ownership and invariants:** A cold open failure leaves the initial instance untitled and presents its ordinary startup failure; intake or independent-launch failure is shown in the receiving instance without changing its document; child read/import/activation failure is shown in that child, which remains independent. OS events never run the in-app dirty gate or replacement transport: they do not prompt, save, revert, acknowledge, close, or terminate a receiver, and do not change its document/path/baseline/title/selection/dirty state or source bytes. One multi-file event is rejected atomically with bounded feedback; separate single-file events remain separate. The extension-fallback declaration indicates Finder eligibility only; it neither proves Finder Open With presentation nor changes a user's selected default, guarantees Dock-drop acceptance, or validates file contents.
- **Boundary:** This is macOS file-URL intake, not a typed in-app Open command, replacement handoff, OS acknowledgement channel, document broker, singleton, or NSDocument integration. Windows-shell and in-window drop behavior are not implied.

### Windows shell positional startup

- **Requirements:** `AC-WRITING-008.7`; [Desktop workspace](desktop-workspace.md) owns the user-facing shell-launch distinction.
- **Composition and flow:** The native argument vector enters through the desktop process boundary and is parsed without joining or reparsing a command string. Exactly one positional native path is an independent source, mutually exclusive with the custom internal document option. Multiple positionals, mixed sources, and positional input with a handoff are rejected before GUI construction with bounded native startup feedback that does not expose the path. A valid positional request fills the new process's initial document slot and converges on the same bounded read-only source acquisition, content-based FDX validation/version decision, import, and session/path/baseline/title activation used by staged startup opening. Activated alone denotes success; a non-Version-6 decision remains pending in that process, Cancel leaves it untitled without being classified as failure, and terminal read/validation/import/activation failure is reported there and leaves it untitled. Source bytes remain unchanged by opening.
- **Failure ownership and invariants:** The shell-created process owns its independent startup and document lifetime. Positional startup has no replacement identity, protocol output, parent pending record, dirty-session gate, replacement lock, or Close continuation. It neither discovers/forwards to an existing process nor uses singleton IPC or a broker. Existing instances—including dirty receivers—retain their document, path, baseline, title, selection, dirty state, editability, and source bytes. Association and filename extension do not validate content. A one-file executable/shortcut drop is only argument-compatible with the same positional route; a combined multi-path launch is rejected as a whole, and separate launches remain independent. No taskbar/taskbar-hover or in-window file-drop route is described.
- **Boundary:** The internal custom-option/handoff route remains owned by in-app acknowledged replacement. Windows runtime path support does not imply package-delivered association registration; Windows and the user own any Open With/default choice for the portable package.

### Built-in catalog, new documents, and FDXT open-as-new

- **Requirements:** `REQ-WRITING-LOOP-003`, `REQ-WRITING-LOOP-007`, `REQ-WRITING-LOOP-008`; `AC-WRITING-003.1`–`003.3`, `003.7`, `AC-WRITING-007.5`, `007.7`, `007.9`, `AC-WRITING-008.1`–`008.7`; workspace `AC-WRITING-005.2`, `005.2d`–`005.2g`, `005.9`, `011.1`, `011.7`; [Title Page Editing](../../requirements/features/title-page-editing.md) and [macOS packaging](macos-packaging.md).
- **Catalog and creation:** One ordered compile-time catalog in `scriptcraft-fdx` contains exactly `screenplay`, `stageplay`, and `dramatists-guild-musical`, with Screenplay as default and stable display metadata. Each selection is instantiated via the common bounded Version 6 reader into a fresh source-backed document, preserving its complete supported body and title-page Content sequences plus the selected document settings. Stageplay and Musical retain their own complete title Content rather than inheriting Screenplay's sequence. The catalog's closed IDs do not close the editable element-type vocabulary.
- **Fresh persistence state:** Startup without a path and File → New use default Screenplay and its example content in a fresh session. A template-backed document is semantically clean initially but has no saved-on-disk claim, native path, or FDX storage conflict baseline; its Project-owned effective DocumentPageLayout comes from the selected template, its project layout identity and session are fresh, its fresh title is `Untitled ` plus the selected built-in catalog display name or, for external FDXT, the source filename stem with only the final extension removed (default Screenplay therefore remains `Untitled Screenplay`), and ordinary Save routes to Save As. Root WindowState/TextState from a template is disposable imported view state, not a storage baseline or semantic layout identity. Save As publishes ordinary FDX only and cannot overwrite built-in or external FDXT bytes.
- **Shared FDXT routing:** Picker, positional startup, acknowledged in-app replacement, macOS Open Documents, and Windows shell ingress converge on one staged-open disposition selected only by ASCII case-insensitive `.fdxt` filename extension. Do not infer open-as-new from `Template=Yes`, do not restrict ordinary content-detected opening by other extensions, and do not normalize the path string. Compute the disposition once at staged-open entry and retain it with the pending source across non-Version-6 Continue/Cancel; only successful activation is success. Fresh-unsaved activation discards the staging `OpenedFdxSource` read baseline, leaves the native path/baseline pair absent, and carries presentation-only fresh-title identity separately: built-ins use `Untitled ` plus catalog display name, while external FDXT uses `Untitled ` plus source filename stem with only the final extension removed; the selected source is never a writable target. No runtime repository-relative resource or runtime template directory is introduced.
- **Ordinary output and landed UI:** Ordinary FDX output removes only direct-root unqualified `Template` attributes from detached writer output; source bytes/live retained source remain unchanged, namespaced and descendant lookalikes/unrelated root values survive, surviving attribute order is retained, and `Template=No` is not inserted. The read-only Elements inspector shows the live ordered definition registry; its three-entry selector supports distinct Apply and New modes. New from Template launches an independent child through the common loader with complete selected-template body/title Content and settings, leaving the parent untouched and the child untitled, unsaved, and without a writable template path or baseline. Apply uses only normalized target definitions/settings: exact keys survive, unmatched managed Body and typed title Content keys map to target Action, and type-less title Content and opaque lookalikes remain unchanged. Current text/runs, identities, ordering, direct formatting, attachments, opaque source, unrelated settings, and inactive dual membership are preserved. Apply is one ordinary undoable edit; it does not open a picker, replace the session, save, or change the native path/storage baseline. The UI adds no second catalog, loader, executor, or semantic authority.
- **Evidence boundary:** Lifecycle, nonoverwrite, save/reopen, selector, and Apply behavior remain distinct product contracts. The user selects any build, manual, native, packaging, or interoperability evidence; source and prepared scenarios are not execution evidence or acceptance.

### Durable save, identity, and derived scene content

- **Requirements:** `REQ-WRITING-LOOP-003`, `REQ-WRITING-LOOP-009`; `AC-WRITING-003.1`–`AC-WRITING-003.7`, `AC-WRITING-009.1`–`AC-WRITING-009.4`.
- **Composition and flow:** Save/Save As commands resolve a destination in the desktop adapter and enter storage with the session's current source baseline. Session preparation refreshes safely supported derived scene/cast data on a detached candidate. Preservation reconciliation maintains managed and opaque source ownership and identities; the codec serializes Version 6 and independently re-reads/compares the candidate. Storage checks destination safety and conflicts before atomic publication. A receipt then updates the session's save baseline and clean project to the published candidate. Any failed stage reports a bounded failure and leaves the old destination, path/baseline, selection, and live semantic state unchanged.
- **Automatic live derived correction:** A successful automatic correction that changes the project and completes without deferral advances the session clean baseline only if the session was clean immediately before that correction. A previously dirty session retains its old clean baseline and all user edits. Unchanged, failed, deferred, and merely attempted refreshes do not rebaseline. This session clean baseline is separate from the FDX storage conflict baseline; automatic correction leaves that conflict baseline and source-preservation rules unchanged.
- **Boundary:** A safe-stop for unsupported derived data is not a successful storage failure and does not silently discard that source. Actual validation, serialization, re-read, conflict, and publication failures remain failures.

Effective PageLayout is Project data and participates in semantic equality, dirty/history/save/reopen comparison. The session's layout inputs are a derived read-only snapshot and resynchronize from the matching Project after undo/redo, replacement, and successful save rebase. Absent source uses the whole standard default; malformed fields and combined invalid geometry use documented field-local/combined fallbacks, while unsupported DocumentLeading stays Unsupported. Existing retained PageLayout/original bytes are not normalized during ordinary output. Preservation-free output emits effective PageLayout; source-backed output synthesizes only when missing on a detached candidate, between Content and WindowState, then verifies effective reread values. Apply Template excludes PageLayout and leaves current effective/retained values unchanged. No ad hoc mutation or command is provided; future changes require an additive typed command/patch and one atomic session/FDX candidate.

### Root Close and application Quit

- **Requirements:** `REQ-WRITING-LOOP-010`; `AC-WRITING-010.1`–`AC-WRITING-010.5`.
- **Composition and flow:** The root update observes native root-close requests and supplies the live `EditingSession::dirty()` value to a root-close coordinator. Clean requests are allowed directly. A dirty unauthorized request is cancelled before the synchronous native prompt adapter is called. The prompt returns a typed Save, Don’t Save, or Cancel choice and performs no session, save, close, or filesystem work itself. Save calls the existing save path and produces a typed `Saved`, `Cancelled`, or `Failed` outcome; only `Saved` together with a clean live session can arm continuation. Don’t Save arms transient in-memory authorization without reverting or marking the session clean. A confirmed choice reissues root Close; authorization is consumed at the next root update and expires if no close request arrives there. Cancellation or failure leaves the root open.
- **Boundary:** This coordinator protects the implemented root Close/Quit lifecycle; it does not claim that arbitrary forced process termination can be cancelled. It does not add a replacement-Open handshake or change independent Open behavior.

### Opaque FDX source and paragraph owner lifetimes

- **Requirements:** `AC-WRITING-003.1`, `AC-WRITING-003.9`, `AC-WRITING-007.2`, `AC-WRITING-007.9`, `AC-WRITING-007.10`, `AC-WRITING-013.3`, `AC-WRITING-013.11`.
- **Composition and flow:** The shared codec classifier uses exact expanded names and ancestry to distinguish supported managed projections, recognized attachments, typed identity contexts, structural containers, generic opaque source, and invalid/unsafe Open input. Safe unknown nodes and attributes default to opaque retention, and opaque ancestry prevents descendants named Paragraph, Text, DualDialogue, or Image from acquiring typed semantics. After Open, the canonical project owns legal editing; current stable semantic owners drive deterministic source projection, including rebuilding affected Text nodes and regenerating missing managed occurrences where source containers/identity allocation permit. Opaque ID-like values remain raw and reserved for collision avoidance, not edit permissions. Opaque source remains out of semantics, layout, PDF, plain text, and supported exports.
- **Writer and storage gates:** Direct writing and Save/Save As/reopen retain unaffected ordered opaque source and surviving-owner data under normalized structural equivalence, not byte identity. Canonical text/run edits regenerate only affected Text projection; unrepresentable opaque inline descendants within that occurrence are discarded, while unaffected source remains. Save compares output to current intended semantics/projection and preserves strict unrelated-root/board and storage gates; it does not compare mutable paragraph references or original paragraph topology as an immutable permission baseline.
- **Owner lifecycle:** Generic opaque children and arbitrary unknown paragraph attributes, including Bookmark, remain attached to body/title/member/outer owners during ordinary edits. Split is left-biased and copies no opaque data or unknown attributes to the new right owner. Join retains only survivor-owned data; removed-owner data disappears with its owner. Whole-owner deletion removes the subtree and attributes without a graveyard. Dual member data follows member nodes through wrap/unwrap; outer data follows the wrapper and is removed with it on unwrap, never transferred to members. Undo/redo restores exact prior source. Existing `UserParagraphData` and supported `Alts`/spell-check semantics remain separate recognized attachment contracts, not the only opaque cases.
- **Boundary:** Safe opaque retention does not interpret unsupported schemas, expose Bookmark/ScriptNote semantics, promise byte-identical XML, or promise universal FDX compatibility. Malformed/hostile input, resource limits, invalid required Open structure, current semantic/projection defects, required unrelated board-reference failures, output reread mismatch, destination conflicts, and publication failures remain strict. Source-backed and source-less documents share legal editing behavior. Required FDX Content containers and bounded source identity/anchor allocation are unresolved operational limits for source-creating legal edits; they must not be represented as proof that imported source can never restrict an edit. Older-version consent and root-section loss behavior are unchanged.

## Decisions

- Treat staged replacement and detached save candidates as separate transactions; neither publishes partial work.
- Make the source tree and destination baseline explicit authorities alongside the semantic project.
