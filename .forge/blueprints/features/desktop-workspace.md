# Feature-Area Blueprint: Desktop Workspace

> This feature composes desktop presentation, typed command activation, and shared document capabilities into the runnable writing workspace.

## Scope and requirements

Persistent global preference behavior is specified by [User settings requirements](../../requirements/features/user-settings.md) and the [User Settings component blueprint](../components/user-settings.md), with requirement IDs `REQ-WRITING-LOOP-013` and `AC-WRITING-013.1`–`AC-WRITING-013.6b`.

- **Requirements:** [Desktop workspace](../../requirements/features/desktop-workspace.md); [Page layout](../../requirements/features/page-layout.md) owns `AC-WRITING-002.15` and `AC-WRITING-006.5`–`AC-WRITING-006.11`; [Screenplay editing command boundary](../../requirements/features/screenplay-editing.md)
- **Technical context:** [Technical context](../technical-context.md)
- **Requirements traced:** `REQ-WRITING-LOOP-002`, `REQ-WRITING-LOOP-005`, `REQ-WRITING-LOOP-006`, `REQ-WRITING-LOOP-010`, `REQ-WRITING-LOOP-011`, `REQ-WRITING-LOOP-012`; `AC-WRITING-002.15`, `AC-WRITING-005.1`–`AC-WRITING-005.9` including `.2d`–`.2g`, `AC-WRITING-006.1`–`AC-WRITING-006.13`, `AC-WRITING-010.1`–`AC-WRITING-010.5`, `AC-WRITING-011.1`–`AC-WRITING-011.10`, `AC-WRITING-012.1`–`AC-WRITING-012.8`.
- **Area summary:** Toolbar, menus, keyboard, editor surface, and status controls are projections and activation sources over one session. Every enabled ScriptCraft-owned user action enters a stable typed command path where applicable; the workspace never becomes a second owner of document semantics.

## Shared composition

- [ScriptCraft Desktop](../containers/scriptcraft-desktop.md) owns the runnable process and window coordination.
- [Document Model](../components/document-model.md) owns canonical document values, including Project composition in [`project.rs`](../../../crates/scriptcraft-model/src/project.rs), ordered element definitions, and Body values in [`element.rs`](../../../crates/scriptcraft-model/src/element.rs); [Editing session](../components/editing-session.md) owns editing/history and native storage; [FDX preservation and storage](../components/fdx-preservation-and-storage.md) composes model-owned retained source, FDX codec, and session publication. [Layout and pagination](../components/layout-and-pagination.md) supplies complete geometry; [Exports and print](exports-and-print.md) documents bounded reusable output and Print composition; [Command contract](../components/command-contract.md) owns shared typed activations and headless editing execution. [Desktop adapters](../components/desktop-adapters.md) owns Script View, toolbar, status, menus, theme, focus, and host integrations.

## Persistent global settings composition

The desktop app's private settings module owns only the app-wide theme choice and stable default-template ID; it adds no package/internal edge and does not move globals into Project, EditingSession, FDX, layout, command wire, or export. Startup loads before first rendered content and projects appearance through existing app/theme state. Ordinary new-document behavior uses the saved default with a non-mutating Screenplay fallback; explicit New-from-Template selection and supplied document paths retain precedence. New selector mode initializes from the effective saved default, Apply retains Screenplay, and only successful child spawn persists the New-from-Template selection. Recovery, atomic debounced persistence, reset, no shutdown flush, and independent-process boundaries are owned by the linked requirements/component documents.

This composition supersedes the Appearance portion of the transient-state description under “Workspace status and transient view state” below: the applied UI state remains per-process presentation, but its selected global preference persists separately. It also supersedes Screenplay-only ordinary-startup/File-New wording and any selector-initial-value wording elsewhere in this blueprint: Apply starts at Screenplay, while New-document mode starts at the effective saved default. Unrelated workspace and lifecycle contracts remain unchanged.

## Capability realization

### Controls and command flow

- **Requirements:** `REQ-WRITING-LOOP-005`, `REQ-WRITING-LOOP-011`, `REQ-WRITING-LOOP-012`; `AC-WRITING-005.1`–`AC-WRITING-005.9`, `AC-WRITING-011.1`–`AC-WRITING-011.7`, `AC-WRITING-011.10`–`.11`, `AC-WRITING-012.1`–`AC-WRITING-012.4`, `AC-WRITING-012.7`–`AC-WRITING-012.8`.
- **Composition and flow:** Shared menu catalogs, native menu events, toolbar actions, editor shortcuts, and pointer actions produce typed commands with origins. Toolbar choices, status guidance, and platform shortcut bindings project the current ordered definitions and resolved Behavior. One application dispatcher rechecks availability, routes semantic actions through the headless executor, and bridges host effects to adapters. Picker requests only gather a path; their accepted result dispatches a separate direct-path command. Menu and toolbar state reflect the live application/session without owning project mutation. The Show/Hide toolbar item opens a one-action dynamic dropdown in the main and overflow presentations; View > Document supplies the same Show/Hide action on primary+J (Command+J on macOS, Ctrl+J on Windows). Both dispatch command 60, `view.invisibles.toggle`, which toggles only the surface active at execution time. Independent Body/Title visibility flags and the action label are transient desktop projections; availability gates remain authoritative.
- **Dynamic popup sizing:** Elements popup metrics are transient and derived per render from the current ordered definitions and UI style. The normal and overflow presentations use the same row-content height and longest-label-plus-existing-padding width policy; the main popup's maximum outer height includes popup margins. The closed toolbar allocation and truncation remain unchanged, and constrained viewports retain bounded scrolling. In-window Windows top-level and nested menus size from their widest row and all entry heights, using viewport-capped vertical scrolling only when needed. These dimensions are not document/session state; native macOS menu ownership, command routing, and document lifecycle are unchanged.
- **Boundary:** Disabled placeholders never produce a command. Menu/native accelerator ownership is singular; queued menu activations preserve order, while focused text and editor input remain in source event order. Host effect routing is not itself proof that an external operation succeeded.

### Elements, template selection, and document activation

- **Requirements:** `AC-WRITING-005.1`, `AC-WRITING-005.9`, `AC-WRITING-011.1`, `AC-WRITING-011.7`; [Native document lifecycle](native-document-lifecycle.md) owns template creation, FDXT disposition, and Apply semantics.
- **Composition and flow:** Format → Elements and its primary+E accelerator use the shared typed command path. The Elements window is the stable `scriptcraft-elements-inspector` native immediate viewport, titled Elements, with a 640 × 480 logical-point default and 520 × 360 minimum; it projects the live Project registry in exact order as a selectable, independently scrolling listbox, initially selecting the first key and reconciling exact-key selection against registry changes. The selected definition alone appears in read-only Basic/Font/Paragraph tabs. Basic covers Start new page, PaginateAs, active-platform shortcut, Return/Tab targets, and useful Outline values; Font covers declared family, point size, explicit/theme-default color, and active styles; Paragraph covers alignment, spacing, leading, point-valued space-before, and inch-valued indents. Direct paragraph/run overrides and host-face substitutions are not presented as definition values. Apply a Template remains bottom-left and Close bottom-right, routed through their existing typed intents. The shared selector is the separate `scriptcraft-elements-template-selector` native immediate viewport, titled Apply a Template or New from Template, with a 560 × 360 default and 480 × 300 minimum. It presents the three exact catalog names in a left listbox and a right Preview pane, initially selecting/focusing Screenplay (`screenplay`) with its exact name and optional resource-derived Description visible immediately. Missing/unusable metadata has no fallback, and Preview images are not rendered. Initial selection and bounded metadata reading do not load a full target or create a candidate; only explicit Apply enters the existing Phase 8 service once through the shared executor. Apply/New readiness is immediate but dispatch still rechecks mode and exact selected-ID/payload equality. Changed/NoOp, bounded failures, and all Apply/New failure guarantees retain their existing semantics. New from Template uses the same Preview presentation in a distinct selector mode: one matching selected built-in launches exactly one independent child through the common loader with complete template-specific content and a fresh presentation title of `Untitled ` plus that built-in catalog display name. It does not replace, save, or prompt on the parent, and the new child has no writable template path or storage baseline.
- **Boundary:** Catalog IDs/names/order/resource bytes remain FDX-owned; the FDX-owned bounded metadata accessor supplies only optional Preview Description presentation text. Definition data and session mutation remain owned by FDX/model/session; windows own only transient row/tab/template selection and presentation. New and Apply are distinct lifecycle operations, and no selector cancellation path performs a full template load or mutates the document.

The two native viewports use `CentralPanel` content, independent per-dialog appearance contexts/native-scale handling, and no editor or embedded fallback. The shared transient presentation constants include 640 × 480 / 520 × 360 Elements sizes, 560 × 360 / 480 × 300 selector sizes, a 176-point list column, 10-point pane gap, zero horizontal and 4-point vertical listbox inner inset, 8-point detail inset, and 23-point rows with zero item gap, 12-point left-aligned labels, and 6 × 1-point padding. Row labels are nonselectable and use the standard arrow cursor; row backgrounds are square-cornered, outline-free full-bleed rectangles, with the keyboard-focus ring kept separate. The selector is the only interactive element surface while open: parent Elements widgets are disabled, and focus activation from the root, Title Page, or parent inspector redirects to the topmost element viewport; an inspector close request is canceled while the selector remains open. Root/Title paint continues while editor/document input, wheel/pinch zoom, timer interaction, and IME commits remain suppressed. Unsupported immediate viewport classes produce bounded value-free feedback and no root-embedded substitute; selector unsupported state preserves a valid inspector. Cancel/Apply/New closes only the selector; Elements close closes its nested selector and inspector. Apply/New failure leaves the selector, selection, error, and document state intact. A permitted root close sends targeted native close commands and clears element state/appearance; canceled dirty close preserves them. Document activation currently clears element state and both per-dialog appearance applications but does not send targeted native Close commands, so the required native viewport cleanup on activation remains an implementation gap; state reset must not be represented as native viewport closure.

### Script View mode selection

- **Requirements:** `AC-WRITING-002.15`; `AC-WRITING-011.1`, `AC-WRITING-011.7`, `AC-WRITING-011.10`.
- **Composition and flow:** The three View > Script entries produce the same typed `view.script-view.set` command with a bounded Normal, Page, or Speed mode payload. The desktop dispatcher updates one transient root Body mode; same-mode selection is a no-op, and a real change captures the Body viewport center before invalidating Body presentation geometry. Neither operation mutates the editing session or selects a mode for the active surface. The in-window menu derives checks from the current Body mode, and the native macOS controller synchronizes checked command items from that same state; exactly one Script View item is checked. The unrelated static checked placeholder remains separately retained and unchanged.
- **Boundary:** Body mode defaults to Page in each new window and is not persisted to FDX. The Title Page child viewport resolves Page even while Body uses Normal or Speed. Menu check state is a projection, not native-menu-owned mode state; all unrelated disabled placeholders retain their disabled behavior.

### Invisibles menu, toolbar, and editor presentation

- **Requirements:** `AC-WRITING-005.1`, `.3`, `AC-WRITING-011.11`, and the editor-overlay criteria in [Screenplay Editing](../../requirements/features/screenplay-editing.md) and [Title Page Editing](../../requirements/features/title-page-editing.md).
- **Composition and flow:** One FDX-owned per-document value stores independent Body/Title visibility and RGB8 InvisiblesColor outside Project and editing history. The View > Document submenu, owned primary+J accelerator, main-toolbar dropdown, and overflow submenu use `view.invisibles.toggle` and derive Show/Hide from the active surface. The desktop dispatcher selects that surface at execution time and requests repaint for root and, when open, Title Page; the toggle does not alter selection, dirty/revision/mutation tokens, or layout caches.
- **Paint boundary:** Script View's shared paint path draws invisibles only for Editor-purpose layouts and gates by the explicit painted surface's flag. It uses canonical projected boundaries for U+0020 dots and paragraph/CR/LF pilcrows, with CRLF represented once. Marks use the imported/fallback-resolved document color, zoom-scaled geometry, and existing per-line clipping; they do not participate in editing interaction or layout. Print-purpose layouts and PDF/plain-text/native-print output do not call this paint overlay. The Title Page toolbar catalog remains unchanged.

### In-app selected-path Open replacement

- **Requirements:** `AC-WRITING-005.2`, `AC-WRITING-005.2a`–`AC-WRITING-005.2c`, `AC-WRITING-005.9`.
- **Composition and flow:** New keeps the independent blank-instance launcher. Open picker acceptance and direct-path Open converge on one staged selected-path continuation; picker cancellation stages nothing. The parent evaluates the current session's dirty state before spawning: a clean session proceeds directly, while a dirty session uses Save / Don’t Save / Cancel, with Save accepted only when it succeeds and leaves the live session clean. Don’t Save does not revert, clean, or write the old session/source. A matching child handoff is retained as one pending record; while it exists, document-changing actions and editor input are unavailable, including across the Body and Title Page surfaces that share the same session. Spawn, command dispatch, and a child's pending non-Version-6 migration decision are not success. Only the child's matching Opened, emitted after successful session activation, authorizes the existing guarded one-shot root Close.
- **Safe resume:** Launch/setup failure, child failure/cancellation, channel failure, child exit regardless of exit code, exit-poll failure, or timeout clears the pending record and restores the parent's existing session and title (except for a Save already completed at the gate). Timeout does not kill/wait for the child; stale/late events cannot close the resumed parent. Pending migration Continue must end in successful activation before Opened; Cancel or failed conversion resumes the parent.
- **Boundary:** This is exclusively the in-app picker/direct-path Open contract. It does not govern the separate macOS Finder/Dock ingress below; no in-app acknowledgement or close continuation is added to OS requests.

### macOS Finder/Dock Open Documents

- **Requirements:** `AC-WRITING-005.2d`–`AC-WRITING-005.2f`; [Native document lifecycle](native-document-lifecycle.md) owns staged content opening and activation.
- **Composition and flow:** Launch Services supplies host-originated events through one retained main-thread Open Documents Apple-event target, outside the in-app Open dispatcher. The target accepts a bare descriptor or a list containing exactly one item, requests an NSURL through `fileURLValue` on that descriptor, and proceeds only when the result is a local file URL with a valid native path. It is registered immediately before eframe startup; a retained `NSApplicationWillFinishLaunchingNotification` observer re-registers the same target after AppKit setup and before Finder's launch document event, without replacing or mutating winit's delegate. No `NSDocumentController` is used. The adapter does not require the descriptor type to equal `typeFileURL` or use a custom alias importer or manual alias/bookmark/FSRef coercion. If no startup argument owns the initial slot, the first valid request queued before the first root update receives that slot; that first update finalizes availability even if no request is queued. Every later valid request launches one independent child. Separate single-file events retain FIFO order. A multi-file event is rejected in full. The adapter's bounded intake errors and any independent child-startup errors are presented by their owning process.
- **Invariant and boundary:** A resulting URL must be local and its native path must be nonempty UTF-8 accepted by `DocumentPath`; intake does not inspect file contents. OS opens never ask the receiver to save/discard, use the replacement acknowledgement protocol, mutate its document or source bytes, or close/terminate it, including when dirty or in a modal/pending state. Child content-open failures belong to the child; cold failure leaves its initial instance untitled. Finder eligibility from extension metadata, Finder's Open With presentation, a user-selected default handler, Dock-drop acceptance/highlighting, and content validation are separate observations. This does not claim Windows shell associations, in-window drops, singleton behavior, or Launch Services acceptance on a particular macOS installation.

### Windows shell positional startup

- **Requirements:** `AC-WRITING-005.2g`; [Native document lifecycle](native-document-lifecycle.md) owns the staged content and activation outcomes.
- **Composition and flow:** The process entry point consumes the OS argument vector as separate native values. Its parser accepts at most one positional document path, keeps that source distinct from the custom internal `--document-path` option, and rejects multiple or mixed sources before creating the GUI. A positional source cannot carry `--open-handoff`; only internal custom-option child launches participate in the replacement protocol. The validated positional path occupies the requesting process's existing initial startup slot and is consumed on the first root update through staged opening. It does not pass through picker-to-direct-path command dispatch, launch a child, or acknowledge replacement. Spaces and valid Unicode remain part of that single native path. Invalid invocation and unavailable startup presentation are reported through bounded native feedback before GUI creation; document-open terminal failures belong to the requesting process and leave it untitled.
- **Independence and boundary:** Each shell gesture starts an independent process and document session. No existing instance is found, forwarded to, acknowledged, mutated, prompted, saved, closed, or terminated; no singleton or cross-process broker is involved. Existing receiver state and source bytes remain untouched. Runtime acceptance of one positional path does not register an association: the portable Windows package leaves Open With/default selection to Windows and the user. Drag compatibility is limited to one file dropped on the executable or a suitable shortcut when it supplies the same one-path argument. Combined multi-path invocations are rejected in full; separate one-path processes stay independent. Taskbar/taskbar-hover and in-window drops are excluded.

### File Close and application Quit

- **Requirements:** `REQ-WRITING-LOOP-010`; `AC-WRITING-010.1`–`AC-WRITING-010.5`, `AC-WRITING-011.8`–`AC-WRITING-011.9`.
- **Composition and flow:** File Close chooses its target from the active editor surface: Body requests root viewport Close and Title Page closes only its child viewport. Application Quit always requests root Close, including when Title Page is active. All root-close requests converge on the lifecycle coordinator, which allows a clean close directly and cancels a dirty close before asking the native prompt adapter for a decision. Save/Don’t Save/Cancel use the same continuation and clean-save gate for File Close and Quit.
- **Native entry points:** macOS Command-Q is a native application-menu activation for typed `application.quit`; Dock Quit is received as the application Quit Apple event, queued to the UI thread, and dispatched as the same command with Native OS origin. The resulting root Close goes through the same coordinator as other root-close requests.
- **Boundary:** Title Page child closure is not root-document closure. Guarded root Close/Quit does not promise cancellation of arbitrary forced process termination. The separate in-app Open replacement flow does not govern OS-originated opens.

### Workspace status and transient view state

- **Requirements:** `REQ-WRITING-LOOP-006`; `AC-WRITING-006.1`–`AC-WRITING-006.13`.
- **Composition and flow:** Status derives page and cursor guidance from accepted geometry and current editing state; the diagnostic channel is separate and explicitly gated. Zoom, pinch, appearance, Focus Mode, sprint timer, and window actions are transient desktop commands/adapters. The toolbar and status surfaces remain available without placing their state in the screenplay or altering shared pagination.
- **Sprint Timer lifecycle:** Timer state, completion data, the one-shot natural-expiration open request, popup transition state, captured icon/rest geometry, and viewport-local host snapshots belong to transient desktop presentation, not the shared editing session. Natural Countdown expiration creates one open request; Body or Title Page consumes it through the existing status-button opening path with that viewport-local current status-icon anchor and host snapshot. Closed or mid-close popups open once, a stable popup is not restarted, and later deliberate dismissal remains dismissed. Higher-priority Elements/modal/input ownership may defer consumption without clearing the request; Reset, mode/start transitions, completed cleanup, and explicit consumption clear it. If Title Page ownership is unavailable, Body becomes the owner without cross-viewport coordinates. The typed close command requests ordinary dismissal; animation completion performs final cleanup once, while loss of the owning drawable viewport finalizes immediately without delaying native destruction. Running/paused timer ownership remains independent of popup lifetime, and idle/completed reset occurs only at finalization.
- **Boundary:** Timer notifications, fullscreen transitions, native menu presentation, clipboard, and viewport effects remain host-owned. Diagnostic presentation is privacy-safe and cannot control failure-safety behavior.

## Decisions

- Make command dispatch the universal activation boundary for application-owned actions; keep raw framework bookkeeping out of semantic commands.
- Separate model-owned canonical values, session-owned edits/history/storage, FDX codec, layout, export, and commands from app-owned transient per-window controls and native effects.
