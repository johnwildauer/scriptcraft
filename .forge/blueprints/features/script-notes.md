# Feature Blueprint: ScriptNotes

This blueprint describes the production ownership and semantic contracts for ScriptNotes. It is an architecture map, not compilation, persistence, rendered/native behavior, interoperability, or acceptance evidence.

## Semantic model and Body coordinates

`scriptcraft-model` owns ordered ScriptNotes as Project semantics, including equality, validation, history snapshots, dirty state, and save rebase. Each note retains stable and durable identity fields, source/creation order, a half-open flattened Body range, raw Color, title, optional exact Type, author/timestamps, and rich ordered Body paragraphs with canonical runs and direct settings. The read-only Color projection treats absent/empty Color and the exact raw sentinel `#RRRRGGGGBBBB` as theme-default, distinguishes explicit supported palette values (including Black), and classifies every other unsupported nonempty raw source separately. Unsupported spelling remains raw semantic data; theme-default resolves from the active page palette while unsupported presentation falls back to Black, without rewriting the note.

[`body_offsets.rs`](../../../crates/scriptcraft-model/src/body_offsets.rs) is the shared coordinate authority used by ScriptNotes and FDX TextState. It maps Body positions and selections between paragraph-local UTF-8 byte boundaries and flattened UTF-16 code-unit offsets. Adjacent semantic paragraphs contribute one virtual separator; stored CR, LF, and CRLF count as their actual UTF-16 units. Invalid UTF-8 boundaries, surrogate-interior offsets, and out-of-document positions do not map. [`script_notes.rs`](../../../crates/scriptcraft-model/src/script_notes.rs) owns point-capable ranges and the pure replacement rebase rule: deletion/clipping precedes insertion, insertion at/before start shifts both endpoints, insertion inside expands the end, and a fully covered note collapses rather than disappearing.

## Session editing, identity, and history

`scriptcraft-session` owns detached ScriptNote candidates, note selection independent of Body/Title/Beat selection, property and rich-text operations, explicit stable-ID deletion, shared Undo/Redo snapshots, and note-selection save rebase. Semantic changes use one candidate publication boundary; selection-only changes do not create semantic history. The shared Body text/structure primitives and derived Cast List correction rebase note ranges in mutation order. Failed candidates discard Body and note changes together. Range movement and saving do not change DateModified. Explicit deletion is reserved to the note-card Trash command; screenplay edits and collapsed ranges do not delete notes.

Creation derives its range from the current Body selection and supplies generated identities, empty author/title/body, the sentinel raw Color for the default None color, and timestamp values from the command boundary. Opening a note or changing only its Type does not migrate an existing absent/empty Color, and Type-only updates preserve the exact raw Color. Text/property transactions require timestamps supplied to session operations; the command executor does not read the clock. Note paragraphs reuse rich-run normalization and shared effective-run, slicing, caret-attribute, scalar-boundary, and replacement helpers without adopting Beat card selection or geometry.

## FDX projection and transactional storage

`scriptcraft-fdx` owns bounded import, detached candidate finalization, retained-source reconciliation, preservation-free output, and semantic/identity/source verification. Import manages only direct same-namespace ScriptNote children of the first direct root-namespace ScriptNotes container when their single Range maps to ordered valid flattened Body boundaries and managed identity is unambiguous. Supported direct Paragraph/Text data, raw attributes, direct settings, runs, and identities project to the model. Unsupported ranges and ancestry, foreign-namespace lookalikes, later containers, unrelated children, and legacy inline forms remain opaque rather than being clamped into managed notes.

Finalization allocates missing durable numeric note IDs, RefIds, and paragraph IDs on a detached candidate. For generated ScriptNote paragraphs, run defaults are applied before canonical paragraph normalization, so the storage candidate is already canonical and subsequent Session/writer normalization and candidate finalization are idempotent for generated run attributes. The storage candidate and writer/reread therefore compare the same generated run attributes. This ordering does not exempt generated notes from verification: native save continues comparing complete note values and identities and verifying reread/source projection before publication; existing semantic, identity, source-tree, destination, and publication safeguards remain authoritative. Source-backed output reconciles managed notes by durable identity while retaining unrelated source; new notes append in creation order, surviving source notes retain source order, and only explicitly deleted managed notes are removed. Preservation-free output emits a deterministic ScriptNotes container, including when empty. This source contract does not claim error-32 runtime verification or guarantee save/reopen behavior.

## Commands and desktop integration

`scriptcraft-commands` appends eight entries to the existing stable catalog: IDs 76–81 are semantic create, delete, properties, selection, text, and navigation operations; IDs 82–83 are host-only present and dismiss effects. The catalog has 83 entries. Create/property payloads carry optional Color; for property updates, missing means Preserve, the ThemeDefault command-wire value (serialized as `none`) means write the model default sentinel, and existing palette variants mean Explicit. ThemeDefault is not an InlineColor palette entry or a screenplay formatting-menu choice. Existing command IDs 1–83 and command-envelope version 2 remain unchanged. Desktop command dispatch owns menu/context activation, presentation, availability, note input ownership, and output exclusion; session/model semantics remain independent of native viewports.

[`note_overlay.rs`](../../../apps/scriptcraft/src/views/script/note_overlay.rs) projects visible Body-editor marker groups, an independent open-note range highlight, pointer targets, and global Previous/Next ordering. Each marker anchors to the first canonical Body layout baseline of the paragraph containing its range start; notes sharing that paragraph-first baseline group together. Global navigation order is range start, range end, then source/creation order. Successful navigation retains ordinary caret reveal and suppresses only temporary offscreen dismissal until the open note's marker becomes visible. The marker is right-aligned 18 canonical points from the paper edge, baseline-aligned, 12 points normally and 13 on hover; group counts use 7-point Courier and page-paper color. Markers and range highlights use the shared three-state color resolver: theme-default follows active page text color, explicit palette values remain fixed, and unsupported raw source presents as Black. Appearance changes therefore affect theme-default presentation without rewriting note data. The overlay is limited to Body Editor-purpose layouts and does not alter canonical wrapping, pagination, ordinary selection, or export layout.

`scriptcraft-layout` owns measured fixed-card metrics and rich Title/Body layout; app-private `widgets/script_note/` modules own the immediate native viewport, paint, pointer/text input adapters, scroll state, property presentation, and New Type dialog. The card prefers marker-right placement when the complete card fits within monitor/work bounds, with its left origin capped at the root's right edge; it can extend beyond that edge, while left/more-room fallbacks retain full-card screen fitting and monitor-based vertical clamping. Without work bounds, root bounds provide the horizontal screen constraint; without either, horizontal placement remains unbounded. New Type and property-menu placement remain separate. The Color menu presents None first, then Black and the existing twelve colors; None uses the shared no-color circle and checks only for ThemeDefault. Unsupported raw Color leaves None and every explicit row unchecked. Property updates use Preserve/ThemeDefault/Explicit semantics, and Type-only edits preserve exact raw Color. Initial and reset transient creation defaults are theme-default/None; theme-default resolves to active page text color. Explicit colors (including Black) remain fixed, and unsupported nonempty source remains preserved, Black-presented, unchecked, and excluded from new-note defaults. The card is fixed at 296 × 260 logical points and does not scale with screenplay zoom. Note Body layout uses the full fixed Body width without rewriting persisted paragraph indents; measured placeholders share canonical layout geometry, and title truncation is display-only. Color and Type menus are separate below-card native dropdowns in the note focus family. Their rows are frameless, without per-row selected/hover/active border, radius, fill, or focus outline; the popup owns the continuous background and the Type/New Type separator remains. The card and both property-menu native viewports request transparent backgrounds and disabled native shadows; the transparent clear color is scoped to the open note family. App-painted rounded fill/stroke supplies the card edge, and the menu popup retains its rounded outer frame. These are source configuration facts only: host transparency, compositor behavior, and rendered appearance require user-owned native evidence and are not established here. The dialog is a separate fixed 320 × 170 immediate viewport. Document font preparation includes note text and run Font families; disposable note layout caches are presentation state. ScriptNotes do not enter PDF, native print, plain text, Fountain, or screenplay pagination.

## V3 native viewport source-integration contract

ScriptNotes remain off-root: the card and Color/Type menus are separate native viewports, and root-composited notes are not the V3 direction. Root startup enables the renderer's transparent-backbuffer capability; this capability does not make the root visually transparent. The card/menu viewport builders remain transparent and undecorated with native shadows disabled. The note-family clear color is transparent only while that family is open and returns to the ordinary opaque workspace value on dismissal. Child UIs do not add an opaque full-viewport panel, so app-painted rounded frames provide the visible edge; root and other native surfaces retain their ordinary opaque panel paints. wgpu remains the existing default. These source settings do not guarantee alpha support or compositing on a particular host.

Property-menu native dimensions derive from the actual popup style and content, including total popup margin, row heights, gaps, and the Type separator. The popup response's outer rectangle is the reconciliation authority: a differing size schedules one native inner-size update at an ordinary frame boundary, while an identical size issues no repeated no-op resize. Reconciliation retains top-left/below-card placement without recentering. Monitor-height overflow continues to use bounded scrolling. The egui popup shadow is disabled to avoid viewport-edge clipping; rounded fill/stroke and V2 frameless rows remain. An initial size estimate is not authoritative after response measurement.

On Windows only, transition suppression is a best-effort per-window optimization for the exact ScriptNote, ScriptNote Color, and ScriptNote Type viewport titles, after verifying that the resolved HWND belongs to the current process. The adapter applies DWMWA_TRANSITIONS_FORCEDISABLED to each eligible window, never system-wide. Attempts are bounded to once per native-window lifetime and reset when that viewport is recreated. Missing handles and failed calls leave ordinary presentation in place, without foreground-window substitution or a success claim. The existing pinned Windows dependency gains only its Win32_Graphics_Dwm feature; its version and internal package edges do not change. Whether suppression precedes the first visible frame, whether a host honors it, and the actual native animation behavior remain unverified.

These V3 source statements do not change root-attached off-root placement or monitor/work-bound fitting, save/normalization behavior, Color/Type semantics, Title metrics, New Type, Elements, Title Page, non-Windows transition behavior, command IDs 1–83, or envelope version 2.

## Current integration and source-evidence limits

WO-015 through WO-017 record the current source integration. The root content geometry is acquired after the root input closure has ended, avoiding nested root-context input/write acquisition. Note painting waits until the exact prepared font data and family bindings are active; queued font data alone is not treated as readiness. Color and Type property commands are dispatched after immediate viewport composition, and New Type semantic dispatch occurs after its child immediate callback. Current native work-bound adapters and note placement behavior remain as previously integrated. These are source-structure statements only: the deadlock was not reproduced and native behavior was not observed.

The color contract is a three-state projection shared across model, FDX, and desktop presentation. It does not migrate every Black note and does not guarantee FDX interoperability. The worksheet remains user-owned and unchecked; source inspection is not build, runtime, GUI/native, manual, or acceptance evidence.

## Package, dependency, resource, and test boundaries

ScriptNotes add no package or internal dependency edge. The existing six-library-plus-desktop-app graph, dependency declarations, bundled resources, native-save safeguards, and zero-permanent-test/zero-test-only-fixture policy remain unchanged. No ScriptNotes permanent tests, fixtures, CI/CD, or validation claim are part of this integration. The user selects, performs, and records any evidence.
