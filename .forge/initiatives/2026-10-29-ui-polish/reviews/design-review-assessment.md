# UI Polish — Supplemental Group Assessment

**Review disposition:** Partial, user-directed assessment only. The formal Forge design-review result is [blocked](design-review.md:1); this document does not pass the design gate, approve a work order, or authorize implementation. All five WOs remain `draft`.

The task requested a full-intent and technical-risk assessment beyond the narrow comparison permitted by [the current design-review process](../../../process/03-design-review.md:10). ## Overall scope and integration

The five proposals are coherent as one desktop viewport/status outcome: page-scale and scroll geometry feed a shared status seam, appearance establishes themed page rendering, timer and Focus Mode consume that seam in the requested order, and the final WO reconciles durable documents against validated results. The ordered sequence and sequential ownership of shared desktop files are appropriate; the five scopes are related rather than unrelated features. The proposals do not expand into screenplay schema, fixed print pagination, or core editing.

The design broadly captures the requested behavior: system-based UI scale with a 2.3 fallback only for missing/invalid native scale; fixed-size page presentation with horizontal/vertical scrolling only when page plus exterior buffer exceeds the real inner clip; no fit-to-window shrinking; System/Day/Night/Midnight appearance with dark pages for resolved dark themes; Sprint Timer countdown and stopwatch; native Focus Mode; and right-side order Sprint Timer → Focus Mode → Appearance → zoom. The per-WO dispositions below are alignment assessments, not approvals.

## Warnings and notes

### W1 — The proposed 360-point 100% page is a consequential appearance change

- **Severity:** Warning; human design approval required before execution.
- **Evidence:** Current code defines 360 nominal points times 1.6 ([main.rs](../../../../apps/scriptcraft/src/main.rs:22)); current geometry tests assert 576 points at a wide viewport and shrink to 368 points at 400 points wide ([main.rs tests](../../../../apps/scriptcraft/src/main.rs:3042)). [WO-001](../work-orders/WO-001-scale-page-geometry.md:75) proposes a stable 360 logical points at 100%, independent of window fit. At wide widths this is a 37.5% smaller logical page than the current 576-point baseline; native scale changes physical pixels, not that logical comparison.
- **Assessment/disposition:** The new policy's scale arithmetic itself is internally coherent: valid native scale is used at UI zoom 1.0, missing/invalid scale uses UI zoom 2.3, and `360 × resolved-scale / effective-pixels-per-point` avoids squaring native scale. Tests specify sensible physical expectations. But the exact 360-point baseline is an agent-default, not a user-stated target. Human approval must explicitly accept that visible calibration (or revise it) before implementation; the current responsive-fit and 2.0 fallback clauses in [requirements](../../../requirements/features/screenplay-writing-loop.md:183) and [desktop blueprint](../../../blueprints/containers/scriptcraft-desktop.md:153) must then be reconciled through authorized documents.

### W2 — Scrolling root cause is still a hypothesis, correctly not a claim

- **Severity:** Warning / implementation-measurement requirement.
- **Evidence:** Current page rendering sizes from outer `available.x`, calls [`ScrollArea::both()`](../../../../apps/scriptcraft/src/main.rs:507), sets a minimum width, and lays out leading/trailing space in horizontal rows ([main.rs](../../../../apps/scriptcraft/src/main.rs:517)). egui 0.29.1 computes inner size using prior scrollbar state and an animated bar factor ([scroll_area.rs](../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/egui-0.29.1/src/containers/scroll_area.rs:538)) and later measures content with [`content_ui.min_size()`](../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/egui-0.29.1/src/containers/scroll_area.rs:818). The source therefore supports the need to measure actual inner clip/content/bar behavior, not a claim that row gaps caused a reproduced defect.
- **Assessment/disposition:** [WO-001's instrumentation and multi-frame tests](../work-orders/WO-001-scale-page-geometry.md:75) are the right response. Preserve the causal uncertainty; test reserved/overlay bars and settling behavior using actual returned geometry, as proposed.

### W3 — Platform/runtime capability evidence is limited but honestly bounded in the WOs

- **Severity:** Warning; conditional implementation stops already stated in the affected WOs.
- **Evidence:** ScriptCraft has no direct notification dependency in its manifest ([app manifest](../../../../apps/scriptcraft/Cargo.toml:8)) or lockfile app dependency list ([Cargo.lock](../../../../Cargo.lock:2696)). The locked notification binding is transitive and does not prove a safe usable adapter ([Cargo.lock](../../../../Cargo.lock:2235)). For fullscreen, pinned source maps the command to borderless fullscreen and winit's macOS path calls native AppKit [`toggleFullScreen:`](../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/winit-0.30.13/src/platform_impl/macos/window_delegate.rs:1418); neither source path proves this app's native smoke result ([egui-winit](../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/egui-winit-0.29.1/src/lib.rs:1439)).
- **Assessment/disposition:** WO-003 correctly requires offline adapter feasibility and keeps notification failure best-effort; if no safe supported adapter exists, do not ship a fake success. WO-004 correctly distinguishes backend-reported state from native transition completion and forbids an unsafe/maximize substitute. No API-source inspection, mock, or proposal is evidence that a notification was delivered or that Focus Mode works in the target app.
