## Initial architecture assessment — proposals, not decisions

**Feasibility:** FDX can plausibly be the native wire format while the app keeps a format-independent semantic editing model. It is not safe to replace JSON with a simple model-to-XML rewrite: the present model cannot express the source's formatting, arbitrary title-page structure, opaque data, or all its own persisted profile and identity fields in a verified FDX mapping. Native adoption is conditional on proving safe preservation and an acceptable home for all required ScriptCraft state; otherwise retain JSON as native and offer explicitly bounded FDX import/export, or defer FDX saves. An opaque sidecar or private XML extension may solve some app-specific state but brings portability, missing-sidecar, namespace, and Final Draft rewrite risks; none is proven compatible. Never silently default away existing profile, IDs or metadata during migration.

**Ownership candidate:** A document session owns both (1) the semantic project used by editing/layout and (2) a bounded FDX source representation with source-to-model anchors and an explicit ownership map. Keep one authority for each editable field: managed fields come from the model; untouched unknown source nodes/attributes remain source-owned. Record source format and original bytes/tree independently of the file path, so Save As and later disk changes do not accidentally re-read or replace the preservation baseline. Snapshots/undo and dirty comparisons must account for the necessary preservation state and mappings; clone cost and lifetime need design work. Unknown nodes interleaved among managed paragraphs need stable relative anchors, not a single opaque trailing blob. Internal generated IDs must be distinct and bounded; retain source IDs where safe and define mapping for missing, duplicate or invalid IDs and cross-references. Current split-ID generation checks body IDs only ([code](../../../crates/scriptcraft-core/src/editing.rs#L776-L788)), while project validation requires IDs unique across title page and body ([validation](../../../crates/scriptcraft-core/src/lib.rs#L247-L255)); a future identity strategy must cover both.

**Round-trip options:** A source-preserving token/span tree with targeted patches can retain unmodified lexical bytes, comments, declarations, prefix spelling, attribute order, whitespace and unknown mixed content, but patch boundaries, encoding, nested edits and stable anchors are difficult. A namespace-aware XML tree with ordered children and opaque nodes is easier to reconcile semantically, but parse/reserialize may change lexical form, entity spelling, CDATA, whitespace, prefix/attribute ordering and declarations. Preserve unknown attributes, namespace bindings and ordered children even inside managed paragraphs and text runs; keep namespace context valid when moving fragments. Specify whether a particular feature promises byte identity or only semantic preservation, including the no-edit case; neither approach alone guarantees Final Draft will preserve data on its subsequent save. Reject or open read-only when a construct cannot be safely represented or re-emitted, rather than quietly stripping it.

### Native save, migration and safety

- Detect supported input by validated content and declared format/version, not extension alone; distinguish legacy JSON from FDX and reject mismatches or unsupported variants explicitly. Keep a version-1 JSON reader and fixtures. A recommended migration UX opens JSON without modifying the original, reports fields that cannot be represented exactly, and requires Save As to a new FDX destination; only mark clean and switch the native path/format after a complete successful conversion and replacement. Whether old JSON can continue to save in place or becomes read-only is a product decision; no automatic overwrite or rollback assumption.
- If FDX becomes native, propose `.fdx` for native Save/Save As and a distinct legacy JSON open filter; do not write XML under a JSON extension or vice versa. Decide whether FDX Open is native or import, whether a separate FDX export is useful, and how ambiguous filenames are handled. Exports, including Fountain and PDF, must not change native path or mark a session clean. Update desktop dialogs, diagnostics, save-state logic, and recovery handling together; recovery must include the preservation payload or it cannot safely restore an imported FDX session. Existing JSON recovery artifacts need an explicit compatibility policy, even though recovery is not a durable product promise ([manifest](../../project-manifest.md#L39-L44)).
- Before replacing any destination: validate model and preservation mappings, build complete bounded output, and reject conflicts or unrepresentable content. Write a uniquely created same-directory temporary file, handle write/flush/sync/rename failures and cleanup, and investigate atomic replacement and durability on supported platforms. Detect external modification since open/save and require a conflict decision rather than overwriting someone else's changes. Failed parse, serialization, conflict, write or replacement must retain the previous destination, current session, preservation baseline, native path and dirty state. Save As must not mutate the source. Define symlink, permissions, disk-full and concurrent-save behavior; test it rather than extrapolating from the existing rename-only mock.
- Parse as untrusted XML with a maintained, namespace-aware dependency evaluated for preservation capabilities and security: disable DTD/external entity resolution and network/file access, reject or tightly bound entity expansion, depth, nodes, attributes, text and total bytes, and report typed errors without leaking document content. Handle XML declarations, BOM and encodings deliberately: accept only a documented set with explicit decoding/encoding and byte-preservation implications, or reject unsupported encodings without overwriting. Enforce well-formedness, invalid character rejection, duplicate/invalid identifiers and output escaping. Do not assume UTF-8 merely because this fixture declares it.

### Fountain assessment

Fountain is screenplay-oriented plain text, not this app's existing paginated text export. Candidate support belongs in its own Fountain serialization file, independent of the FDX file and of filesystem atomic-save mechanics. A parser/writer would need a defined Fountain dialect and fixtures: blank-line context and conventional scene-heading/character/transition inference; forced element markers such as `.` for scene headings, `!` for action, `@` for character and `>` for transition; dialogue/parentheticals, title-page key/value lines, inline emphasis and escaping, notes, sections/synopses, page breaks and dual dialogue. Syntax details and edge cases require verification against an authoritative specification and representative implementations before being treated as a contract.

Writer output should use explicit forcing and escaping where necessary so ambiguous uppercase action, punctuation, blank lines, literal marker characters and dialogue boundaries are interpreted as intended. Fountain does not naturally guarantee FDX opaque extensions, stable IDs, arbitrary title-page layout, fonts/page profile, unsupported types or all run attributes. Even when screenplay meaning round-trips, lexical text, ambiguous classification and metadata may not; provide an actionable loss report, avoid claiming a native or lossless round trip, and require explicit export to a separate destination. A future import should similarly expose ambiguity and unsupported content rather than silently asserting exact equivalence. Decide whether initial scope is export-only or also import; neither is implemented or approved here.

#### Proposed conversion contract and mappings

The following are **proposals**, not established FDX facts. Parse to an ordered, source-located Fountain intermediate representation, then convert it into the same semantic document used by FDX deserialization, including a typed preservation layer where needed. Recognized delimiters are syntax, not literal screenplay text; preserve literal punctuation only when escaped or not recognized. Preserve order, Unicode, source text and enough anchors to account for writer data. Generate fresh collision-free project/element IDs across title and body; do not infer FDX IDs or timestamps from Fountain. Use a documented default profile with a warning where meaningful; do not derive page geometry from whitespace. Retain source-specific metadata only if it has a proven native FDX persistence home and edit/undo rules. Otherwise warn and require an explicit choice, retain the original input separately, or block a native save that would falsely promise preservation; a transient attachment is not durable preservation.

#### Parsing, error handling, loss and verification proposals

- Implement an ordered, bounded scanner/state machine: decode a documented text encoding and BOM policy; preserve original line endings/source spans for diagnostics, then handle boneyards and notes, initial title block, line/blank context, explicit page break before synopsis, centered action before forced transition, forced and inferred elements, dialogue state and inline emphasis. This is a candidate precedence, not a claim the prose specifies all conflicts. Decide and test beginning/end-of-file as blank boundaries, escaping of non-emphasis markers, Unicode case and alphanumeric definitions, nested/overlapping delimiters and title-body ambiguity against independent readers. Recognize a marker only when its full context is valid; never remove it merely because it looks special.
- Follow the spec's [error rule](../../../.reference/Syntax%20%E2%80%93%20Fountain.html#L1308-L1317): when in doubt show writer text as Action rather than skipping it; closing syntax normally cannot be sought past a double line break, except a boneyard. An unclosed boneyard is underspecified: propose retaining the entire uncertain remainder as recoverable literal/source data with an actionable warning rather than suppressing it; do not present a guessed interpretation as certain. Apply the same no-drop principle to malformed notes, force markers, title lines, scene numbers, orphan cues and excessive nesting. Bound input bytes, line lengths, elements, spans and output; invalid encoding, invalid native characters or exceeded limits produce typed failure with location and leave session/source untouched, rather than truncation or replacement. Do not claim every ambiguous classification is detectable.
- Warnings should be structured by category, severity, source line/column or model element/range, affected construct, and concrete consequence/fallback; avoid including sensitive content by default. Distinguish parsed-but-unrepresentable data, formatting/style loss, semantic reclassification, lexical normalization, unresolved ambiguity, unsupported FDX payload and fatal unsafe persistence. Report whether retained data is durable, transient or omitted, and require informed confirmation where content or semantics would be lost. Export reports belong out of band, never as Fountain comments or a banner that changes parsing.
- Fountain cannot generally carry native IDs, page profile and layout, arbitrary FDX title-page positioning, headers/footers, revision/tag links, board images, external paths or opaque XML. The [reference's board/image data](../../../.reference/reference2.fdx#L751-L790) illustrates non-text losses. Preserve original FDX and its native source state regardless of export; do not claim semantic or lexical round trip for all constructs. Where a verified Fountain subset is representable, test semantic import → export → import equivalence, not byte identity; separately test FDX → Fountain → model loss reports and avoid claiming that untouched FDX survives that route. For unsupported visible FDX paragraphs, propose explicit plain-text/action or other readable fallback with role-loss warning; for hidden material preserve its nonprinting status or report its omission rather than revealing it in formatted output.
- Place a future independent Fountain parser/writer in a dedicated headless-core module, e.g. [fountain.rs](../../../crates/scriptcraft-core/src/fountain.rs), alongside but independent of the prospective FDX codec and [persistence](../../../crates/scriptcraft-core/src/persistence.rs); convert through the shared semantic model rather than generating or reparsing FDX XML. Keep filesystem dialogs and safe writes outside the codec. Import must leave the Fountain source untouched, create a new dirty/unsaved document and use native Save As; export must leave session state unchanged. Confirm how preservation payload participates in snapshots, undo, recovery and native save before promising retention.
- Create permission-safe local fixtures derived from the spec: its [completed example](../../../.reference/Syntax%20%E2%80%93%20Fountain.html#L1330-L1498), all scene prefixes/numbers and dot versus ellipsis, forced uppercase action, mixed-case/non-Roman cues, extensions, parentheticals and paired dialogue; title aliases, duplicate/unknown keys and multiline formatted values; nested emphasis, literal backslashes and punctuation, malformed/unterminated spans, note and boneyard delimiters, arbitrary outline depths, synopsis versus page-break precedence, centered text and lyrics; action tabs/indent/extra blanks, dialogue and note two-space lines, CRLF/LF/BOM/Unicode and trailing-space transitions. Cover start/end boundaries, marker collisions, orphan elements, limits and invalid encodings. Compare expected semantic structures and warning locations; test deterministic export and independent-reader interpretation, plus generated adversarial/property/fuzz cases ensuring no text disappears.
- Obtain permission-safe, version-identified Final Draft fixtures for populated multi-run styles, inline and standalone Scriptnotes, numbered scenes, actual dual dialogue, lyric conventions, manual page breaks, custom title-page layouts and outline hierarchy; open/save/reopen generated and edited cases in named Final Draft versions. The supplied richer FDX is useful evidence but neither proves these mappings nor grants a general interoperability claim. No such validation or code tests were performed for this research.

#### Preservation, identity and edit dependency policy

1. **Inventory, classify, then act.** At import retain the original source independently of path, with an ordered namespace-aware representation and stable source locations/anchors. Build a dependency graph containing known document, paragraph, scene, board/item/image, character/name, run/range and other references; include nested content and cross-section edges. Check uniqueness and target existence within each observed identifier domain, and distinguish ID definitions from references even when spellings differ. Scan unknown attributes/elements and opaque content for possible links, but do not claim a generic ID scan can discover name-based, positional, implicit, external or undocumented dependencies. Unrecognized structures remain unknown, not independent.
2. **Four disposition classes per section and edit, with evidence:** preservable when its source and all relevant anchors/references remain valid; updateable only when the transformation and references are specified and verified; removable only when demonstrably derived/disposable for the relevant producer/version, with no authored payload or live references; unknown otherwise. Even removal of a proven cache is a change and does not prove Final Draft recreates it. A setting, suggestive name, empty node, page/length field or auto-generation flag alone is insufficient proof. Keep authored and ambiguous data by default; preserve known-independent XML and reject, warn or require an explicit decision for potentially stale data. A Save As or backup protects the original but does not make a broken or misleading output valid.
3. **Identities.** Keep application IDs distinct from foreign document, body, title, nested beat, list-item, board and image IDs, with scoped maps and source provenance; preserve foreign IDs unchanged when possible. Allocate collision-free new IDs across all relevant domains; detect missing, duplicate, invalid or ambiguous foreign IDs before making references or editing, with read-only/safe-stop when meaning cannot be established. Define document-reference and XRef lifecycle, copy/Save As semantics and external references through experiments, not UUID-shaped guesses. Do not recycle deleted IDs or remap a board/image ID without updating every known reference and validating unknown ones. Existing [split](../../../crates/scriptcraft-core/src/editing.rs#L754-L788) generates body-only IDs while [validation](../../../crates/scriptcraft-core/src/lib.rs#L247-L255) checks title and body, and neither covers foreign domains.
4. **Edits and anchors.** Insertion into known text shifts anchored ranges using defined boundary affinity; insertion outside an unknown range may still affect dependent scene/cast metadata. Replacement/deletion adjusts fully understood style and annotation ranges, but overlapping unknown semantics requires an actionable stop or explicit safe resolution. Split retains one original identity, allocates the other, assigns each anchor according to position and requires an explicit policy for scene-level data; merge preserves one identity only after moving/mapping every dependent reference, otherwise stop. Cross-paragraph deletion, reorder, heading/character role changes and scene-boundary changes invalidate affected scene ranges, list generation, page/length candidates and potentially foreign references; never duplicate hidden attachments, infer ownership from current index, or leave dangling links. Deleting an entire anchored scene/board is potentially loss of authored beats and images: warn with specific consequences and require explicit consent and a recoverable original, or safe-stop if output cannot be valid. Consent for deletion is unresolved and must not be presumed.
5. **Runs and transactions.** Preserve ordered text runs, attributes, inline unknown nodes, comments and mixed content; offsets must use a documented representation and map UTF-8 byte boundaries to source ranges and Unicode scalar/grapheme boundaries as appropriate. Escaping ampersands, less-than signs, quotes, line endings, XML-invalid characters, non-ASCII and entity normalization require explicit output rules; preserve lexical bytes only where actually promised. Uppercasing can expand Unicode and existing [editing normalization](../../../crates/scriptcraft-core/src/editing.rs#L684-L741) can change imported text; disable implicit import-time conversion and transform anchors for deliberate edits. [Current replacements](../../../crates/scriptcraft-core/src/editing.rs#L578-L615) and [joins](../../../crates/scriptcraft-core/src/editing.rs#L791-L805) remove elements, while [snapshots](../../../crates/scriptcraft-core/src/editing.rs#L53-L70) and [undo](../../../crates/scriptcraft-core/src/editing.rs#L449-L477) retain only the project and local editing state. Preservation source, graph, mappings, generated state and clean baseline must participate transactionally in edit, undo/redo, recovery and save.
6. **Safe persistence.** Parse as untrusted bounded XML, disable external entities/network/file resolution and avoid resolving the recorded image path; bound aggregate file size, node depth/count and embedded-image sizes without truncation. The current 1 MiB JSON cap is not a justified FDX/image limit ([limits](../../../crates/scriptcraft-core/src/lib.rs#L14-L18), [persistence](../../../crates/scriptcraft-core/src/persistence.rs#L56-L90)); select explicit tested resource budgets. Validate well-formedness, mappings, references and output before replacing a destination; retain session and original on failures, detect external modifications, and use safe Save As/backup where appropriate. Format dispatch, legacy JSON, recovery of source data and atomic replacement need coordinated design; the existing JSON recovery and rename-only failure test do not establish FDX safety ([recovery](../../../crates/scriptcraft-core/src/persistence.rs#L93-L158), [test](../../../crates/scriptcraft-core/src/persistence.rs#L247-L264)).

**Diagnostics proposal.** Report category and severity, location or stable element/section identifier, operation, affected dependency, whether content is authored/derived/unknown and the confidence/evidence, consequence, and available safe action. Distinguish preserved-but-uneditable, stale/unknown dependency, supported automatic update, potentially lossy removal, unsupported XML/type, invalid reference, resource limit and fatal parse/save failure. Give a clear choice among cancel, inspect, save a separate copy or explicitly consent only when valid output can be produced; otherwise safe-stop. Never print screenplay content, image payloads or local paths in routine diagnostics. Report actual loss, not an unsupported claim that another program will regenerate it.

### Module and dependency boundary

Start by considering separate FDX and Fountain modules/files inside the existing headless core, with legacy JSON similarly isolated and persistence responsible for format dispatch and safe filesystem replacement. This meets the requested separation without a premature crate boundary and preserves the existing UI/core dependency direction. A later serialization crate could depend on a smaller semantic-model crate, keeping XML dependencies and optional formats away from editing consumers; extracting it now while model, preservation ownership and mappings are unstable risks churn or a core↔serialization dependency cycle. A codec within core can use an XML library, but this changes the currently dependency-free core; evaluate maintained Rust parsers/writers for lexical preservation, namespaces, bounded resource use, unsafe-code policy, licensing, API and testability rather than assuming a tree serializer is lossless. Avoid implementing an ad hoc XML parser. No particular library or crate split is selected.
