### Warnings

- **TTP-DESIGN-W-001 — Phase and execution-log metadata are stale.** **Severity:** warning. **Evidence:** The plan says the initiative is in `plan` and records only `draft -> plan` ([`toolbar-and-titlebar-polish-v1.md`](../toolbar-and-titlebar-polish-v1.md:5,23)), while the execution log still says `draft` and says no review or approval has occurred ([`execution-log.md`](../execution-log.md:10-19)). The process expects a formal design review after the initiative reaches `review` ([`03-design-review.md`](../../../process/03-design-review.md:5-13)). **Recommendation:** The orchestrator should record the `plan -> review` transition and reconcile the execution-log phase header/result before evaluating the execution gate. **Required next state:** `review`; do not dispatch implementation until the metadata is reconciled and separate human design approval is recorded. This is a recordkeeping/readiness warning in this review, not a finding that makes the intended design impossible to compare.

- **TTP-DESIGN-W-002 — Branch capability remains unverified.** **Severity:** warning. **Evidence:** The plan records a required branch policy but no branch creation or capability evidence ([`toolbar-and-titlebar-polish-v1.md`](../toolbar-and-titlebar-polish-v1.md:15-20)); the manifest records local branch capability as unknown and requires verification before implementation ([`project-manifest.md`](../../../project-manifest.md:61-71)). **Recommendation:** Verify or delegate creation of `dev/2026-10-27-toolbar-and-titlebar-polish` from the recorded base before implementation dispatch. If capability fails, record the explicit reduced-capability fallback and no-branch notice. **Required next state:** `review` until the branch decision is recorded; then `execute` only if the required branch gate or an explicitly authorized fallback is satisfied. This is not a design-alignment blocker because branch creation is a pre-implementation gate.

- **TTP-DESIGN-W-003 — Native smoke remains unavailable and must not become a success claim.** **Severity:** warning. **Evidence:** The plan makes bounded native smoke part of the future validation boundary but states that no validation is currently claimed ([`toolbar-and-titlebar-polish-v1.md`](../toolbar-and-titlebar-polish-v1.md:42-43)); each applicable work order explicitly records native-window evidence as conditional/unavailable rather than substituting headless evidence ([`WO-001-toolbar-geometry-hover-and-elements-width.md`](../work-orders/WO-001-toolbar-geometry-hover-and-elements-width.md:74-79), [`WO-002-custom-title-strip-and-viewport-toggle.md`](../work-orders/WO-002-custom-title-strip-and-viewport-toggle.md:73-78), [`WO-003-toolbar-and-document-cursor-ownership.md`](../work-orders/WO-003-toolbar-and-document-cursor-ownership.md:67-72), [`WO-004-new-document-scene-heading-and-cross-surface-checks.md`](../work-orders/WO-004-new-document-scene-heading-and-cross-surface-checks.md:76-82)). The manifest does not configure native smoke as a hard-stop manual gate ([`project-manifest.md`](../../../project-manifest.md:88-95)). **Recommendation:** Preserve separate unavailable observations for title-strip behavior, hover geometry, cursor rendering, and maximize/restore during validation; do not mark them observed from deterministic tests. **Required next state:** `review` now; future validation may proceed with an honest warning unless project policy is explicitly changed to require native smoke.

- **TTP-DESIGN-W-004 — Platform-bounded restoration needs backend-specific evidence.** **Severity:** warning. **Evidence:** The installed API evidence supports optional maximized/outer-rectangle state and `ViewportCommand::Maximized(bool)`, but the plan explicitly records no universal exact prior-frame restore API ([`toolbar-and-titlebar-polish-v1.md`](../toolbar-and-titlebar-polish-v1.md:115-116,145,151)); [`WO-002-custom-title-strip-and-viewport-toggle.md`](../work-orders/WO-002-custom-title-strip-and-viewport-toggle.md:51-57,61-65) correctly limits capture and fallback behavior. Its acceptance wording is honest about exact restoration only where the platform/backend provides that guarantee ([`WO-002-custom-title-strip-and-viewport-toggle.md`](../work-orders/WO-002-custom-title-strip-and-viewport-toggle.md:76-78)). **Recommendation:** During implementation and validation, identify the OS/backend, record whether `maximized` and `outer_rect` are observable, record command-ignored/unknown-state behavior, and report exact prior-frame restoration only for the tested supported combination. If no safe restoration behavior can be demonstrated on the target backend, retain the bounded fallback rather than inventing an application-owned frame history. **Required next state:** `review` for design; `execute` only after human approval, with WO-002 remaining bounded to observable/native-supported behavior. This is not a hard-stop because the work order expressly permits a no-op/fallback outcome and forbids a false universal claim.
