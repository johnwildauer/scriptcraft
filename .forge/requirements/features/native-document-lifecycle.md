# Requirements Area: Native Document Lifecycle

> This document specifies desired user-facing behavior for a cohesive area. Describe requirements in established-state voice, even when implementation is future work. Group related capabilities into sections and keep stable IDs so each requirement and acceptance criterion remains independently traceable. Do not add lifecycle status, implementation evidence, progress, or a backlog here.

## Area purpose

The native FDX project remains the durable source of screenplay meaning. Open, version handling, derived scene information, save, replacement, and reopen preserve authored content and protect the last valid destination.

## Capability groups

### FDX opening, version handling, and preservation

- **REQ-WRITING-LOOP-008: Native FDX versions and safety.** The system shall open supported FDX projects and FDXT templates safely, create new template-based documents without making template sources writable, and save ordinary native projects as Version 6 without claiming universal Final Draft compatibility.
  - **AC-WRITING-008.1:** An explicit FDX version other than Version 6 requires a Continue/Cancel warning before attempting the Version 6 import. The warning explains that conversion may contain errors or lose data and carries no compatibility guarantee. Older versions import supported title and content while preserving unfamiliar Type values as exact editable keys; ordinary FDX/FDXT import never maps an unfamiliar type to Action or General. FDXT open-as-new disposition is determined once at the shared staged-open boundary from an ASCII case-insensitive `.fdxt` filename extension, not from a root `Template` attribute; other extensions retain existing content-based opening. That disposition remains attached to pending non-Version-6 input through Continue or Cancel. Content or structures that cannot be represented safely produce an incompatibility notice and leave both the active document and source unchanged; partial salvage is not implied.
  - **AC-WRITING-008.2:** Newer explicit versions also receive the warning and an importer attempt; newer-version conversion is not guaranteed. Missing, malformed, or duplicate version information and invalid input fail safely rather than being silently assigned a version.
  - **AC-WRITING-008.3:** Opening never changes the source file. Explicit Save may replace an ordinary FDX source with a Version 6 project, but a built-in or external FDXT source is never a writable target. The temporary read/conflict baseline acquired while staging external FDXT is discarded before fresh-unsaved activation. A template opened as new has no native path or FDX storage conflict baseline; ordinary Save therefore requires Save As to an FDX destination. Save As to a new destination is create-only; replacement of an existing destination is allowed only after explicit consent. An unsafe, unreadable, oversized, or changed destination, or any failed save preparation/publication, leaves the destination and active document unchanged, including path, baseline, and accurate dirty/clean state. External changes are not overwritten, and a competing creator of a previously absent destination is not overwritten. Ordinary FDX output has no direct-root unqualified `Template` attribute; removing it affects only the detached output projection and leaves original bytes, namespaced lookalikes, descendant elements, surviving root-attribute order, opaque non-Content title structures, and unrelated root attributes unchanged. No `Template=No` value is added. No legacy JSON migration or compatibility API is provided.
  - **AC-WRITING-008.4:** Untrusted input is bounded and cannot access external entities, networks, or local image paths. Diagnostics do not reveal screenplay text, image payloads, or unnecessary paths.
  - **AC-WRITING-008.5:** In-app selected-path replacement Open reads the selected source without modifying it. FDX and FDXT are both selectable through the native-document/template picker filter. For a dirty originating session, Don’t Save is memory-only: it neither writes/reverts the source nor clears the live session's dirty state while replacement is pending or if replacement fails. A non-Version-6 child remains pending during Continue/Cancel, and an FDXT open-as-new disposition remains attached to that staged request through either choice; pending, Cancel, and failed conversion are not successful Open outcomes. Only successful activation of the replacement session may produce the matching Opened acknowledgement that authorizes the parent to use its ordinary guarded root-Close continuation. Any launch, read, version, import, activation, channel, child-exit, exit-poll, or timeout outcome other than matching Opened preserves and resumes the originating session and title (apart from any independently successful Save before launch). Timeout does not kill or wait for the child, and late acknowledgements cannot authorize closure. This replacement contract is in-app only and does not add or govern Finder, Dock, Windows shell, or other OS-originated opens.
  - **AC-WRITING-008.6:** macOS Finder/Dock Open Documents requests use a separate ingress and converge on the existing bounded content-read, version, migration, and activation path; FDX and FDXT extension/association metadata is not content validation. An FDXT request activates as fresh unsaved content and never gives the receiving or child process a writable template path/baseline. With no startup document argument, the first valid cold request occupies the new process's initial document slot, while every subsequent request after that slot is allocated opens in its own independent child. OS opens never enter in-app replacement: they do not inspect or change receiver dirty state, prompt, save, acknowledge, close, or terminate the receiver. The receiver's document, path, baseline, title, selection, dirty state, and source bytes remain unchanged. Cold-open failure leaves the initial instance untitled; intake/spawn failure is reported in the receiver, and a content-open failure is reported in its independent child. A bare descriptor or exactly one item in a list is converted through `fileURLValue`; only a resulting local file URL with a valid nonempty UTF-8 native path is accepted. A multi-file event is rejected in full. Separate events retain FIFO order, and bounded intake/overflow errors are fixed and path-free.
  - **AC-WRITING-008.7:** On Windows, a shell-supplied document path is one positional native argument in a newly started process and is mutually exclusive with the custom internal document-path option. More than one positional path, either path source combined with the other, or positional input combined with the replacement handoff is rejected before GUI creation; invalid invocation or startup-presentation errors receive bounded native, path-free feedback. Native argument boundaries preserve spaces and valid Unicode without command-string reconstruction. The positional path occupies that process's initial document request and converges on the existing bounded, read-only source acquisition, content/version decision, import, and activation flow; FDXT is selected by the shared ASCII case-insensitive extension disposition and opens as fresh unsaved content, while association and extension are not content validation. Only completed activation is success. AwaitingMigration is pending and stays in the new process; Continue uses the existing importer, Cancel leaves that process untitled without converting cancellation into failure, and a terminal read, validation, import, or activation failure leaves it untitled with bounded privacy-safe feedback. Opening never rewrites the source. The shell-created process owns its document and lifetime independently: it has no replacement handoff or acknowledgement, does not discover or forward to a singleton/broker, and never prompts, saves, mutates, closes, or terminates an existing instance. Existing receiver content, path, baseline, title, selection, dirty state, editability, and source bytes remain unchanged. A single file dropped on the executable or suitable shortcut is only another one-positional-argument launch; combined multi-path input is rejected in full, while separate processes remain independent. Taskbar/taskbar-hover delivery and in-window drops are not included.

- **REQ-WRITING-LOOP-007: FDX document model.** The system shall preserve supported FDX-owned content and keep screenplay content independent of unrelated production material.
  - Element-type and authored-text editing criteria are maintained in [Screenplay Editing](screenplay-editing.md); title-page criteria are maintained in [Title Page Editing](title-page-editing.md). This area owns the requirement statement and the FDX independence criterion below.
  - **AC-WRITING-007.4:** Beat boards and screenplay content, including outlines and scene beats, are independent: changing one does not change the other. Cross-domain links may be orphaned by import and do not prevent screenplay edits. Board items, images, and their relationships remain preserved where possible; a conflict between preserving authored material and maintaining independence is surfaced rather than silently resolved by deletion.

### Apply Template to an existing document

- **AC-WRITING-008.8 — Settings-only ordinary edit:** Applying a built-in template to an existing session loads it through the common built-in loader and consumes only its normalized ordered element definitions and corresponding winning direct-root `ElementSettings` nodes. Target body, TitlePage, PageLayout, headers/footers, continuation, view/window state, source bytes, identities, path, baseline, and all other target values are excluded. The operation replaces only the current direct-root `ElementSettings` region and the explicitly remapped current Type projections. Exact case-sensitive keys retain their type; every unmatched managed body key (including managed dual members) and every unmatched present typed TitlePage Content key maps to the target's exact Action key. Type-less TitlePage Content paragraphs remain unchanged; direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, other non-Content title structures, and opaque Type-looking descendants are never remapped. Current text, runs, order, stable/foreign IDs, direct formatting, attachments, opaque source, dual containers/members, and all non-definition settings are preserved. The edit publishes through one ordinary undoable session candidate on clean or dirty documents, retains the existing clean baseline and storage target, recomputes dirty state, and has no Open/replacement/activation/save/filesystem effect. A source-backed session supplies the detached settings winners to the generic candidate; a preservation-free session changes only its semantic definitions/types and retains its existing writer behavior without acquiring a source snapshot. A changed candidate advances history, revision, and mutation token once and clears redo; a true no-op publishes nothing, and any planning, source, validation, or publication failure leaves session and storage state unchanged. Selections and typing styles remain attached to the existing owners and offsets. Capabilities, Behavior, derived invalidation, dual activity, layout, and controls use the current registry through their existing mechanisms; Apply does not synchronously correct Cast Lists, SceneProperties, parentheticals, other content, or unwrap dual groups. A headless built-in service is available independently of selector/menu/dialog presentation, which remains a later desktop capability.

### Elements and Apply selector lifecycle

- **AC-WRITING-008.9 — Elements and Apply selector lifecycle:** Format → Elements presents a compact read-only view of every current Project definition in exact registry order; the view has no per-definition edit or mutation affordance. Its Apply a Template selector presents only the ordered Phase 7 built-in catalog, begins without a selection, permits one selection, and disables Apply until one is selected. Opening, selecting, changing selection, Cancel, selector title-close, and selector Escape load no target and create no candidate; Cancel/close/Escape close only the selector and preserve the Elements window when applicable. Explicit Apply passes one typed built-in ID through shared dispatch to the Phase 8 service once, after a dispatch-time check of selector visibility, Apply mode, and selection/payload equality. Changed or NoOp closes only the selector; Changed refreshes current Body/Title, dual, layout/font and generated-control projections through existing authorities, while NoOp claims no mutation. Target-load/extraction/planning/edit failures retain the selector and selected ID and display one bounded value-free error per attempt; failure/cancellation preserve the current session, source, history, dirty state, selection, native path/target and clean baseline. The desktop neither replaces/activates/saves the current document nor adds a second catalog, parser, remap policy, or candidate. Dialog state is transient and contains no document definitions, target, source nodes, candidate, session snapshot, or storage path. New from Template remains a separate optional independent-child operation and stays disabled unless its WO-009.7 separability condition is met; it cannot use Apply's edit path.

- **AC-WRITING-008.10 — New from Template independent child:** File → New from Template opens the shared catalog selector in New-document mode, initially unselected and without opening/replacing the current session. New is disabled until a catalog ID is selected. An enabled activation must still match the current New-document selector mode and selected ID, and launches exactly one independent child using only the stable built-in ID; it does not enter Apply's executor, stage replacement, prompt/save/close the parent, or serialize parent/session/source data into arguments. The child instantiates that ID exactly once through the Phase 7 common built-in reader, retaining complete editable example body/title content and template settings. The child receives a fresh session/layout identity, no native path or FDX baseline, and `Untitled ` plus the selected built-in display name (default Screenplay therefore remains `Untitled Screenplay`), with Save As behavior. The selected-template startup option rejects duplicate, unknown, document-path, and replacement-handoff combinations. Successful spawn closes only the selector; spawn failure keeps the selector and selection with one bounded value-free launch error. Parent project/session/history/selection/dirty/target/baseline/source and the built-in resource remain unchanged. Apply-to-current mode and its Phase 8 transaction invariants are unaffected.

### Durable save, reopen, and safe replacement

- **REQ-WRITING-LOOP-003: Durable native save and reopen.** The system shall let a screenwriter save and reopen a project without losing its last valid version.
  - **AC-WRITING-003.1:** A native save shall contain screenplay meaning, the ordered current document element definitions, retained FDX-owned metadata, paragraph identities, title-page structure, document settings, and supported opaque content. Transient caret, layout, undo history, and editing-session identities are not required content. The Project registry is the semantic authority for complete definitions; each recognized definition has one winning retained ElementSettings projection after save, while later exact-label duplicates remain retained but inert and unanchored. Winning settings are projected in current registry order, not treated as a second editable authority. Removing a definition removes its complete exact-label direct-root settings family when an inert duplicate could otherwise become a new reread winner; case-distinct and foreign-namespace lookalikes remain separate. New native documents use exactly their current ordered definitions, not an appended fixed role catalog. Built-in templates are instantiated through the common reader with all supported example body and TitlePage Content retained as editable content and their document settings preserved. Ordinary FDX output has no direct-root unqualified Template attribute; removal is limited to detached output and preserves original bytes and unrelated root data. Source-backed and preservation-free output emit arbitrary body and TitlePage Content Type keys exactly, including optional Type absence on type-less Content titles, and reread compares the complete ordered definitions and managed keys. Opening and saving preserve source order, authored text (including whitespace), definition order and values, and safe unknown or opaque material; original input bytes remain unchanged by in-memory edits. Exact expanded names and source ancestry determine whether source is managed, a recognized attachment, or generic opaque data; unsupported but bounded and unambiguous source remains opaque rather than being discarded or promoted into screenplay meaning. A field without a safe supported representation is not silently lost. Transient ScriptCraft-only settings are not promised to survive a native save. Cosmetic serialization may be normalized only where it does not alter authored content; this is structural preservation, not byte-identical XML or a blanket compatibility promise.
  - **AC-WRITING-003.2:** A conflict or save/replacement failure preserves the prior valid destination, active document, path, clean baseline, and accurate dirty/clean state. The user receives a document-unchanged failure notice, not a false report of successful save. Status presentation does not introduce a second Clean/Dirty indicator.
  - **AC-WRITING-003.3:** Reopening a successfully saved native project preserves semantic element types and text, ordered definition values, retained FDX-owned metadata, paragraph identities, title-page structure, supported document settings, and retained source content, within the explicit version and independence boundaries. Type values may differ from their pre-candidate values; save/reopen comparison and rebasing preserve selection and identity without requiring the Type label to remain unchanged. Dual source containers preserve ordered member ownership and wrapper provenance whether their current type pattern yields an active two-column projection or an inactive sequential projection. Before first Save As, a new-from-template session may be semantically clean but has no saved-on-disk or FDX conflict baseline. Successful save installs the reread registry/source projection as both the live project and clean baseline, leaves the session clean, and retains ordinary undo/redo behavior against that new baseline. Mismatched ordered definitions or failed identity mapping prevent publication. Transient editing identities may be regenerated; nondefault layout settings and editing policies are not persistence guarantees. Pagination is repeatable for the same effective layout inputs but need not match every FDX layout. Missing supported fields use their defaults and malformed input fails safely. Established paragraph identities remain stable through ordinary edits, Type changes, derived refresh, Save/Save As, and reopen; structural edits affect only the relevant identities, and undo/redo restores the prior editing state. Empty managed paragraphs remain paragraphs without managed text content through repeated save/reopen; clearing and retyping updates their saved text consistently.
  - **AC-WRITING-003.5:** Supported Scene Headings retain generated scene metadata and derived Character membership. A scene's derived character list follows the Character cues up to the next Scene Heading or end, trims surrounding Unicode whitespace, removes a recognized trailing delivery extension, ignores empty results, deduplicates case-insensitively in first-occurrence order, and presents names in uppercase without changing canonical Character text. Retained Character names keep their associated scene-beat text through unrelated additions, removals, reordering, and cue-case changes. Removing a Character removes its derived scene-beat entry; renaming it to a different normalized name creates a new blank entry rather than transferring text by position. Supported metadata is regenerated from canonical content on an owner-local basis. Unsupported metadata on a surviving heading remains opaque and may defer only that heading's derived refresh; the deferral does not reject the screenplay edit or prevent native save. Deleting a heading removes its complete owner subtree and registrations, and recreating it inherits no former generated payload or identity. Supported generated metadata remains associated with its Scene Heading and is preserved on save/reopen.
  - **AC-WRITING-003.6:** Newly created native paragraph identities are unique and stable after they have been established by save/reopen. Imported identities, including non-UUID values, remain unchanged while their owners survive. Ordinary text edits, Type changes, derived scene refresh, Save, Save As, and reopen retain established identities. A Type change does not change the stable identity used to map selection, generated bookkeeping, or dual membership across save rebase. Splitting retains the original identity for the original/left paragraph and assigns a fresh identity to the right paragraph; an authorized explicit structural deletion or join removes the complete removed paragraph owner and its identity, without being vetoed by raw paragraph-target uses in surviving source. Those surviving raw values may remain orphaned. Undo/redo restores exact prior and post-edit project/source snapshots; recreating content allocates a fresh identity with no deleted-owner payload or historical graveyard. Current semantic identity/group invariants and required unrelated board-reference checks remain strict; stale/missing imported owner registrations are repaired or projected from current semantic state rather than acting as edit permissions. Matched derived scene entries retain their identity and text; new or renamed entries receive new identities, and safely removed entries lose their associated derived content. Opaque title-page paragraphs remain preserved as source occurrences, including repeated foreign identifiers.
  - **AC-WRITING-003.7:** A successful Save or Save As updates the native document's current-save record while preserving its existing document identifier and unrelated source data. Save records the session-open time once where applicable; Save As records the corresponding source relationship. A template-based new document has a fresh session and project layout identity, no native path or FDX storage conflict baseline, and is presented as `Untitled ` plus the selected built-in catalog display name or, for external FDXT, the source filename stem with only the final extension removed (default Screenplay therefore remains `Untitled Screenplay`); its initial semantic clean state is session bookkeeping, not a saved-on-disk claim. Ordinary Save therefore routes to Save As, which accepts an FDX destination and cannot overwrite the built-in or external FDXT source. Any preparation, serialization, conflict, or publication failure leaves destination, active document, path, baseline, selection, and dirty state unchanged.
  - **AC-WRITING-003.8:** Imported desktop window geometry is best-effort view state: invalid or incomplete geometry does not prevent opening and does not cause a later unexpected restore. A valid imported size and position may be applied once after activation. Window movement and resizing do not change screenplay meaning, revision, dirty/history state, layout, or PDF output. Save/Save As records current valid window geometry without altering unrelated source data; a failed save publishes neither that update nor other candidate changes.
  - **AC-WRITING-003.9:** Bounded, well-formed FDX elements and attributes not interpreted as managed content remain generic opaque source by default. Safe opaque source is retained under normalized structural equivalence, not byte identity, subject only to the explicit owner-local destructive rules below. Opaque ancestry prevents nested FDX-looking names and ID-like values from acquiring managed meaning; raw IDs remain reserved for collision-safe allocation, and a recognized paragraph ID definition does not create a substring reference. After successful Open, canonical text, ordered runs, formatting, exact paragraph Type keys, title structure, and semantic groups are editing authority. Source topology, old text partitions, foreign IDs, absent/ambiguous anchors or managed occurrences, direct formatting, Alts/UserParagraphData, raw paragraph-target uses, opaque inline nodes, unusual title/dual structure, and generated metadata do not veto a semantically legal edit. Canonical mutation is followed by deterministic current Text/run/Type/structure projection. Rebuild the affected Text occurrence from canonical runs and discard only opaque inline descendants in that changed occurrence that cannot represent the canonical result; preserve unchanged templates, unaffected opaque siblings, surviving-owner attachments, and unrelated source. Clear removes managed Text content but retains unrelated non-Text owner data. Type changes update the current Type while attachments stay opaque on the surviving owner. Join/range replacement retains the semantic survivor and removes consumed owners; split retains source on the left and creates a fresh right owner; deletion removes the complete owner and its registrations. New and recreated owners receive fresh source identity and no deleted-owner payload. Raw references in surviving source may remain orphaned and do not veto editing or Save. Current semantic and generated-projection invariants and strict output reread against current intent remain required; unrelated root/board data, required board references, safe Open limits, storage conflict detection, and atomic publication remain protected. Source-backed and source-less sessions accept identical legal semantic operations. Genuine role/selection/final-element/text/capacity/resource bounds and operational identity or required-container allocation failures remain failures; these container/identity limits are unresolved source-related operational restrictions, not evidence that every legal edit is unrestricted. Malformed or hostile XML, resource limits, invalid required Open structure/version, required-reference failures, current-projection reread mismatch, destination conflict, and failed candidate publication remain bounded failures. Older-version Continue behavior is unchanged.

  - **AC-WRITING-003.10 — Bounded output typography:** PDF and native print consume the same canonical Print composition and positions without output-side rewrapping or repagination. PDF uses bounded nonembedded Base-14 Courier/Helvetica/Times resources, positions displayed scalars at Print-layout offsets, renders absent color as black and supported explicit RGB literally, and provides a bounded privacy-safe report for font-resource substitutions, unsupported scalar substitutions, and unsupported explicit-color fallback. Windows native print captures the prepared project/page/revision and resolved typography environment, requests DirectWrite family/style, and positions each scalar at canonical offsets. Its bounded privacy-safe report identifies Courier New/nearest-family substitutions, unverified DirectWrite face identity, glyph coverage and metric/shaping policy, canonical geometry metric uncertainty, and unsupported explicit-color fallback; absent color is black, supported RGB remains literal, and unsupported explicit color falls back to black with a report. macOS PDF-backed Print carries the PDF report and presents its summary after output/operation preparation. Output success does not establish embedded-font or exact visual parity, universal non-ASCII coverage, Final Draft pagination parity, or physical-printer delivery.

### Derived scene cast lists

Scene and cast semantics in AC-WRITING-003.5–003.6 and REQ-WRITING-LOOP-009 are determined only by exact-label capabilities: Scene Heading identifies scene boundaries, Character identifies cues, and Cast List identifies correctable lists. Arbitrary labels and case variants do not acquire these meanings from spelling, Behavior targets, or PaginateAs. PaginateAs is reserved for layout behavior and cannot make Shot a scene boundary, End of Act a Character cue, or an arbitrary label a Cast List. SceneProperties are read or reconciled only for a current scene-capability heading; a Type change that removes that capability leaves its attachment opaque and unchanged, and restoring the exact base key permits the ordinary derived refresh path to consider it again. Session invalidation evaluates before and after capabilities against each side's own registry, tracks heading order/identity plus Character cue text and owning-scene projections, and falls back to complete invalidation when key resolution or identity/order correspondence is ambiguous. Scoped skipping is limited to an unchanged exact key and registry whose old and new capabilities are neither scene-boundary nor character-cue relevant; registry replacement/remapping keeps complete invalidation. Type changes preserve attachments and authored scene/cast text; established derived refresh or save preflight may make supported corrections later rather than eagerly rewriting content as part of the Type change. Cast List correction retains its existing per-scene safe-stop behavior and never synthesizes a missing list.

Generated-Parenthetical bookkeeping referenced by AC-WRITING-003.6 is transient session state. Rebase derives the old and new owners' Parenthetical capability from their respective current registries and retains a mark only for a mapped owner whose capability remains present and whose canonical text is unchanged `()`; Type identity itself is not owner identity. Owner mapping prefers valid stable identity, then unique source identity, and uses only a unique source-less text occurrence when no source identity exists; it never relies on zip position or unchanged Type. A generic Type change/remap never inserts delimiter text, and removing Parenthetical capability drops the mark without changing authored text. A newly opened session starts without these marks.

- **REQ-WRITING-LOOP-009: Scene cast lists.** Imported Cast List text is preserved as authored input; supported derived cast information is refreshed from screenplay Character cues without changing their canonical casing.
  - **AC-WRITING-009.1:** Direct edits may be corrected on refresh, and Save/Save As shall check and correct supported derived lists before saving. Derived Cast List text is uppercase; canonical Character cues retain their typed casing.
  - **AC-WRITING-009.2:** A scene whose derived source data is unsupported retains that owner-local metadata and cast list unchanged while other supported scenes may update; this deferral never blocks the underlying screenplay edit or an otherwise valid native Save or Save As. A formatted Cast List that cannot be safely corrected without changing its runs retains its text and formatting. A failure to project a legal edit is not converted into a successful deferral.
  - **AC-WRITING-009.3:** After a successful save, the active document and clean baseline match the saved candidate. Failed preparation, conflict, or replacement publishes no derived correction. Refresh, undo/redo, and pending saves use the same deterministic per-scene safe-stop rules. Actual document, validation, preservation, conflict, and storage failures remain failures, not successful deferrals.
  - **AC-WRITING-009.4:** Relevant screenplay changes cause supported derived scene information to refresh without repeatedly changing unchanged content. Edits, undo/redo, successful derived updates, successful saves, and document replacement are reflected in subsequent refresh behavior. Save/Save As always prepare current supported derived information, independent of background refresh timing. A failed update remains pending until relevant content changes; unrelated changes do not repeatedly retry an unchanged failing update. Deferred scenes are reconsidered after relevant changes, while independent scenes may continue to refresh. A successful automatic derived correction that changes the project and completes without deferral advances the session clean baseline only if the session was clean immediately before that correction; a previously dirty session retains its prior clean baseline and all user edits. Unchanged, failed, deferred, and merely attempted refreshes do not rebaseline. Automatic refresh does not alter the FDX storage conflict baseline or source-preservation rules.

### Root Close and application Quit protection

- **REQ-WRITING-LOOP-010: Guarded root-document closure.** The desktop shall protect a dirty root document from an unconfirmed Close or application Quit while allowing ordinary clean closure.
  - **AC-WRITING-010.1:** A clean root-window Close proceeds without an unsaved-changes prompt. An unauthorized Close request for a dirty root session is cancelled before a native Save / Don’t Save / Cancel decision is presented.
  - **AC-WRITING-010.2:** Cancel leaves the root window and live session open. Don’t Save permits the confirmed root Close using transient in-memory authorization only; it does not revert or clear the live session’s dirty state, write the native file, or change its saved baseline before closure.
  - **AC-WRITING-010.3:** Save permits the confirmed root Close only when the save operation reports success and the live session is clean afterward. Picker cancellation, save failure, or a still-dirty session prevents closure. A save failure is visibly reported and preserves the open document and its unsaved changes.
  - **AC-WRITING-010.4:** A confirmed-close authorization applies to at most the next root update’s Close request and expires if that update has no request. It is transient lifecycle state, not document/session state.
  - **AC-WRITING-010.5:** If native prompt presentation is unavailable or returns no recognized choice, the decision fails safe to Cancel; the root window and session remain open.

## Constraints

- Native FDX remains the semantic source of truth; transient view and history state do not replace it.
- Save and replacement failures preserve the last valid native project and active editing state.
- Root Close and application Quit protection does not imply that arbitrary forced process termination can be cancelled.
- Opaque source preservation does not provide ScriptNote display, editing, navigation, definitions management, semantic modeling, or export, and does not provide Bookmark navigation, editing, or semantic modeling.
- This area does not promise universal Final Draft compatibility or byte-identical XML. Native FDX is the durable project format; no legacy JSON codec, state, schema, migration, recovery, continued writing, or special JSON detection exists. JSON input receives ordinary bounded unsupported-input handling, with no migration or recovery offer.
- **NFR-WRITING-001:** Malformed input and operational failures produce bounded errors rather than crashes or project corruption.
- **NFR-WRITING-003:** Native serialization and structural pagination are deterministic for the same semantic content and effective layout inputs.
