# Requirements Area: Screenplay Editing

> This document specifies desired user-facing behavior for a cohesive area. Describe requirements in established-state voice, even when implementation is future work. Group related capabilities into sections and keep stable IDs so each requirement and acceptance criterion remains independently traceable. Do not add lifecycle status, implementation evidence, progress, or a backlog here.

## Area purpose

Writers create and revise semantically meaningful screenplay text with document-defined element behavior, precise selection and navigation, and reversible editing. Keyboard, pointer, clipboard, and formatting interactions preserve the same canonical content and editing rules.

## Capability groups

### Semantic screenplay content and editing

Screenplay elements retain exact, case-sensitive document element types and exact text independently of their visual presentation. Editing operations preserve element order, valid text boundaries, and authored content.

- **REQ-WRITING-LOOP-001: Semantic screenplay editing.** The system shall let a screenwriter create and edit an ordered screenplay whose paragraphs reference exact, open element types owned by the current document, while retaining screenplay meaning.
  - **AC-WRITING-001.1:** A new project shall instantiate the complete default Screenplay template, retaining its editable example body and title-page Content, with a fresh unsaved state. The insertion point shall begin at the start of the initial Scene Heading; creating a project shall not replace the template's example content with an empty-body seed.
  - **AC-WRITING-001.2:** Each element shall retain its exact, case-sensitive document element type and exact canonical text, including casing, spaces, tabs, and indentation, independently of display formatting. Typing, paste, split, join, element-type assignment, Enter/Tab transitions, undo, and redo shall not normalize authored or imported text. All Caps shall affect display only, including when Unicode uppercase changes the number of displayed characters. Opening a project shall not rewrite stored text; source font overrides without All Caps shall display canonical casing.
  - **AC-WRITING-001.3:** Insertion, deletion, split, join, element-type change, undo, and redo shall preserve valid text boundaries and element order. For a collapsed body Delete or Backspace at a paragraph boundary, an empty current element is removed before considering a join; otherwise an empty adjacent element is removed before exact element-type compatibility is considered. Delete removing an empty current element places the caret at offset zero of the next element, or at the previous element's end when there is no next element; Backspace prefers the previous element's end, or offset zero of the next element at the leading edge. Removing an empty adjacent element leaves the caret with the same surviving semantic element. A nonempty collapsed boundary join is permitted only between identical element-type keys, retains the left element's identity and type, and removes the right owner. A type mismatch rejects transactionally without changing content, either selection, history/redo, revision, dirty state, generated state, or dual-dialogue semantics. One final empty body element remains editable; Delete/Backspace on it and ordinary document-edge operations with no removable empty neighbor are silent no-ops. Noncollapsed selection deletion remains range deletion and is not subject to the collapsed-join type gate. Undo/redo restores exact corresponding semantic and source snapshots.
  - **AC-WRITING-001.4:** Element-type transitions shall follow the current document's Behavior definitions and shall be undoable. Definitions and exact type keys are document-owned and open-ended; no fixed editable-type inventory governs these transitions.
  - **AC-WRITING-001.4a:** Enter shall split at the caret and create the next element using the current element definition's ReturnKey target; Tab shall select the current definition's TabKey target and shall never insert a literal tab. Targets resolve by exact, case-sensitive key against the current document's ordered definitions. An absent or unresolved target is a safe consumed no-op. Enter still performs its split when its resolved target is the current type; a same-key Tab assignment that would otherwise only assign that key does not change the screenplay or history. For an ordinary split, the original element retains its exact prefix and identity, a new element of the resolved target type contains the exact suffix, and the caret moves to its beginning; Enter inside Dialogue retains Dialogue, while empty/end-boundary Dialogue uses ReturnKey. Automatic Parenthetical behavior is transient session policy, not document content. When a high-level editing transition or assignment resolves to the exact Parenthetical capability for an empty element, enabled automation creates a transient `()` pair with the caret between its delimiters; generic Type-only changes and definition remapping never generate delimiters. Undo/redo restores generated-pair provenance, it is never saved, and successful content edits invalidate it. Only a still-marked exact `()` Parenthetical may be cleaned up; pasted parentheses remain authored text. With automatic Parenthetical behavior disabled, no pair is generated or specially removed. Only the exact Parenthetical capability activates delimiter rules; repair/advance and generated-pair cleanup resolve the appropriate current Behavior destination before changing text or structure, and the before-opening Enter insertion retains the current Parenthetical key.
  - **AC-WRITING-001.4b:** Up/Down shall move between adjacent wrapped visual lines, retain the preferred horizontal position over repeated successful moves, and clamp to shorter lines and document/page edges. Shift+Up/Down shall extend selection. Horizontal movement, edits, pointer selection, Home/End, element-type changes, undo/redo, or a boundary no-op reset the preferred horizontal position.
  - **AC-WRITING-001.4c:** Any user-facing paragraph-key guidance shall agree with the current Enter/Tab decision, including same-key targets and Parenthetical behavior. Guidance shall not change screenplay content, selection, history, or save state, and shall not imply that a displayed operation is guaranteed to succeed when preservation or document limits prevent it.

  For AC-WRITING-001.4a and AC-WRITING-001.4c, ReturnKey and TabKey are resolved on each decision by exact, case-sensitive lookup in the current document registry. An absent target and a present but unresolved target are distinct data states but both produce a consumed, nonmutating no-op; neither substitutes Action, General, the current type, or a static transition. A resolved same-key Tab is exposed as that exact guidance target but publishes no mutation when it would only reassign the existing key; Enter still splits when ReturnKey resolves to the current key. Read-only guidance and execution use the same decision and exact open-key target; guidance does not independently reconstruct a transition.
  - **AC-WRITING-001.5:** Malformed or out-of-bound input shall produce a bounded error without corrupting the project or editing state.
  - **AC-WRITING-001.6:** When Body invisibles are enabled, the editor paints a small dot at each canonical U+0020 space and a pilcrow at each paragraph ending and imported CR or LF line break; a CRLF pair receives one line-break marker. The marks use the current document's resolved InvisiblesColor and scale with presentation zoom. They are painted from canonical projected boundaries as a noninteractive overlay in every Body presentation mode: they do not alter text, spacing, wrapping, pagination, selection, caret or pointer geometry, IME, clipboard contents, undo/redo, or dirty state. They are editor presentation only and are omitted from PDF, plain-text export, and native print.

### Open element types and authored source content

These screenplay-editing criteria realize the open-type/content portion of [`REQ-WRITING-LOOP-007`](native-document-lifecycle.md), whose requirement statement is owned by Native Document Lifecycle.

For title semantics and Type operations, only paragraphs inside TitlePage Content are managed titles. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, and all other title structures outside Content remain opaque and do not contribute definitions or receive type remapping.

Required-base completion supplies missing structural base definitions from packaged Screenplay data; it does not limit the editable vocabulary. Structural capabilities derive only from exact base labels in the current registry. Arbitrary and case-distinct keys remain editable without inferred capabilities, and PaginateAs does not confer structural identity.

- **AC-WRITING-007.1:** The current document shall own an ordered set of element definitions with exact, case-sensitive labels and complete font, paragraph, Behavior, and Outline values. Every managed typed body or title paragraph shall resolve to exactly one definition; a type-less title paragraph remains valid. A direct body Paragraph with one unique, unqualified, bounded, nonempty Type shall be managed and editable even when its exact label is arbitrary or case-distinct; unfamiliar Type spelling alone shall not make its content opaque or substitute General or Action. Recognized Text alone supplies canonical runs, while unsupported descendants remain opaque at their own child boundary without acquiring guessed semantics. Arbitrary labels remain distinct and editable, and definition order and complete values participate in project equality, dirty state, undo/redo snapshots, validation, and later save comparison. Explicit type assignment and Enter/Tab targets shall use current definitions. Required-base completion is sourced from packaged Screenplay data, not a permanent closed type table. Absent recognized visibility and page-start settings use their defaults; explicit imported values remain preserved. Hidden-text settings shall be honored in print output so hidden notes and outline content are not exposed.
- **AC-WRITING-007.2:** Canonical text, ordered runs, formatting, and exact element-type keys shall be authoritative for legal editing in both newly created and source-backed documents. The generic body Type-only operation uses exact old and new keys, requires the new key to exist in the current definitions, and updates canonical Type, source provenance, and retained Type projection together without changing text, runs, identity, direct formatting, attachments, or opaque payload. The optional-key title operation supports typed-to-typed, typed-to-type-less, and type-less-to-typed changes without changing title content or body selection. Neither operation substitutes General or Action for an unmatched key, applies Behavior, or repairs content. They publish one undoable revision and dirty update; no-ops publish nothing, and failures preserve project/source, history/redo, selections, typing state, and derived state. Generic body Type changes do not enter the structural unwrap retry. A Type change that makes a group's member pattern invalid retains its ordered source membership and wrapper provenance while deactivating the two-column projection; the group remains valid and editable sequentially. Element-type assignment updates the managed Type projection regardless of old Type shape or Alts/UserParagraphData; such attachments remain opaque on the surviving owner. After canonical text mutation, the affected owner's Text projection shall be rebuilt deterministically from current runs. Unchanged matching Text templates and unaffected opaque siblings shall remain in place; opaque inline descendants within a changed Text occurrence that cannot represent the new canonical runs may be discarded at that affected occurrence only. Unknown direct Paragraph children, attributes, attachments, and unrelated source remain owner-bound while the owner survives. Clear removes managed Text content while retaining unrelated non-Text owner data. Undo/redo restores exact semantic and source snapshots. Invalid canonical positions, text/resource limits, and actual source-mapping failures remain transactional; source attachments are not editing vetoes.
- **AC-WRITING-007.10:** Generic opaque children and arbitrary unknown attributes, including Bookmark, remain source-owned by their body paragraph during text, paste, style, alignment, clearing, and type edits; they do not enter screenplay semantics. A split retains opaque source and unknown attributes only on the original/left paragraph; the new right paragraph receives no copied opaque children, Bookmark, or unknown attributes. A join or cross-paragraph deletion retains only the surviving paragraph's own opaque source and attributes; removed-owner data is discarded with its owner. Explicit whole-owner deletion removes the complete owner subtree and its owned identity, anchor, override, and derived/group registrations, without transfer, merge, tombstone, or graveyard. Raw paragraph-ID occurrences in surviving source may remain as orphaned values and do not veto this explicit structural deletion; unrelated surviving source remains intact. Stale typed bindings that exist only for the removed paragraph are cleaned while their raw source occurrences are retained. Ordinary ambiguous inline edits, invalid managed identity mappings, required board-reference failures, and unsafe candidate publication remain transactional failures. Undo/redo restores the exact corresponding source state. Bookmark is not a navigation, editing, or semantic feature.

  The dynamic editing rules for AC-WRITING-001.3–001.4c and AC-WRITING-007.1–007.2 use derived capabilities from the exact current element key. Only the exact base labels Scene Heading, Character, Dialogue, Parenthetical, Transition, and Cast List receive their respective built-in semantics. Arbitrary labels and case variants receive none, regardless of Behavior targets or PaginateAs. PaginateAs is layout data only. Ordinary split retains the current exact key; a nonempty join requires exact key equality, not merely matching capabilities. A Type-only assignment preserves runs, stable and foreign identity, direct formatting, attachments, and opaque source. Automatic Parenthetical insertion/cleanup belongs only to high-level editing transitions or assignment; generic Type replacement and definition remapping never synthesize delimiters. A generated-pair mark is transient and is created only for a pair synthesized by the current session; cleanup requires that mark, exact `()` text, the current Parenthetical capability, and enabled automation. Removing that capability drops the mark without changing text. Delimiter-only forward Delete is special only for a Parenthetical-capability owner with exact `(`, `()`, or `)` text; it removes the later owner to the predecessor end, or keeps a first/only owner empty and changes it through the unique current Dialogue-capability key. After the closing delimiter, Delete follows ordinary character/edge behavior; noncollapsed selections always use ordinary range deletion. Surviving-owner attachments and source remain with that owner. A resolved arbitrary Behavior target remains an ordinary type and gains no capabilities from being a target.

  AC-WRITING-007.2's existing Type-only and transaction guarantees apply when a Type change makes a dual source container inactive: ordered source membership and wrapper provenance remain intact, and the members remain editable in sequential flow. Body split uses the paragraph's exact open key, join requires exact key equality, and Type assignment uses the exact-key source operation without changing owner content. Only explicit dual-dialogue disable unwraps an inactive group; a generic Type change or definition remap never unwraps or deletes it. The earlier transitional rejection wording for a change that would invalidate a group is superseded by this inactive-container rule.

### Apply Template type policy

The Elements inspector is a read-only presentation of the current ordered definitions and their effective values. It observes exact Behavior targets and current-registry resolution, including absent versus unresolved states; it neither supplies fallback semantics nor edits definitions. Applying through the selector replaces only the target's normalized ElementSettings definitions and uses the following established Phase 8 type policy; it preserves current nondefinition settings and never changes screenplay text, runs, order, identity, direct formatting, attachments, or opaque source except for the required Type projection.

Apply Template retains every current managed Body key and every present typed TitlePage Content key that is an exact, case-sensitive key in the target definitions. Each unmatched managed Body key, including a managed member inside a dual source container, and each unmatched typed TitlePage Content key maps to the target's exact Action key. Matching is not trimmed, case-folded, label-similar, or mediated through a closed type list; ordinary import and generic definition replacement do not acquire this fallback policy. Type-less TitlePage Content paragraphs receive no mapping or synthetic Type. Direct TitlePage/Paragraph nodes, Header/Footer data, wrappers, every other out-of-Content title structure, and Type-looking descendants beneath opaque source boundaries remain untouched. Only the required Type projection changes; canonical text, runs, body/title order, identities, direct formatting, attachments, and opaque source remain current-document values. Apply performs no parenthetical generation, Cast List correction, SceneProperties repair, or other content rewrite.

The session's pure planning step operates only on current semantic Body owners in flat order and present typed Content-title keys. It retains exact target matches and emits one explicit mapping per unmatched source key and surface, so every owner sharing that key receives the same target Action result through the generic key-based candidate. It validates that current managed keys resolve in the current registry and that the target has its exact Action definition before returning the ordered target registry and remappings. It does not traverse or mutate retained source, opaque structures, content, dual-group activity, or selections; retained settings replacement and publication are separate later steps.

These rules apply to arbitrary open type keys through the ordinary editing and command paths; command values do not impose a second closed document-type vocabulary. Version-2 editing command payloads carry exact open keys and validate current-registry membership. Historical version-1 role spellings are confined to the private command-wire adapter and do not define document semantics.

### Selection, navigation, input, and history

Pointer and keyboard interactions operate on canonical text positions, and all supported edits remain reversible. The same editing result is available through the supported user actions without exposing internal command mechanics.

- **REQ-WRITING-LOOP-012: Consistent editing actions.** User actions shall provide consistent, safe results across keyboard, pointer, menus, and other available controls; invalid or unavailable actions shall not change screenplay content.
  - **AC-WRITING-012.1:** Malformed, out-of-range, unknown, or unavailable user actions shall fail without changing screenplay content. Transient interaction state shall not become saved screenplay content.
  - **AC-WRITING-012.2:** Typing, paste, deletion, Enter/Tab, element-type changes, undo/redo, Select All, and selection changes shall obey the same canonical editing, deterministic source-projection, text-boundary, history, and failure-safety rules in source-backed and source-less documents. Imported source topology and registrations shall not veto semantically legal edits. Collapsed Delete/Backspace follows AC-WRITING-001.3; noncollapsed selection deletion remains distinct. Desktop rejection feedback does not change command success or canonical content. Layout-based selection shall commit only valid screenplay positions.
  - **AC-WRITING-012.3:** Open and Save As selection workflows shall not change the active document when cancelled. Clipboard Cut, Copy, and Paste follow the transaction and privacy rules in AC-WRITING-011.3. Save without an active path shall offer Save As. A native import warning shall require an explicit Continue or Cancel choice; cancellation shall not replace the active document, and a document with unsaved changes shall not be silently replaced.
  - **AC-WRITING-012.4:** A pointer click or drag shall select a valid screenplay position. A primary-button double-click shall select the Unicode word at that position, or leave a caret when no word is associated with it. A triple-click shall select only the complete text of the clicked screenplay or title-page paragraph. These actions shall respect UTF-8 boundaries and shall not extend across paragraph boundaries. A physical key activation shall produce no more than one editing operation. Disabled controls shall not activate.
  - **AC-WRITING-012.5:** Unmodified Enter and Tab shall follow AC-WRITING-001.4a. Modified Enter/Tab shall not accidentally invoke those actions. Editor shortcuts shall apply only to focused Body editing, with exact modifiers and a physical-key match where named-key routing requires it; for dynamic document digit bindings only, the demonstrated Shift-active logical Exclamationmark plus physical Num1 event resolves to Num1 for the current binding lookup. No other logical/physical mismatch is normalized, and this narrow exception does not add a numpad alias. No input method may be composing or have supplied input in the current frame, and replacement, import-modal, native-output, and other active editing locks remain authoritative. Key releases and numpad keys are not aliases for specified named-key shortcuts. Document-defined element shortcuts never activate in Title Page.
  - **AC-WRITING-012.6:** Element-type shortcuts shall be parsed from each current definition's platform-appropriate `Shortcut` value on macOS or `WinShortcut` value on Windows, without modifying the retained source spelling. The ordered current document definitions remain the sole source of exact binding keys; activation assigns that exact open type through the ordinary shared command and safe type-editing behavior, with current availability and registry membership rechecked at execution. Blank or ASCII-whitespace-only values create no binding. Parsing trims only surrounding ASCII whitespace and accepts bounded ASCII case-insensitive `Ctrl`, `Alt`, `Option`, and `Shift` modifier tokens without duplicates, followed by exactly one supported key: A–Z, 0–9, a supported named editor key, semicolon, or colon. Each chord has an implicit Command primary modifier on macOS or Control primary modifier on Windows; macOS `Ctrl` adds literal Control, Windows `Ctrl` names the already-implied primary, and Windows `Shift` adds Shift. `Alt` and `Option` share one modifier slot. Semicolon and colon are logical text chords; colon canonicalizes to Shift+semicolon for modifier matching and conflict detection. Other platforms create no bindings. Unsupported/malformed/oversized values, reserved chords, and duplicate/conflicting chords are disabled with bounded privacy-safe diagnostics; every member of a duplicate/conflicting group is disabled, and definition order never selects a winner. Shortcut choices do not imply a fixed supported-type list.
  - **AC-WRITING-012.7:** Document-defined element shortcuts apply only while focused Body editing owns input and shall not replace, shadow, or alter native/in-window application menu accelerators or macOS Command-Q. Existing application menus continue to work outside screenplay focus. Exact modifier matching remains required, and the narrow Shift-active logical Exclamationmark/physical Num1 normalization applies only to dynamic document digit lookup; it does not change fixed editor, menu, dual-dialogue, text-punctuation, focus, replacement/modal/native-output, IME, or numpad ownership. Fixed editor deletion, navigation, unmodified Enter/Tab behavior, and active menu ownership take precedence over dynamic element bindings; key/modifier conflicts are disabled rather than resolved by order. The editor does not add Find, search, SmartType, revision, Beat Board, Index Cards, Scene View, or other reference-only features through these shortcuts.
  - **AC-WRITING-012.8:** User-facing editing actions shall remain limited to the supported document, text, selection, navigation, formatting, focus, view, and status behaviors described in these requirements. Pointer hover, painting, caret blinking, input-method preedit, and ordinary scrolling shall not themselves change screenplay semantics.

The following menu-family criterion keeps its stable ID here because clipboard semantics are part of screenplay editing; the parent [`REQ-WRITING-LOOP-011`](desktop-workspace.md) is owned by Desktop Workspace.

- **AC-WRITING-011.3:** Cut and Copy shall use the selected canonical screenplay text in document order, preserve exact casing and selected characters, and place one newline at each crossed paragraph boundary. They shall not apply print or export transformations. Cut leaves the screenplay unchanged if the clipboard write fails. Paste reads the clipboard only when requested; empty or unreadable content does not mutate the screenplay and produces a privacy-safe notice. Clipboard contents are not polled to enable or disable controls.

- **AC-WRITING-007.12 — Inline formatting overrides:** Font, Size, and Color actions apply to exactly the selected canonical UTF-8 run ranges, including ranges spanning paragraphs, as one undoable transaction. They split only at valid boundaries and change only the requested attribute; shared normalization may remove empty runs or merge adjacent semantically equivalent runs, while preserving exact text, unrelated attributes, paragraph overrides, identities, attachments, and representable opaque source. Style tokens use the shared canonical vocabulary/order, preserving unknown tokens and attributes; unsafe or ambiguous source topology and invalid values reject without partial mutation. A collapsed Body caret updates an independent transient inline-typing patch for Font, Size, or Color rather than formatting its paragraph; this advances the session mutation token but does not change Project, document revision, dirty state, or undo history. Undo/redo snapshots retain the patch with existing typing state; moving the caret clears it; later insertion applies it over inherited run attributes. Replacing a noncollapsed selection applies the run edit instead of the caret patch. The pending patch is absent from Project, FDX, and native saves. Element Default removes the direct Font, Size, or Color attribute and restores definition inheritance; clear Size is not a toggle. The existing integer menu values remain unchanged, while imported valid decimal Size values retain fixed-point precision. Plain Text clears only the five supported Style flags and leaves Font, Size, and Color unchanged.

- **AC-WRITING-007.13 — Paragraph formatting and explicit Body Type reset:** A first direct paragraph-formatting edit materializes the complete current definition ParagraphSpec—Alignment, FirstIndent, Leading, LeftIndent, RightIndent, SpaceBefore, Spacing, StartsNewPage, and unchanged Type—then overlays existing effective direct fields and changes only the requested field. Later edits retain earlier effective custom fields. Alignment uses the same complete-baseline operation. Source-backed paragraphs retain existing recognized attribute slots and unrelated source where possible; missing recognized attributes are inserted deterministically in reference ParagraphSpec order, retaining Type and paragraph ID. Preservation-free output emits the same complete semantic baseline. Spacing uses typed Single, OneAndHalf, or Double direct values and Leading uses typed Regular, Tight, or Loose values; unrecognized imported values remain source-owned and have no invented numeric interpretation. Space Before menu line counts are multiplied by the current definition's base font size in points. A real explicit Body Type change to a different exact key removes that paragraph's semantic direct-paragraph-override entry and recognized direct Alignment, FirstIndent, Leading, LeftIndent, RightIndent, SpaceBefore, Spacing, and StartsNewPage attributes so the new definition supplies defaults. It preserves canonical text, ordered runs and all inline attributes, stable/foreign identities, selection, attachments, unknown attributes, opaque children, dual source membership, outer-wrapper overrides, and unrelated source. Assigning the existing exact key is a no-op preserving overrides; Tab assignment through the same per-paragraph candidate follows this reset, while Enter-created right paragraphs retain their no-copy behavior. This narrowly supersedes AC-WRITING-007.2's preservation of direct paragraph formatting only for a real explicit Body Type change; the Title Page Type contract and Apply Template's bulk remapping policy are unchanged.

- **AC-WRITING-012.9 — Secondary-click selection:** In the Body Script View, a secondary click first establishes Body focus and resolves a canonical hit position using the existing presented-page/caret hit-test. A noncollapsed selection is preserved only when the hit lies within its ordered inclusive anchor/focus boundaries. Otherwise, a valid hit commits one collapsed pointer-release selection at that position before context-action availability is computed. A failed hit preserves the current selection and does not create a synthetic caret. This does not alter primary click/drag, double/triple click, Title Page interaction, or clipboard privacy behavior.

### Inline run normalization and source round-trip

Body and Title Page paragraphs use one shared canonical run-normalization contract. A normalized run vector contains no empty runs, preserves the paragraph's exact concatenated UTF-8 text, and is idempotent; an empty paragraph has no semantic runs, while a legacy nonempty paragraph without runs projects as one unformatted run. Adjacent runs merge when their known Style sets, semantic Size values, and retained non-Style/non-Size attributes are equivalent, irrespective of known Style token order or accepted strikethrough alias. Unknown Style tokens, including duplicates, are retained and emitted alphabetically after known tokens; known flags emit as Bold, Italic, Underline, Strikeout, AllCaps. Style is omitted when no token remains. AllCaps remains display-only. Unknown run attributes retain exact names and values and their relative order. Valid source Size spelling is retained; absent Size means inheritance, while invalid/unsupported Size remains source-owned and is not silently rewritten. Newly generated Size precedes Style, without reordering unchanged source attributes.

AC-WRITING-007.12's requirement to preserve unchanged ordered run structure and source token order is superseded only where normalization removes empty runs, merges semantically equivalent adjacent runs, canonicalizes known Style/alias output, sorts unknown Style tokens, omits empty Style, or applies the approved Size semantic key. AC-WRITING-007.12 continues to require exact selected-range behavior and preservation of canonical text, unrelated attributes, paragraph overrides, identities, attachments, and opaque source. Selected Font, Size, and Color insertion on ordinary unqualified Text attributes is valid even when absent from the source run; retained source partitions are not an edit permission rule when their data remains representable.

Font, Size, and Color range operations and text/structure changes use this shared rule for touched paragraphs, and every emitted save candidate uses it for managed Body and Title paragraphs. Clear Size restores definition inheritance by removing only the direct Size attribute; it is not a toggle. The current integer Size menu choices remain unchanged.

## Constraints

- Canonical screenplay text and exact element types are distinct from display-only capitalization, typography, selection, and transient editing state. Element labels are not trimmed, case-folded, or mapped to a fallback type.
- An operation that cannot preserve authored content safely leaves the existing screenplay unchanged. Native FDX remains the durable project format; no legacy JSON migration or compatibility API is provided.
- **NFR-WRITING-002:** Core editing, layout, and persistence behavior remains usable without opening a desktop window.
