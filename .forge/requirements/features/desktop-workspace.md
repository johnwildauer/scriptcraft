# Requirements Area: Desktop Workspace

> This document specifies desired user-facing behavior for a cohesive area. Describe requirements in established-state voice, even when implementation is future work. Group related capabilities into sections and keep stable IDs so each requirement and acceptance criterion remains independently traceable. Do not add lifecycle status, implementation evidence, progress, or a backlog here.

## Area purpose

The desktop workspace exposes common project and editing controls, communicates current page and cursor guidance, and presents menus and platform-native window chrome without taking ownership of screenplay meaning.

## Capability groups

### Toolbar and native window presentation

- **REQ-WRITING-LOOP-005: Desktop command toolbar.** The desktop application shall present common project commands and document-driven element-type selection in a consistent toolbar while preserving safe document behavior.
  - **AC-WRITING-005.1:** The main and Title Page toolbars each present the configured ordered selection of built-in item IDs from their independent global settings arrays. The default main sequence is flexible space, New, Open, Save, Save As, flexible space, Title Page, Elements, flexible space, Show/Hide, Export Text, Export PDF, flexible space, and overflow. The default Title Page sequence is flexible space, Styles, Alignment, flexible space, Close Title Page, and overflow. Missing, explicitly empty, or all-unknown arrays use their corresponding defaults; known entries retain order and repetitions, while unknown entries are omitted from the effective list. Flexible space is an ordinary list item. Built-in captions, accessibility names, graphics, commands, special dropdown/group behavior, disabled placeholders, measurement, and presentation overrides do not become user-defined. Show/Hide is enabled and opens a two-action dropdown in both main-toolbar and overflow presentations: active-surface Show/Hide Invisibles followed by global Show/Hide Ruler. Each action has a dynamic label and dispatches its shared typed toggle command once through deferred choice handling. The dropdown assigns no shortcut; existing menu accelerators remain as specified for their respective View actions. When the available width is insufficient, a configured overflow item appears only for actions that do not fit; flexible spaces do not appear in overflow. If a configured list omits overflow, no static indicator is synthesized and nonfitting items have no overflow affordance. The overflow control is accessible and has no visible caption.
  - **AC-WRITING-005.2:** Each New action opens an independent application instance initialized from the default Screenplay template, retaining its complete example body and title-page content as editable content, and does not replace or mutate the originating document, whether clean or modified. The new instance is Untitled Screenplay with no native path or FDX storage baseline; ordinary Save requires Save As. File → New from Template opens the shared three-entry selector in separate New-document mode; New remains disabled until a catalog ID is selected and then starts exactly one independent child using that stable ID. Its startup instantiates the selected full document through the Phase 7 common reader, retains complete body/title/settings content, and has a fresh session/layout identity, no native path or FDX baseline, `Untitled ` plus the selected built-in display name (default Screenplay therefore remains `Untitled Screenplay`), and Save As behavior. The parent receives no prompt, save, close, replacement, or mutation; launch failure preserves the selector and current parent. In-app Open picker selection and direct-path Open use the selected path to request replacement of the current instance only after the dirty-session gate and child activation acknowledgement; the picker accepts FDX and FDXT documents/templates. FDXT selection creates a fresh unsaved document rather than a writable document backed by the selected template path; picker cancellation launches no child. This acknowledged replacement contract is distinct from the macOS Finder/Dock OS-open behavior in AC-WRITING-005.2d–.2f and Windows shell-open behavior in AC-WRITING-005.2g. Save as Template remains disabled.
  - **AC-WRITING-005.2a:** In-app Open skips the unsaved-changes prompt for a clean session. For a dirty session, Cancel launches no child; Save proceeds only after a successful save leaves the live session clean; Don’t Save proceeds without writing, reverting, or marking the live session clean. Save picker cancellation, save failure, or Saved-but-still-dirty launches no child. A successful Save performed before a later failed replacement remains an ordinary completed Save; replacement failure does not undo it.
  - **AC-WRITING-005.2b:** After an accepted gate, command dispatch or child spawn is not Open success. While one matching replacement handoff is pending, document editing/actions are locked and the current instance remains available only for safe presentation/lifecycle controls. A non-Version-6 child remains pending through its Continue/Cancel decision; neither pending migration nor Cancel is Open success. Only a matching Opened acknowledgement sent after the selected document's session is activated authorizes the existing one-shot root-Close continuation.
  - **AC-WRITING-005.2c:** Launch/setup failure, child read/version/import/activation failure, migration Cancel, malformed/oversized/closed acknowledgement channel, child exit with either zero or nonzero status, exit-poll failure, or the acknowledgement timeout clears the pending lock and safely resumes the current instance without replacing its session or title. Timeout does not kill or wait for the child; stale or late Opened events do not close the resumed instance. Don’t Save never reverts edits or changes the source file, including on failed replacement.
  - **AC-WRITING-005.2d:** On macOS, a Finder or Dock Open Documents request containing one local FDX or FDXT file URL uses the new process's initial document slot when that slot is still available and no startup document argument owns it. The first valid cold request is staged through ordinary startup opening; each later request, including each later single-document event, launches one independent child with the selected path. The shared staged opener classifies FDXT by ASCII case-insensitive filename extension and activates it as fresh unsaved content, never as a writable template path/baseline; an FDX root Template attribute alone does not select that lifecycle. OS-originated opens bypass in-app Open and its replacement handoff.
  - **AC-WRITING-005.2e:** A macOS OS-open request never replaces or otherwise mutates a receiving document and never triggers its dirty-session prompt, Save/Don’t Save/Cancel decision, replacement acknowledgement, root Close, or child termination. This remains true for a dirty receiver and while Title Page, migration, native output, or an in-app replacement is active. Receiver content, path, save baseline, title, selection, dirty state, source bytes, and ordinary editing availability remain unchanged by the request. Intake or child-launch failure is reported in the receiver without changing its document; a failed cold open leaves the initial instance untitled, and a child content-open failure belongs to that independent child.
  - **AC-WRITING-005.2f:** Each Apple event is accepted all-or-nothing: a bare descriptor or a list containing exactly one item is converted through `fileURLValue`; only a resulting local file URL with a valid nonempty UTF-8 native path may proceed. A multi-document event opens none of its items and reports one bounded error. Separate single-document events remain distinct and are handled in FIFO order. Bounded-queue overflow rejects new events without evicting accepted events and is reported without exposing paths. Association metadata determines Launch Services eligibility only and does not validate FDX content.
  - **AC-WRITING-005.2g:** On Windows, an ordinary launch without a document remains a blank launch. A shell-open process accepts exactly one positional native argument as its document path; an FDXT path is classified by the shared ASCII case-insensitive extension rule and opens as fresh unsaved content, never as a writable source; that source is mutually exclusive with the custom `--document-path` input, and repeated or mixed document sources, multiple positional paths, or a positional path with the internal handoff option are rejected in full before document-window creation. Argument-vector boundaries are authoritative: spaces and valid Unicode are retained as one path, and arguments are not joined, split, or reparsed as a command string. Invalid invocation or unavailable startup presentation receives bounded native feedback before GUI creation without disclosing supplied paths. A valid positional path belongs to the process Windows started and is consumed on its first update by the existing staged native open and activation path, not by a picker, in-app Open command, child launch, or acknowledged replacement. Only Activated is successful activation; AwaitingMigration remains pending, the existing Continue/Cancel decision stays in that process, Cancel leaves it untitled without being treated as Failed, and terminal read/content/version/import/activation failure leaves it untitled with bounded, privacy-safe native feedback. Association or extension metadata does not validate content; opening preserves source bytes. Each shell request starts and owns an independent process/document lifetime: it has no handoff, acknowledgement, existing-instance discovery or forwarding, singleton, broker, prompt, save, mutation, or close effect on any existing process or its document, including a dirty receiver. A one-file drop onto the executable or a suitable user-created shortcut is covered only when Windows supplies the same single positional argument; a combined multi-path invocation is rejected in full, while separate one-path processes remain independent. Taskbar/taskbar-hover delivery and in-window file drops are outside this behavior.
  - **AC-WRITING-005.3:** Toolbar items present their assigned graphic, caption, and enabled/disabled state consistently. Disabled items do not respond to pointer or keyboard activation, acquire focus, open popups, dispatch actions, or appear enabled to accessibility tools. Captions are accessible without redundant visible-label tooltips. Show/Hide and Export Text retain their assigned graphics and captions; Show/Hide opens its accessible two-action dropdown, whose invisibles and ruler action names reflect current visibility. Each row has the shared command and is unavailable under the existing modal, replacement, native-output, and element-dialog gates; activation dispatches only the selected action once. Overflow entries preserve enabled/disabled presentation and behavior. Icons use the bundled Material Symbols Rounded presentation and distinguish outlined/filled forms without changing document typography.
  - **AC-WRITING-005.4:** Elements displays the exact element type of the focused Body paragraph at the current editing position, when that selection resolves in the current project. Its dropdown and overflow submenu use one per-render read-only choice snapshot of every current document definition, in exact registry order, with exact labels; the opened popup derives its minimum width from the longest current label plus the existing option padding, while the closed control's allocated width and truncation remain unchanged. Full content height includes every current row and popup margin; ordinary usable viewports expose the complete list where feasible, and constrained viewports retain bounded scrolling so every definition remains reachable. An invalid or absent focused selection does not invent or preselect Action or another type. Choosing a definition constructs the open-key element-change command and invokes shared dispatch once; current availability and exact project membership are rechecked at execution. Rejection preserves the document. The closed control, popup, and accessibility behavior clearly identify the element-type selector.
  - **AC-WRITING-005.5:** The toolbar keeps the leftmost configured ordinary items that fit and puts remaining actionable items into a far-right overflow menu only when that list includes its built-in overflow item. Overflow appears only when needed; without the configured item, nonfitting items have no overflow affordance. A fully fitting toolbar keeps its final configured item and caption within the visible toolbar edge. Flexible spacing is divided evenly when all ordinary items fit, and item widths remain consistent between measuring and display. Repeated known entries, including flexible spaces, remain supported and each rendered entry has an identity scoped by ordered position as well as item ID.
  - **AC-WRITING-005.6:** On macOS, the desktop uses the OS-owned native window header, with the toolbar at the top of the window content below it. Header interactions remain OS-owned; no particular double-click result is promised.
  - **AC-WRITING-005.7:** Toolbar actions and Elements controls use the standard arrow cursor; the screenplay editing surface uses the text/I-beam cursor. Decorative labels and painted page rectangles do not compete for cursor ownership.
  - **AC-WRITING-005.8:** The toolbar boundary aligns with the Script View below it without an intervening application spacer or fixed page inset. Its controls remain within the toolbar area and the visible lower divider aligns with the panel boundary. Page-edge spacing belongs to scrollable page content.
  - **AC-WRITING-005.9:** A fresh built-in document's native window title is `Untitled ` plus its selected catalog display name (default Screenplay therefore remains `Untitled Screenplay`); a fresh external FDXT document uses `Untitled ` plus the source filename stem with only the final extension removed; an active ordinary FDX document shows only its final filename component, including the extension. Startup and File → New instantiate the default Screenplay through the common built-in loader and retain its complete example body/title content. Their initial semantic-clean session is not a saved-on-disk claim: native path and FDX conflict baseline are absent together, and ordinary Save routes to Save As. Only verified successful FDX publication establishes the destination path and baseline together. Opening an FDXT, whether built-in or external, produces a fresh unsaved document with the applicable template-derived title; its staged read baseline is discarded before activation, and the template filename is never retained as the native path/baseline. Successful New/Open/Save/Save As updates the title when appropriate; an in-app replacement child presents the selected FDX filename after ordinary FDX activation. A failed or cancelled replacement leaves the originating instance's title and session unchanged, except for an independently completed Save chosen at its dirty gate. The title does not contain a full path, dirty marker, or duplicate application-name suffix. Native window decorations remain enabled.

Command 22 is validated against the exact current project registry both at envelope validation and again at direct executor entry. A valid explicit Title Page surface is supported by the command path; the generated toolbar and dynamic keyboard choices remain Body-only. Unknown or stale targets are rejected without exposing the supplied label and without publishing project, source, selection, history/redo, dirty, revision, or mutation-token changes. Global replacement, modal, and native-output locks remain authoritative.

Phase 8 exposes settings-only Apply through a headless session service and does not add a command ID, selector, menu action, dialog, or desktop mutation path. Phase 9 owns selector visibility and selection, Cancel/Apply presentation, menu enablement, and the thin desktop adapter; Cancel constructs no target or candidate, while an explicit Apply activation calls the headless service once. The desktop then relies on the existing session mutation token/revision refresh path for Body and Title surfaces, dual presentation, layout/font environments, and generated controls rather than implementing separate template policy.

### Elements inspection and template selection

  - **AC-WRITING-005.11 — Read-only Elements inspection:** Format → Elements and the existing primary+E accelerator open one compact, resizable native immediate Elements viewport in the existing process and session through the shared typed command/dispatcher path. Its stable viewport identity is `scriptcraft-elements-inspector`; native inner size defaults to 640 × 480 logical points and has a 520 × 360 logical-point minimum. A selectable, independently scrolling listbox presents every current Project definition exactly once in exact registry order, including arbitrary and case-distinct keys. The first current definition is selected on initial open; selection tracks the exact key and falls back to the first current key when the prior key disappears, while an empty registry has no selected definition. The selected definition alone is projected in read-only Basic, Font, and Paragraph tabs. Basic presents Start new page, PaginateAs, the active-platform shortcut, Return/Tab targets, and useful Outline values; Font presents declared family, nonzero point size, explicit color or Theme default, and active style flags; Paragraph presents alignment, spacing, leading, point-valued space-before, and first/left/right indents in inches. Direct paragraph/run overrides and resolved host-face substitutions are not represented as definition values; no host-font discovery is initiated. Absent and unresolved Behavior remain distinguishable; unresolved targets are never replaced with Action, General, or another fallback. Definition editing, add/remove/rename/reorder, and settings controls are absent. **Apply a Template** is bottom-left; **Close** is bottom-right and uses the existing Elements close path.
  - **AC-WRITING-005.12 — Built-in selector:** **Apply a Template** opens the shared two-pane selector over the sole ordered built-in catalog: Screenplay (“The industry standard”), Stageplay (“An alternative for modern plays with looser dialogue margins in Times New Roman”), and Dramatists Guild Musical (“The Guild's modern format for musicals in Times New Roman”). These exact names/order remain catalog expectations; Preview Description text is read from each embedded FDXT resource, not duplicated Rust metadata. Its three-name listbox opens with the default built-in ID `screenplay` selected and focused; the Preview immediately shows the selected exact name and its direct-root FDXT Preview Description. In New-document mode, the initial primary action is **New**; in Apply mode it is **Apply**. Missing or unusable Preview metadata produces no description fallback, and Preview Image payload is not displayed. Opening establishes only transient selection and performs a bounded metadata read: it does not invoke the full common loader, instantiate a target, create a candidate, call the Phase 8 service, or mutate a session. Explicit selection changes update the selected Preview; Cancel, title-bar close, and Escape load no target and create no candidate. Apply/New dispatch still rechecks the exact current selector mode and selected-ID/payload equality. Cancellation closes only the selector and clears its pending selection/error, preserving Elements when already open.
  - **AC-WRITING-005.13 — Explicit Apply and refresh:** An enabled Apply activation carries one typed built-in catalog ID through the shared desktop dispatcher and headless executor to the Phase 8 `EditingSession.apply_builtin_template()` service exactly once. Initial Screenplay selection and Preview metadata reads are presentation-only; neither invokes the full target loader or that service. At dispatch time, the adapter verifies that the selector remains open in Apply-to-current mode and that its current selection equals the command payload; rendered availability alone is not authorization. Changed and NoOp are successful selector outcomes: close only the selector, clear its pending selection/error, and leave Elements open. Changed exposes the current registry through the existing session/layout/control refresh mechanisms. A target-load, extraction, planning, or edit failure leaves the selector open with its selection and current document intact and presents one fixed, bounded, value-free error for that attempt; subsequent frames do not repeat the error. Failure and cancellation do not change content, definitions, selection, history/redo, dirty/revision/token state, native target/path, clean baseline, or source. NoOp is not presented as a document mutation.
- **AC-WRITING-005.14 — Input, accessibility, and window ownership:** Both windows are compact egui windows in the root application context, not native OS modals, additional document windows, sessions, processes, or viewports. Stable accessible names, selected state, enabled state, visible focus, and predictable keyboard navigation identify every actionable control; read-only definition summaries remain reachable without becoming row actions. Selector rows expose their exact catalog name, description, and radio selected state. Initial selector focus is on the first row without selecting it; Tab proceeds through the single-selection rows, Cancel, and then enabled Apply/New, with stock Space/Enter activation and a visible focus indicator. Disabled Apply/New cannot receive focus or activation. While either Elements window owns input, Body and Title pointer/editor commands, text, paste, dynamic element shortcuts, timer/editor popup interaction, navigation, and IME commits cannot reach either editor surface, while the dialog retains its own navigation and scroll behavior. IME activity on either surface or any same-frame IME event suppresses menu/editor shortcut capture; dialog ownership additionally blocks every editor commit without synthesizing one or routing preedit text. In-window accelerator handling captures only explicitly permitted dialog-focus and root-lifecycle commands, preserving unrelated input for egui; native macOS and in-window Windows menu activation continue through the same fresh availability and typed FIFO/dispatcher path. Only the topmost element window handles Escape; selector Escape cannot also close Elements. Existing migration/replacement/native-output locks retain precedence. Native root Close/Quit continues through the ordinary dirty-document lifecycle. Opening Elements from Title Page relinquishes editor focus and moves input ownership to the root dialog without closing the Title viewport or changing semantic Body/Title selection. On final dialog close, focus returns to the captured Title Page only if its viewport remains open and supported, otherwise to Body, and never over a remaining dialog or higher-priority lock. An already-open Title Page viewport remains open and may repaint current content, but cannot receive dialog input. New from Template is a separate selector mode and host child-launch effect, distinct from Apply; it rechecks New mode and exact selected ID without changing Apply behavior.

For both listboxes, row selection and Elements tab selection are transient presentation actions only; they do not edit the Project/session or dispatch a document-edit command. Full-width rows expose complete accessible names and selected state; inspector detail values remain read-only and noninteractive. The row label is nonselectable and uses the standard arrow cursor. Row backgrounds are square-cornered, outline-free full-bleed rectangles within the listbox; the separate keyboard-focus ring remains. Selector rows expose only their exact template name and selected state (no radio bullet or per-row description); the selected Preview Description is reachable as read-only text in the Preview pane. Elements is an ordinary resizable native immediate viewport titled **Elements**, with a 640 × 480 logical-point default and 520 × 360 minimum. The selector is a separate resizable native immediate viewport titled **Apply a Template** or **New from Template**, with a 560 × 360 default and 480 × 300 minimum. Both compose CentralPanel content, bound pane content to available space, keep list/detail panes independently scrollable or clipped, and keep their footers visible; they have no root-window clamping or embedded fallback. Shared presentation constants own the 176-point list column, 10-point pane gap, zero horizontal and 4-point vertical listbox inner inset, 8-point detail inset, 23-point row height, zero row gap, 12-point left-aligned row text, and 6 × 1-point row padding. Detail typography and read-only values remain unchanged. Every inspector frame derives ordered summaries directly from [`Project.element_definitions()`](../../crates/scriptcraft-model/src/project.rs:72), using exact keys and current normalized definition/Behavior projections without caching definitions or initiating font discovery. Elements-local reference-inspired list/tab styling preserves theme legibility and does not alter application-wide visuals.

### Status, diagnostics, and menus

For AC-WRITING-006.2a, paragraph hints display the exact resolved current-definition target key returned by the same pure Return/Tab decision used for execution; the status adapter uses that key's exact display text without a closed-role lookup or static label table. Missing and unresolved targets are consumed no-ops and are not replaced by static labels or fallback types. A resolved same-key Tab remains an exact displayable target even though applying only that same key publishes no mutation. Hint text is presentation-only and cannot mutate editing state. Toolbar choices, status guidance, and platform shortcut bindings are transient projections of the current ordered registry and Behavior, using the active platform's Shortcut or WinShortcut field as specified by the criteria below. Source-level assertions do not establish physical desktop-keyboard, focus, IME, or rendered-guidance acceptance.

  - **AC-WRITING-006.2a:** Without a held exact enabled element-type shortcut chord, paragraph-key hints appear only for a collapsed caret at the end of canonical element text (including an empty element) and with no unsupported modifiers. For clarity, in AC-WRITING-005.2 and AC-WRITING-005.9 the Screenplay-only ordinary-startup/File-New statements are superseded: an ordinary no-document launch and File → New use the saved default ID, with Screenplay as the version-1 default and the effective fallback for an unknown ID. A fresh built-in document is titled `Untitled ` plus the selected catalog display name; this remains `Untitled Screenplay` when Screenplay is selected. In AC-WRITING-005.12, Screenplay remains the initial selection for Apply-to-current mode; New-document mode starts from the effective saved default. The same mode distinction supersedes the later “each newly opened selector starts with Screenplay” wording. These are narrow replacements; the existing stable IDs and unrelated New, Apply, cancellation, and document-lifecycle guarantees remain unchanged.

- An ordinary no-document launch and File → New use the saved default template, with Screenplay as the effective fallback for an unknown ID. An explicit New-from-Template ID controls that child; a supplied document path controls its opened document. A persisted default is not an explicit template argument and does not pre-finalize the macOS cold-open initial slot.
- New-document selector mode initially selects the effective saved default; Apply mode retains its Screenplay initial selection and never changes the preference. Only successful independent child spawn from New from Template persists the selected ID. Browsing, Preview, Cancel, Apply Changed/NoOp, failed spawn, and ordinary File New do not independently update it; the parent document remains unchanged.
- Appearance is a persistent global choice projected through the existing per-process UI state, not a screenplay setting. The existing typed appearance command persists a real applied change; changing it does not dirty the screenplay or alter undo/history, layout identity, or exports.
- Ruler visibility is a separate persistent global preference, not a per-document or screenplay setting. The parameterless desktop-only `view.ruler.toggle` command changes it; it does not alter screenplay state, session history, canonical layout, or exports. Its version-1 default, old-file behavior, reset behavior, and writer/process limits are specified in [User Settings requirements](user-settings.md).
- The ordered `toolbar` and `title_page_toolbar` arrays are separate persistent global presentation preferences. They retain stable built-in item IDs only, remain outside the document/session/FDX/command/layout/export state boundaries, and are resolved independently; unknown-ID filtering and empty-result fallback do not rewrite their raw settings. Their default arrays and overflow-omission behavior are specified in [User Settings requirements](user-settings.md).
- Recovery, reset, no-shutdown-flush behavior, schema evolution, and independent-process limits are specified in [User Settings requirements](user-settings.md), rather than duplicated here.

### Inline clear-size and replacement Open error ownership

The Body Size menu provides an Element Default action before the existing numeric choices. Element Default clears only the selected runs' direct Size attribute, restoring inheritance; at a collapsed Body caret it changes only the transient typing patch applied to later insertion. It is not a toggle and preserves all other run attributes and text. This supersedes AC-WRITING-011.13's “with no Default row” clause only for the Size submenu; the existing integer choices and command-envelope version remain unchanged.

For an acknowledged replacement Open failure, the parent is the sole native-dialog owner; the replacement child reports the existing terminal handoff and bounded development diagnostic without showing a second native dialog. Direct cold-start and independent-child failures retain child-local native reporting. This does not change migration, dirty-document, or replacement acknowledgement rules.

## Constraints

- Status, menu, timer, and focus-mode state are desktop presentation or per-window state, not screenplay semantics. Toolbar item presentation remains built in, while its selected global item order and membership, Appearance choice, and ruler-visibility preference are persisted separately and remain outside screenplay semantics.
- Platform-specific behavior is limited to the explicitly stated platform expectations.
- Root Close and application Quit protection does not imply that arbitrary forced process termination can be cancelled.
