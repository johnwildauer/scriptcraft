# V6-WO-001.4 — OS-independent geometry with physical desktop presentation

- **Status:** Implemented 2026-11-03; regression coverage authored but not executed; user desktop validation pending
- **Depends on:** V6-WO-001.3 for persisted root TextState Scaling; no core layout changes are authorized by that dependency
- **Validation:** User-owned; no agent-run checks or independent validators

## Objective

Keep document, pagination, and PDF geometry identical across operating systems while making desktop 100% zoom approximate the page's physical size through OS logical-coordinate conversion and native display scale.

Remove the current thumbnail-like 360-point 100% presentation and eliminate the former 2.3/2.333 fallback.

## Architecture decision

The stable document unit is 1/72 inch. Core layout and PDF continue to use that unit directly, so a default Letter page is 612 × 792 document points on every OS.

Only the desktop visual layer converts document points into egui logical coordinates:

| Platform | Logical points per document point at 100% | Default Letter width before native scale |
|---|---:|---:|
| macOS | 1.0 | 612 |
| Windows | 96 / 72 | 816 |

The native display multiplier then applies exactly once through egui. This uses the operating systems' logical-coordinate conventions rather than changing the underlying document definition.

Examples at 100%:

- macOS with native scale 2.0: 612 logical points × 2.0 produces 1224 physical pixels, representing 8.5 inches at 144 DPI.
- Windows with native scale 1.25: 816 logical points × 1.25 produces 1020 physical pixels, representing 8.5 inches at 120 DPI.

These are coordinate-model examples, not monitor-calibration guarantees. No physical hardware measurement or arbitrary display PPI database is introduced.

## Pre-implementation defect

Before this order was implemented, [`presentation_metrics_at_zoom()`](../../../apps/scriptcraft/src/main.rs:1355) used [`CURRENT_DEFAULT_PAGE_WIDTH`](../../../apps/scriptcraft/src/main.rs:33), fixed at 360, instead of the effective paper width. This made 100% smaller than the document's logical 612-point Letter width even before considering OS display conventions.

Before this order was implemented, [`resolved_ui_pixels_per_point()`](../../../apps/scriptcraft/src/status_bar.rs:215) fell back to 2.3 when native scale was absent or invalid. The user rejected that fallback for v6; the implemented neutral fallback is 1.0.

## Scope

1. Derive desktop presentation width and typography scale from effective paper width, OS logical conversion, and page zoom.
2. Keep core layout, source mapping, pagination, PDF, and plain-text geometry OS-independent.
3. Apply valid native display scale exactly once with UI zoom 1.0.
4. Use neutral 1.0 when native scale is absent/invalid and replace it when a valid value arrives.
5. Persist only the user's TextState Scaling percentage through 001.3, never the OS/native multipliers.
6. Update tests and durable requirements that currently encode the 360-point and 2.3 behavior.

## Non-goals

- No changes to shared document points, page bounds, role geometry, fixed-cell font metrics, pagination, PDF coordinates, or canonical text.
- No physical monitor calibration, PPI setting, platform-specific document model, or native-scale value in FDX.
- No 2.3 or 2.333 fallback.
- No global scaling of toolbar/status controls beyond the existing native UI behavior.
- No guarantee that every window manager or physical display reports accurate density.
- No DocumentRef/XRef or WindowState behavior changes.
- No agent-run tests, desktop automation, review, or validation.

## Implementation requirements

### 1. Separate document scale from presentation scale

Replace the fixed 360-point baseline in [`presentation_metrics_at_zoom()`](../../../apps/scriptcraft/src/main.rs:1355) with:

- effective paper width in document points;
- a platform logical-points-per-document-point factor;
- normalized page zoom divided by 100.

The resulting presentation scale also applies to base typography and fixed-cell editor geometry. At 100%:

- macOS default Letter uses width 612 and scale 1.0;
- Windows default Letter uses width 816 and scale 96/72;
- 75% and 300% scale those values linearly.

Use an explicit helper for the platform factor and a testable pure conversion helper so both macOS and Windows expectations can be authored independently of the host running the tests. Unsupported platforms may use neutral 1.0 without becoming a new product-support commitment.

Remove [`CURRENT_DEFAULT_PAGE_WIDTH`](../../../apps/scriptcraft/src/main.rs:33) rather than replacing it with another platform-independent hard-coded page width.

### 2. Apply native scale once

Retain the existing collection of [`native_pixels_per_point`](../../../apps/scriptcraft/src/main.rs:1725). It is a display-scale multiplier, not a document-layout input.

Update [`resolved_ui_pixels_per_point()`](../../../apps/scriptcraft/src/status_bar.rs:215) and [`ui_zoom_factor()`](../../../apps/scriptcraft/src/status_bar.rs:221) so:

- a finite positive native value is effective unchanged with UI zoom 1.0;
- an absent, nonfinite, zero, or negative native value produces effective scale 1.0 and UI zoom 1.0;
- a later valid native value replaces the neutral fallback;
- page zoom is not multiplied into global UI zoom;
- native scale is not multiplied into TextState Scaling, document points, or PDF geometry.

Do not introduce an explicit Retina multiplier on top of egui's native scale.

### 3. Preserve core/PDF determinism

Do not change [`LayoutInputs`](../../../crates/scriptcraft-core/src/lib.rs:395), shared layout code in [`layout.rs`](../../../crates/scriptcraft-core/src/layout.rs), or export geometry in [`exports.rs`](../../../crates/scriptcraft-core/src/exports.rs) for this order.

The same semantic project and effective fixed layout inputs must continue to produce the same document-point page structure and PDF output regardless of desktop OS, native scale, or TextState Scaling. Desktop hit testing consumes the existing layout-to-presentation transform; it must not feed scaled coordinates back into canonical source ranges.

### 4. Integrate with persisted TextState Scaling

001.3 restores and saves only the user's whole-percent page zoom. This order consumes that percentage exactly as it consumes slider/pinch changes:

- no OS conversion factor is stored;
- no native display multiplier is stored;
- reopening on a different OS uses the same percentage with that OS's presentation conversion;
- fixed layout/PDF remain identical when only the saved percentage differs.

### 5. Preserve editor interactions

Update geometry-dependent expectations while retaining:

- page centering when the sheet and side buffers fit;
- horizontal overflow and scrolling when they do not;
- pointer-to-source hit testing;
- selection painting and caret reveal;
- preferred vertical navigation and visible-page tracking;
- no changes to focus/IME ownership or global toolbar/status scale.

Tests that assert 360 as an intentional invariant must be updated to the corrected physical-presentation contract rather than preserving the defect.

9. A core/export control demonstrates that OS presentation helpers are not consumed by fixed layout or PDF generation.

## Implementation record — 2026-11-03

Implemented V6-WO-001.4 on top of completed 001.1–001.3 without changing those work orders' behavior or core/PDF document geometry. Removed the desktop's 360-point baseline. Presentation now uses effective paper width in document points, a platform conversion factor (macOS 1.0, Windows 96/72, unsupported platforms neutral 1.0), and normalized user zoom. The same presentation scale applies to page dimensions and base typography. The helper accepts an explicit platform so both OS contracts can be covered independent of the host. Existing scroll centering/overflow, hit testing, caret/selection painting, and visible-page geometry continue to use the shared presentation transform.

Native display scale remains sourced from egui's viewport and is applied once with UI zoom 1.0. Missing, nonfinite, zero, or negative native scale now resolves to neutral 1.0; a subsequent valid native value is consumed unchanged. The OS presentation factor and native scale are not passed into core layout, pagination, PDF, or TextState. Save continues to write only `zoom_percent` into TextState Scaling.
