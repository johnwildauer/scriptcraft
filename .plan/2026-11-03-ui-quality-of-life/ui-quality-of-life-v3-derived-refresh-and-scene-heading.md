## 3. Finding — repeated Cast List updates require a state-sequence reproduction

A successful first update is expected to clear the completed pending scope in [`complete_derived_invalidation()`](../../crates/scriptcraft-core/src/editing.rs:441). A later Character text or role change should produce a new affected-scene scope through [`classify_derived_invalidation()`](../../crates/scriptcraft-core/src/editing.rs:1203), which compares ordered Character identity/text projections by owning scene. A due scheduler tick should then call [`refresh_cast_lists_with_outcome()`](../../crates/scriptcraft-core/src/editing.rs:505) again.

The source therefore does **not** support a simple conclusion that completed scenes are permanently marked clean. At least one of the following must be happening in the user's sequence, but static inspection cannot select among them:

- the later edit is not producing the expected affected-scene invalidation;
- the scene remains in safe-deferred or failed state and the later edit is not clearing/reactivating that state as intended;
- a refresh runs but its correction considers the scene unchanged or defers it;
- the visible Cast List and the scene being edited are not the same owning scene after structural role/topology changes.

The preflight added in [`cast_list_source_is_replaceable()`](../../crates/scriptcraft-core/src/cast_list.rs:252) can return a safe-deferred outcome without an error, while [`scene_needs_cast_list_update()`](../../crates/scriptcraft-core/src/cast_list.rs:236) decides whether list replacement is currently needed. After the first update, multi-run lists contain a full first run and empty later runs in both semantic and preserved projections, so a second update must be exercised explicitly rather than assuming the first-update tests cover it.

The initial scan found no dedicated repeated-update sequence; the follow-up scan in Section 9.1 corrects that broad statement. Existing coverage includes a preservation-free second scheduler update and an imported second update through a fresh Complete scope, but not second/third Character edits in one imported scene across actual affected-scope completion and scheduler reactivation. The highest-value missing evidence is that precise deterministic sequence, recording the value-free pending/retryable/deferred/failed summary and requested/attempted/changed scene counts after each edit and refresh.

This is an unresolved diagnosis, not evidence for a particular fix. Clearing every deferred/failed flag on every edit would be unsafe and could recreate the former retry loop.

## 4. Finding — the saved empty Scene Heading shape is legal

The absence of a Text element is not by itself malformed or evidence of save corruption.

The native writer explicitly removes managed Text elements when semantic text is empty in [`reconcile_managed_paragraph()`](../../crates/scriptcraft-core/src/fdx.rs:2173). The reader also projects wholly empty Text runs to no semantic runs in [`make_semantic_element()`](../../crates/scriptcraft-core/src/fdx.rs:3720). This matches the durable empty-managed-paragraph contract: empty canonical text has no semantic runs and no direct managed Text children, while role, identity, attachments, and other source-owned children remain.

The text-replacement path also has explicit support for a childless managed paragraph. In [`replace_text_element_children()`](../../crates/scriptcraft-core/src/preservation.rs:2821), an empty old text plus zero-offset insertion creates a namespaced Text element and then inserts content.

Therefore, typing into a genuinely empty semantic/source Scene Heading should not produce the reported mismatch. The saved XML is a useful fixture shape, but the missing Text element alone does not explain the error.

## 5. Finding — the text-replacement error proves an earlier semantic/source divergence

The new diagnostic localizes the failure to [`replace_managed_text()`](../../crates/scriptcraft-core/src/preservation.rs:1606) and its helper, rather than scoped validation, whole-list replacement, or paragraph removal.

The immediate failing comparison is in [`replace_text_element_children()`](../../crates/scriptcraft-core/src/preservation.rs:2821): the concatenated source Text-run content must equal the semantic element's prior text before applying the edit. The direct-text-child branch has the same requirement in [`replace_managed_text()`](../../crates/scriptcraft-core/src/preservation.rs:1606).

Consequently, the user's sequence establishes this stronger finding:

- at the moment text insertion was attempted, the semantic Scene Heading's prior text and its retained in-memory source Text projection disagreed;
- the eventual saved empty paragraph shows the source shape after later deletion/save, but does not reveal the semantic text or run state at the earlier failure;
- role cycling, split/join, derived refresh, or an earlier failed/rolled-back candidate must be examined to find where that divergence was introduced;
- forcing insertion into a childless paragraph or deleting this check would conceal rather than repair the synchronization defect.

The reproduction must capture the exact role sequence and the semantic text/runs immediately before the failing insertion. The current XML fixture should be paired with a role-cycle sequence that reaches a nonempty semantic Scene Heading while its source has no Text, or otherwise produces unequal old text/source segments. That precise before-state is still not established.

## 6. Finding — Scene Heading deletion has a direct attachment guard

Structural deletion is a separate, deterministic issue. [`remove_managed_paragraph()`](../../crates/scriptcraft-core/src/preservation.rs:1997) requires [`is_plain_managed_paragraph()`](../../crates/scriptcraft-core/src/preservation.rs:2708). A generated SceneProperties child is not a Text element or whitespace node, so the paragraph is not plain and removal returns StructuralAttachmentConflict before identity/provenance checks or source removal.

Thus the reported deletion error is fully explained by the current implementation. The guard does not distinguish app-owned, successfully generated SceneProperties/SceneArcBeats from unknown authored nested data.

A related guard exists in [`change_managed_role()`](../../crates/scriptcraft-core/src/preservation.rs:1802): entering or leaving Scene Heading while attached or unknown nested data is present also returns StructuralAttachmentConflict. This makes role-cycle behavior and deletion behavior part of the same ownership question, even though the text-replacement mismatch is a distinct failure.

The saved shape has an empty generated arc, but the current removal guard does not use that fact. Any remediation needs an explicit, bounded distinction between safely generated scene containers and opaque/authored attachments; simply deleting every attached Scene Heading would violate the existing preservation contract. Section 9.3 and V3-WO-005 now draft that bounded deletion-only remediation without changing split/join or role-transition safe-stops.

## 9. Additional static research — 2026-11-04

### 9.1 The missing Cast List case is repeated imported affected-scene refresh

The earlier statement that no repeated-update sequence exists was too broad. [`derived_refresh_pending_gate_tracks_relevant_edits_history_and_replacement()`](../../apps/scriptcraft/src/main.rs:4206) already authors an initial refresh, a later Character replacement, and a second scheduler-driven update. That fixture is preservation-free, so it does not exercise retained FDX runs, scene arcs, or managed-source replacement. [`imported_multirun_cast_list_refresh_preserves_runs_arcs_and_save_projection()`](../../crates/scriptcraft-core/src/cast_list.rs:848) does exercise a second imported update, but it constructs a fresh session after the first external correction; that refresh begins from Complete scope rather than a completed activation pass followed by affected-scene invalidation.

The exact missing regression is therefore: import a supported scene, complete the session's initial refresh, perform two or more successive Character edits with a successful affected-scene refresh after each, and assert semantic text, semantic runs, retained Text runs, scene-arc names, and pending/retryable/deferred/failed summaries after every step. Include a multi-run Cast List whose later runs become empty after the first correction, then exercise both rename and removal/addition cases.

Static tracing still does not reveal a permanent-clean defect. [`classify_derived_invalidation()`](../../crates/scriptcraft-core/src/editing.rs:1203) compares each scene's ordered Character identity/text projection, [`PendingDerivedInvalidation::merge()`](../../crates/scriptcraft-core/src/editing.rs:95) unions new affected scenes, and [`complete_derived_invalidation()`](../../crates/scriptcraft-core/src/editing.rs:441) removes only completed scopes. A scoped retry excludes safely deferred and failed scenes in [`refresh_cast_lists_with_outcome()`](../../crates/scriptcraft-core/src/editing.rs:505), making a newly deferred or failed second pass a concrete alternative to investigate rather than assuming that no refresh was scheduled.

The desktop receives changed/unchanged scene counts in [`CastListCorrection`](../../crates/scriptcraft-core/src/cast_list.rs:22), but [`PerformanceDiagnostics::safe_summary()`](../../apps/scriptcraft/src/main.rs:316) currently projects requested, attempted, and deferred scene totals without those per-scene changed/unchanged values. The diagnostic order should expose only the existing value-free counts needed to distinguish no invalidation, a skipped deferred/failed scope, an attempted unchanged pass, and a changed pass. This is a coverage/observability gap, not yet a production diagnosis.

### 9.2 Existing Scene Heading probes do not exercise the reported cycle

[`v2_wo0026_scene_heading_sync.rs`](../../crates/scriptcraft-core/tests/v2_wo0026_scene_heading_sync.rs) covers Enter/split insertion into plain imported Action, one transition to Scene Heading, later text insertion, undo/redo, and serialization. It does not repeatedly cycle Tab/Enter roles across a derived refresh or begin from the user's generated empty-heading shape. [`wo0011_imported_role_source_sync.rs`](../../crates/scriptcraft-core/tests/wo0011_imported_role_source_sync.rs) verifies role/source synchronization and unknown-attachment rollback independently. No authored case establishes the reported nonempty-semantic versus empty/different-source before-state.

A synchronization oracle should therefore use the exact saved shape as one fixture branch, alternate role creation and transition operations with derived refreshes, and stop at the first divergence rather than waiting for the later insertion error. It should inspect semantic text/runs and retained source projection in core test code, where document values are assertions rather than new desktop diagnostics. The later production order remains gated on that established divergence; the empty Text element itself remains legal under [`replace_text_element_children()`](../../crates/scriptcraft-core/src/preservation.rs:2821).

### 9.3 Generated-container deletion can be separated from split/join policy

The deletion failure is deterministic: [`remove_managed_paragraph()`](../../crates/scriptcraft-core/src/preservation.rs:1997) calls [`is_plain_managed_paragraph()`](../../crates/scriptcraft-core/src/preservation.rs:2708), which rejects generated SceneProperties before reference and identity removal. A narrow repair can classify the exact supported app-owned SceneProperties/SceneArcBeats shape using the same recognition rules as [`recognized_beat()`](../../crates/scriptcraft-core/src/scene_metadata.rs:761), require safe removal of the heading and every nested arc Paragraph identity, and remove that complete subtree with the heading. Unknown authored attachments, duplicate/ambiguous structures, external references, and unsafe identities must still reject the detached candidate.

This does not require relaxing [`change_managed_role()`](../../crates/scriptcraft-core/src/preservation.rs:1802) or [`replace_managed_projection()`](../../crates/scriptcraft-core/src/preservation.rs:2050). The durable contract explicitly retains Scene Heading split/join attachment safe-stops in [`AC-WRITING-003.5`](../../.forge/requirements/features/screenplay-writing-loop.md:292); the deletion order must not broaden into role-transition or split/join attachment destruction.

### 9.4 The zoom oracle bypasses the lifecycle implicated by the desktop report

The production path is capture in [`capture_pending_zoom_anchor()`](../../apps/scriptcraft/src/main.rs:666), possible manual-scroll cancellation in [`handle_surface_input()`](../../apps/scriptcraft/src/main.rs:1782), target queueing in [`live_document_surface()`](../../apps/scriptcraft/src/main.rs:1366), then geometry publication and one-shot consumption. The current desktop matrix in [`wo0012_desktop_zoom_keeps_the_viewport_anchor_once_or_clamps_at_an_edge()`](../../apps/scriptcraft/src/main.rs:6417) manually captures the anchor, assigns zoom state, invalidates geometry, and renders only the document surface. It does not drive native pinch through [`raw_input_hook()`](../../apps/scriptcraft/src/main.rs:2651) or slider/preset/keyboard input through the full application update.

The same matrix compares old/new page-local points but not page index or outside-page displacement, so it does not completely establish page/gap anchor preservation. Existing input tests and compensation tests therefore do not compose into an end-to-end result. A simultaneous raw scroll delta can explicitly cancel a pending anchor, but static inspection does not establish that the user's gesture produces that input combination; it is a reproduction branch, not a diagnosed root cause.

The zoom oracle order should add value-free lifecycle counters for capture success/miss, cancellation, queued compensation, and publication/consumption, then drive complete input-to-settled-scroll scenarios. It should compare page index, page-local point, and outside-page displacement except at clamped edges. Only the following repair order should change production behavior, based on the established failing stage.
